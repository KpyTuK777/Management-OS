# M6.14 — Design-to-Code Mapping

## Status

```text
Approved for M6 dependency use
Milestone M6 — Active
```

## Authority

This document is the canonical architecture definition of traceability from the
approved M6 Presentation Architecture into implementation-facing names,
interfaces, and artifacts. It owns the Design-to-Code Mapping Contract, mapping
taxonomy, mapping-record lifecycle, preservation and traceability rules,
compatibility and migration obligations, mapping conformance, and the boundary
between canonical presentation contracts and implementation artifacts.

It consumes all approved M6.1–M6.13 documents without modifying their meaning,
identity, ownership, lifecycle, state, composition, interaction, navigation,
rendering, accessibility, motion, conversational, or adapter contracts.

Mapping makes canonical meaning addressable by implementation. It never creates,
completes, corrects, or infers canonical meaning.

---

# 1. Purpose

The Presentation Architecture requires a stable, reviewable path from canonical
contracts to materially different implementations. Without that path,
implementation-facing names can drift, generated artifacts can appear
authoritative, and platform conventions can silently collapse professional
distinctions.

The model:

- identifies every mapped canonical source by stable identity and revision;
- defines implementation-facing names as replaceable aliases;
- permits multiple platform realizations of one canonical source;
- preserves all required distinctions across those realizations;
- records mapping coverage, compatibility, degradation, and evidence;
- prevents code and generated artifacts from becoming reverse-authoritative;
- supports deterministic change, deprecation, migration, and recovery;
- remains independent of implementation technology.

Design-to-Code Mapping is a translation ledger and conformance boundary. It is
not a programming model, schema, generator, repository convention, or source of
professional meaning.

---

# 2. Mapping Principles

1. **Canonical Source First.** Every semantic mapping begins at an approved,
   identified canonical source revision.
2. **Alias, Never Identity.** An implementation-facing name addresses a source;
   it does not become the source's canonical identity.
3. **One Meaning, Many Realizations.** Multiple platform realizations are
   permitted only when each preserves the same canonical obligations.
4. **No Reverse Authority.** Code, generated artifacts, and observed platform
   behavior cannot establish canonical truth.
5. **Complete or Explicitly Unmapped.** Required mapping coverage cannot be
   silently omitted.
6. **Evidence Before Conformance.** A declared mapping is not conformant without
   evidence for identity, revision, coverage, and preservation.
7. **Versioned Change.** Mapping changes are attributable and compatibility is
   evaluated against both source and mapping revisions.
8. **Mechanics Remain Replaceable.** Implementation technology may change
   without changing canonical meaning.
9. **Degradation Is a Disposition.** Unsupported or incomplete realization is
   explicit, deterministic, and reviewable.
10. **Atomic Publication.** Consumers observe one complete mapping revision,
    never a mixture of revisions.
11. **Accessibility Is Coequal.** Accessibility obligations are mapped with the
    represented contract, never added as optional metadata.
12. **Professional Intent Survives.** Names and interfaces cannot weaken
    authority, consequence, uncertainty, provenance, continuity, or recovery.

# 3. Design-to-Code Mapping Contract

## 3.1 Definition

A **Design-to-Code Mapping Contract** is the versioned canonical agreement that
associates an approved presentation-architecture source with one or more
implementation-facing aliases and required realization obligations.

It answers:

- which canonical source and revision are being realized;
- which mapping category and obligations apply;
- which implementation-facing alias identifies the realization;
- which target context the alias addresses;
- which dependencies and equivalence constraints must remain intact;
- what coverage, compatibility, degradation, and evidence disposition applies;
- how replacement, migration, and recovery are governed.

It does not prescribe the physical form of an interface or artifact.

## 3.2 Ownership

The Design-to-Code Mapping model owns only:

- mapping-record identity and revision;
- association between canonical source references and implementation-facing
  aliases;
- mapping category, target-context declaration, and coverage disposition;
- traceability, preservation, compatibility, migration, and evidence
  obligations;
- mapping publication, deprecation, withdrawal, and recovery rules;
- mapping-level conformance verdicts.

Ownership remains with approved upstream models for:

- professional truth, identity, authority, lifecycle, and relationships;
- Design Objects and semantic roles;
- Rendering Nodes, Rendering Tree identity, and projection;
- Semantic Tokens and symbolic meaning;
- Presentation State dimensions and valid transitions;
- component categories and composition;
- layout intent and structural relationships;
- interaction intent, eligibility, consequence, and recovery;
- navigation layers, transitions, context, and representation;
- rendering and platform adapter contracts;
- accessibility obligations;
- motion meaning;
- AI and conversational presentation.

Implementation Artifact Adapters own realization mechanics only. Code, generated
artifacts, and platform interfaces own neither canonical meaning nor mappings.

## 3.3 Mapping descriptor

Every mapping record contains, conceptually:

| Field | Obligation |
|---|---|
| **Mapping ID** | Stable identity of the mapping record, independent of file, tool, or target location. |
| **Mapping revision** | Immutable revision of this mapping definition. |
| **Canonical source ID** | Stable identifier supplied or governed by the owning canonical model. |
| **Canonical source revision** | Exact approved source revision to which the mapping conforms. |
| **Canonical owner** | Upstream model retaining authority. |
| **Mapping category** | Exactly one primary DCM category, with referenced cross-category dependencies. |
| **Source obligations** | Meaning, invariants, states, relationships, and outcomes that must survive realization. |
| **Target context** | Bounded implementation realization context without selecting its technology. |
| **Implementation-facing alias** | Replaceable address used by the target context. |
| **Realization multiplicity** | Declared one-to-one, one-to-many, or composed realization relationship. |
| **Dependency references** | Other mapping records required for a complete realization. |
| **Coverage disposition** | Complete, explicitly degraded, superseded, deprecated, withdrawn, or non-semantic. |
| **Compatibility disposition** | Compatible, migration-required, or incompatible, with basis. |
| **Degradation and recovery** | Explicit limitation, safe fallback, recovery condition, and continuity obligation. |
| **Evidence references** | Reviewable evidence supporting traceability and conformance. |
| **Lifecycle state** | Draft, validated, published, deprecated, superseded, or withdrawn. |

Descriptor fields are logical obligations, not a data schema. Their physical
representation is outside this architecture.

## 3.4 Responsibilities

The contract must:

1. bind every semantic realization to an approved source identity and revision;
2. preserve upstream ownership and all applicable invariants;
3. distinguish canonical identity, mapping identity, alias, and artifact
   identity;
4. declare complete mapping coverage and cross-category dependencies;
5. allow equivalent target-specific aliases without semantic divergence;
6. expose unsupported obligations and degraded dispositions;
7. make source and mapping changes compatibility-reviewable;
8. require migration and recovery evidence before replacement;
9. prevent generated or handwritten artifacts from acquiring authority;
10. support deterministic conformance decisions.

The contract must not:

- invent a source obligation missing from approved architecture;
- normalize away a canonical distinction for implementation convenience;
- treat naming similarity as identity or equivalence;
- derive canonical state from an artifact;
- allow target availability to redefine canonical validity;
- make one implementation the reference model for another.

## 3.5 Definition lifecycle

```text
Identify approved canonical source and revision
    ↓
Classify mapping category and target context
    ↓
Enumerate source obligations and dependencies
    ↓
Assign mapping identity and implementation-facing alias
    ↓
Evaluate coverage, compatibility, degradation, and recovery
    ↓
Collect preservation and traceability evidence
    ↓
Validate complete mapping revision
    ↓
Publish atomically
    ↓
Observe, deprecate, supersede, or withdraw under governance
```

A record cannot be published when its source is unapproved, its source revision
is unresolved, required obligations are absent, or evidence is incomplete.

## 3.6 Realization lifecycle

For each published mapping:

1. resolve the exact published mapping revision;
2. resolve its exact canonical source revision;
3. validate target context and declared dependencies;
4. realize only the declared source obligations;
5. expose any declared degradation before consequential use;
6. collect evidence against the resolved revisions;
7. publish the realization only after a conformant verdict;
8. retain traceability while the realization remains addressable;
9. migrate, supersede, or withdraw it without rewriting history.

Changing an alias, target context, obligation set, dependency, or disposition
creates a new mapping revision.

# 4. Mapping Taxonomy

## 4.1 Admission and classification

A mapping is semantic only when it traces to an approved M6 source. Every
semantic mapping has exactly one primary category. Dependencies on other
categories are explicit references, not duplicated definitions.

Pure mechanics may be marked **non-semantic** only when they neither express nor
affect canonical meaning, order, availability, authority, consequence,
accessibility, continuity, or recovery.

## 4.2 DCM-01 Design Object and Semantic Role Mapping

Maps canonical Design Object types, occurrences, primary semantic roles, and
qualifiers to implementation-facing aliases.

It must preserve object type, source identity, occurrence identity, role,
qualifiers, representation role, and prohibited ownership. It cannot turn an
implementation object into a Design Object or infer a role from artifact form.

## 4.3 DCM-02 Rendering Node and Tree Identity Mapping

Maps Rendering Node categories, node identity, tree-generation identity,
parentage, semantic order, cross-references, and replacement continuity.

Implementation tree position is not canonical parentage. Artifact reuse,
reordering, virtualization, or omission cannot alter canonical node identity or
the published Rendering Tree contract.

## 4.4 DCM-03 Semantic Token Mapping

Maps canonical token identities, categories, dimensions, combinations, and
resolved symbolic obligations to implementation-facing aliases.

Concrete values and target conventions remain downstream mechanics. Equal
values do not merge token identities; different values do not create new
canonical meaning.

## 4.5 DCM-04 Presentation State Mapping

Maps applicable Presentation State dimensions, snapshots, guards, transition
readiness, fidelity, and degraded dispositions.

Implementation state storage, events, or lifecycle callbacks cannot become
canonical state. Every target realization preserves independent dimensions and
valid successor constraints.

## 4.6 DCM-05 Component Mapping

Maps canonical component categories, contracts, admissible Rendering Node
subgraphs, containment, reuse, and replacement obligations.

A platform component name is an alias, not a canonical component category.
Convenience composition cannot transfer truth, interaction, navigation, or
state ownership to a component.

## 4.7 DCM-06 Composition and Layout Mapping

Maps typed component relationships, Structural Regions, Layout Intent,
containment, semantic order, adaptation, and atomic replacement obligations.

Physical arrangement may vary. Information residency, professional priority,
identity, relationship, reading order, continuity, and recoverability may not.

## 4.8 DCM-07 Interaction Mapping

Maps canonical interaction patterns, participant roles, eligibility, guarded
progression, validation, commitment, outcome, feedback, cancellation, retry,
interruption, and recovery.

Input events and handlers are mechanics. They cannot invent intent, grant
authority, combine distinct consequences, or treat acknowledgment as approval.

## 4.9 DCM-08 Navigation Representation Mapping

Maps navigation representation categories, destination references, exposure,
origin, continuity, interruption, suspension, return, history distinction, and
replacement.

Routes, addresses, containers, and dialogue topics are aliases or mechanics.
They do not own navigation state, priority, movement, or Context Envelope.

## 4.10 DCM-09 Rendering and Adapter Contract Mapping

Maps Rendering Contract and Adapter Contract identities, capability
requirements, matching outcomes, fallback order, degradation, recovery, and
evidence obligations.

Platform capability declarations describe mechanics; they cannot weaken the
canonical contract or promote a partial match to full equivalence.

## 4.11 DCM-10 Accessibility Mapping

Maps AO-01–AO-08 obligations together with semantic discoverability,
operability, perceivability, structural navigation, interaction equivalence,
presentation equivalence, degradation, and recovery.

Accessibility mapping is required wherever an obligation applies. A target API
or modality cannot redefine professional equivalence or waive an obligation.

## 4.12 DCM-11 Motion Mapping

Maps MT-01–MT-09 meaning, applicability, stable before/after states, no-motion
equivalence, interruption, degradation, and recovery.

Motion mechanics create no state or meaning. Absence of motion must preserve the
same professional interpretation and interaction outcome.

## 4.13 DCM-12 AI and Conversational Presentation Mapping

Maps CA-01–CA-08 contracts, projection identity, dialogue continuity,
conversational navigation, interaction equivalence, attribution, accessibility,
multimodal representation, degradation, correction, and recovery.

Language, dialogue state, generated expression, or model behavior cannot become
canonical truth, authority, Current Situation, Focus, Navigation, Operational
Memory, or canonical history.

## 4.14 Collective completeness

The taxonomy covers the full path from Design Object and semantic role through
rendering, tokens, state, component composition, interaction, navigation,
adapters, accessibility, motion, and conversational presentation.

A realization spanning categories must reference every applicable category.
Classification in one category never discharges obligations owned by another.

# 5. Deterministic Mapping and Traceability

## 5.1 Source identity and revision

1. Every semantic mapping resolves exactly one approved canonical source ID and
   exact source revision.
2. A source ID remains stable across compatible source revisions.
3. A changed source obligation requires a new source revision and mapping
   compatibility evaluation.
4. An unresolved, ambiguous, or unapproved source makes the mapping invalid.
5. A source citation without stable identity and revision is insufficient.

## 5.2 Alias and identity separation

Four identities remain distinct:

- canonical source identity;
- mapping-record identity;
- implementation-facing alias;
- realized-artifact identity.

Aliases may differ by target context and may change through migration. Alias
equality does not establish canonical equality; alias difference does not
establish semantic difference.

## 5.3 Multiplicity and equivalence

One canonical source may have multiple target realizations when:

- each resolves the same applicable source obligations;
- target-specific differences are mechanics or explicit degradation;
- cross-platform equivalence evidence exists;
- no realization is treated as the canonical template for another;
- every realization remains independently replaceable.

Many canonical sources may participate in one composed artifact only through
separate mapping records and explicit dependencies. Composition never merges
their identities or ownership.

## 5.4 Forward-only authority

The authoritative direction is:

```text
Approved canonical source revision
    ↓
Published mapping revision
    ↓
Qualified adapter realization
    ↓
Implementation artifact
```

Inspection of code may reveal drift or produce evidence, but it cannot define,
repair, or revise canonical meaning. Round-trip generation, reverse engineering,
usage frequency, runtime behavior, or artifact shape cannot be accepted as
canonical truth.

## 5.5 Completeness and testability

A mapping set is complete only when:

1. every applicable canonical obligation has a disposition;
2. every required category and dependency is represented;
3. unsupported obligations are explicitly degraded or blocking;
4. every alias resolves unambiguously within its target context;
5. preservation assertions have reviewable evidence;
6. normal, replacement, degraded, and recovery paths are testable;
7. the set can be reconstructed from published identities and revisions.

Silence, convention, or assumed platform behavior is not a disposition.

## 5.6 Deterministic resolution

Given the same approved source revisions, published mapping revision, target
context, and capability declaration, resolution must produce the same:

- applicable mapping records;
- aliases and dependencies;
- coverage and compatibility dispositions;
- required degradation and recovery obligations;
- conformance evidence requirements.

When inputs conflict or are incomplete, resolution fails closed and identifies
the unresolved obligation.

# 6. Change, Compatibility, Deprecation, and Migration

## 6.1 Change classification

Every change is classified as:

- **Editorial** — no change to identity, obligations, alias resolution, or
  disposition;
- **Compatible** — preserves all existing obligations while adding or replacing
  a realization without invalidating conformant consumers;
- **Migration-required** — preserves canonical meaning but requires consumers
  to adopt a new alias, dependency, or mapping revision;
- **Incompatible** — cannot preserve an existing consumer contract and requires
  explicit replacement governance;
- **Canonical-source change** — originates upstream and cannot be decided by
  this model.

Classification is evidence-backed and cannot be inferred solely from naming or
artifact compatibility.

## 6.2 Compatibility rules

Compatibility requires preservation of canonical identity, meaning,
relationships, state dimensions, order, authority, outcomes, accessibility,
continuity, degradation, and recovery.

Mechanical compatibility is insufficient when any semantic obligation changes.
A source revision and mapping revision are evaluated independently.

## 6.3 Deprecation

Deprecation:

- creates a new lifecycle disposition without deleting prior history;
- identifies the replacement mapping when one exists;
- states the compatibility and migration basis;
- retains source and evidence references while consumers remain;
- cannot make a canonical obligation optional;
- cannot silently redirect an alias to a semantically different source.

Withdrawal is permitted only when no active conformant consumer depends on the
mapping or when governance explicitly blocks unsafe continued use.

## 6.4 Migration

A migration plan declares:

- source and destination mapping revisions;
- affected aliases, target contexts, and dependencies;
- preserved obligations and known incompatibilities;
- coexistence and cutover rules;
- degraded behavior during transition;
- rollback or forward-recovery disposition;
- evidence required before completion.

Migration publication is atomic per consumer-visible mapping set. Partial
migration cannot mix incompatible source or mapping revisions.

---

# 7. Degradation and Recovery

## 7.1 Ordered degradation

When full realization is unavailable, resolve in this order:

1. an equivalent realization preserving all obligations;
2. an alternative composition preserving meaning and operation;
3. an explicit reduced realization preserving essential professional meaning,
   authority, accessibility, continuity, and recovery;
4. an explicit unavailable disposition that prevents misleading or unsafe use.

No fallback may fabricate support, suppress a required distinction, or imply a
canonical consequence that did not occur.

## 7.2 Degradation record

Every degraded mapping identifies:

- affected source, mapping, and target revisions;
- unsupported obligation and cause;
- preserved and unavailable capabilities;
- professional and accessibility impact;
- safe fallback or blocked operation;
- recovery condition and continuity requirement;
- evidence and review status.

## 7.3 Recovery

Recovery must:

1. resolve a valid published mapping and source revision;
2. re-evaluate capabilities and dependencies;
3. preserve canonical and occurrence identity;
4. prevent duplicate interaction or navigation outcomes;
5. restore accessibility, motion/no-motion, and multimodal equivalence;
6. replace the degraded mapping atomically;
7. record whether continuity was preserved;
8. collect fresh conformance evidence.

Cached or generated artifacts cannot self-certify recovery.

# 8. Adapter Boundary

## 8.1 Boundary

```text
Canonical Presentation Architecture
    ↓ canonical source identities, revisions, and obligations
Design-to-Code Mapping Contract
    ↓ aliases, coverage, dependencies, and conformance requirements
Implementation Artifact Adapter
    ↓ technology-specific realization mechanics
Code / Generated Artifacts / Platform Interfaces
```

## 8.2 Canonical Presentation Architecture

The canonical layer owns all meaning, identity, state, relationships,
composition, interaction, navigation, rendering obligations, accessibility,
motion semantics, conversational contracts, authority, and invariants.

It supplies the sources to be mapped. It does not depend on an implementation
artifact for its validity.

## 8.3 Design-to-Code Mapping Contract

The mapping layer owns traceability and implementation-facing addressability.
It binds aliases to canonical sources, declares coverage and compatibility, and
defines evidence required for conformance.

It owns neither upstream meaning nor downstream mechanics.

## 8.4 Implementation Artifact Adapter

The adapter:

- resolves published mappings for a declared target context;
- realizes aliases through target mechanics;
- preserves declared obligations and dependency boundaries;
- reports capabilities, limitations, failures, and evidence;
- applies approved migration, degradation, and recovery dispositions.

It cannot reinterpret a source, create a mapping, infer canonical truth from an
artifact, or declare architecture approval.

## 8.5 Code, Generated Artifacts, and Platform Interfaces

The lowest layer performs mechanics only. Handwritten and generated artifacts
have equal non-authoritative status. Their names, structures, interfaces,
defaults, inferred relationships, and runtime behavior do not create canonical
meaning.

## 8.6 Boundary failures

The boundary fails when:

- an alias or artifact is treated as canonical identity;
- code is used to infer an absent source obligation;
- generation output changes meaning or ownership;
- platform limitations silently remove an obligation;
- a target interface creates authority, state, navigation, or consequence;
- a mapping embeds technology-specific structure as canonical;
- drift evidence rewrites the mapping instead of triggering review;
- a lower layer certifies its own architecture conformance without evidence.

# 10. Validation and Conformance

## 10.1 Required evidence

Conformance evidence must include:

- source-ID and source-revision resolution for every mapping;
- mapping-ID, revision, category, alias, and target-context inventory;
- complete obligation and dependency coverage;
- evidence that aliases do not replace source identity;
- equivalence evidence for every multi-platform realization;
- state, composition, interaction, navigation, accessibility, motion, and
  conversational preservation where applicable;
- deterministic resolution results for identical inputs;
- explicit unsupported and degraded dispositions;
- compatibility and migration evidence for changed mappings;
- replacement and recovery continuity evidence;
- proof that generated and handwritten artifacts remain non-authoritative;
- negative evidence for boundary-failure scenarios.

Evidence identifies the canonical and mapping revisions it tests. Evidence for
one realization cannot silently certify another.

## 10.2 Deterministic verdict

A mapping revision receives exactly one verdict:

```text
Conformant
```

or:

```text
Non-conformant
```

It is **Conformant** only when all applicable obligations are covered, all
dependencies resolve, preservation rules hold, degradation is explicit,
evidence is complete, and no invariant is violated.

Any unresolved source, missing obligation, ambiguous alias, silent degradation,
semantic divergence, reverse authority, incomplete migration, or missing
evidence produces **Non-conformant**.

## 10.3 Architecture conformance criteria

The architecture is conformant when:

1. the twelve-category taxonomy covers every approved M6 presentation model;
2. canonical identity, mapping identity, alias, and artifact identity remain
   distinct;
3. mappings are versioned, complete, deterministic, testable, replaceable, and
   evidence-backed;
4. multiple realizations preserve semantic and professional equivalence;
5. code and generated artifacts cannot become canonical truth;
6. change, compatibility, deprecation, and migration are governed;
7. degradation and recovery are explicit and deterministic;
8. all upstream ownership boundaries remain intact;
9. lower layers own mechanics only;
10. no implementation technology is selected.

# Explicit Exclusions

This architecture does not define:

- programming languages;
- application or UI frameworks;
- serialization, metadata, or interface schemas;
- code generators or generation templates;
- naming syntax or naming conventions;
- build tools, package systems, or compilers;
- repositories, branches, modules, directories, or file layouts;
- API signatures, protocols, concrete interfaces, or concrete types;
- source-code structure or implementation code;
- platform-specific mappings or decisions;
- design-tool plugins or synchronization mechanisms;
- runtime topology, deployment, or persistence mechanics.

These are replaceable implementation concerns constrained by the canonical
mapping contract.
