# M6.10 — Rendering Contracts and Platform Adapters

## Status

```text
Approved for M6 dependency use
```

## Authority

This document is the canonical architecture definition of the boundary between
the M6 Canonical Presentation Architecture and platform implementations. It
owns Rendering Contract structure, the Adapter Contract taxonomy, capability
matching, degradation and fallback obligations, adapter qualification, and
conformance evidence.

It consumes the Canonical Management Model, M6 Charter, Canonical Design Object
Model, Canonical Design Semantics, Canonical Rendering Model, Semantic Token
Architecture, Presentation State Model, Canonical Component Model, Composition
and Layout System, Canonical Interaction Patterns, and Navigation
Representation Model without modifying them.

---

# 1. Purpose

The Canonical Presentation Architecture defines professional meaning,
presentation structure, state, composition, interaction, and navigation
representation independently of a platform. A concrete platform cannot consume
those definitions safely unless the handoff is explicit, complete, and
testable.

A **Rendering Contract** specifies what a platform realization must preserve.
It never specifies how rendering is implemented.

This model:

- aggregates all M6 presentation obligations at one platform boundary;
- makes preservation requirements explicit and traceable;
- separates canonical responsibility, adapter translation, and framework
  mechanics;
- resolves platform capability differences deterministically;
- permits implementation freedom without semantic freedom;
- makes degradation visible, bounded, and reviewable;
- provides one conformance verdict for a Platform Adapter.

It does not create presentation meaning. It protects meaning while it crosses
the final architecture boundary.

---

# 2. Contract Principles

1. **Preservation Before Realization.** A platform mechanism is admissible only
   after its preservation obligations are known.
2. **What, Never How.** Contracts state observable guarantees and prohibited
   transformations, not implementation techniques.
3. **One Aggregate Boundary.** Every platform realization is qualified through
   one complete Adapter Contract Set.
4. **Canonical Sources Remain Authoritative.** An adapter may translate a
   canonical contract but cannot reinterpret it.
5. **Declared Capability Only.** Undeclared capability cannot be assumed.
6. **Deterministic Matching.** Identical canonical inputs, contract revisions,
   and capability declarations produce the same qualification outcome.
7. **Explicit Degradation.** Reduced expression is never silent and never
   changes canonical meaning.
8. **Fail Closed.** If required meaning cannot be preserved, the realization is
   incompatible rather than approximately conformant.
9. **Traceability End to End.** Every realized obligation traces to its
   canonical source and its conformance evidence.
10. **Adapter Neutrality.** No canonical contract favors a platform,
    interaction mechanism, sensory channel, or implementation technology.
11. **Framework Subordination.** Framework convenience cannot override an
    adapter obligation.
12. **Accessible Equivalence.** An alternative expression must preserve
    professional meaning, operability, order, and consequence.

# 3. Rendering Contract

## 3.1 Definition

A **Rendering Contract** is a versioned, implementation-independent statement
of the canonical input, preservation obligations, admissible outcomes,
prohibited transformations, degradation policy, and evidence required at a
platform boundary.

It is not a Rendering Node, Rendering Tree, component, layout, style, theme,
platform capability, implementation interface, or guarantee of identical
physical appearance.

## 3.2 Ownership

This model owns:

- the Rendering Contract descriptor;
- AC-01–AC-11 and their non-overlapping responsibilities;
- Adapter Contract Set completeness;
- capability declaration and matching rules;
- fallback and degradation disposition;
- adapter qualification and conformance evidence;
- the three-layer platform boundary.

Upstream canonical models retain exclusive ownership of Design Objects,
Semantic Roles, Rendering Nodes and Trees, Semantic Tokens, Presentation State,
Canonical Components, Composition Plans, Structural Regions, Layout Intent,
Canonical Interaction Patterns, Navigation Representation, and all
professional or domain truth.

A Platform Adapter owns only the translation of a valid Adapter Contract Set
into platform capabilities. A Platform UI Framework owns only technical
mechanics.

## 3.3 Contract descriptor

Every Rendering Contract contains:

| Field | Required meaning |
| --- | --- |
| **Contract ID** | Stable AC identifier. |
| **Revision** | Immutable contract revision. |
| **Canonical sources** | Exact source documents, identifiers, and revisions. |
| **Input scope** | Canonical objects and states governed by the contract. |
| **Preservation obligations** | Meaning, identity, structure, order, state, or consequence that must survive realization. |
| **Required capabilities** | Abstract capabilities needed to satisfy the obligations. |
| **Admissible outcomes** | Complete, Explicitly Degraded, or Incompatible. |
| **Fallback policy** | Ordered meaning-preserving alternatives permitted by canonical sources. |
| **Prohibited transformations** | Changes an adapter must never perform. |
| **Determinism basis** | Inputs that must yield the same resolution. |
| **Evidence obligations** | Proof required for a conformance verdict. |
| **Continuity obligations** | Identity, focus, state, and replacement continuity that must survive. |
| **Known limitations** | Explicit boundaries of the realization. |

An incomplete descriptor is not a Rendering Contract.

## 3.4 Adapter Contract Set

An **Adapter Contract Set** is the atomic, versioned aggregate of AC-01–AC-11
for one adapter identity and capability declaration. It is the only valid
handoff from Canonical Presentation Architecture to a Platform Adapter.

The set references one compatible revision of every required upstream
contract, covers every canonical occurrence in scope, contains no conflicting
obligation, carries one capability-match result and one conformance verdict,
and is replaced atomically when a source revision changes. An adapter cannot
select only convenient contracts from the set.

# 4. Contract Lifecycle

## 4.1 Rendering Contract definition lifecycle

```text
Proposed → Registered → Active → Deprecated → Retired
```

- **Proposed** may be reviewed but cannot qualify an adapter.
- **Registered** has a stable ID, complete descriptor, and source traceability.
- **Active** is mandatory for new Adapter Contract Sets.
- **Deprecated** remains interpretable during an explicit migration window but
  cannot be selected for a new adapter.
- **Retired** is historical and cannot govern a current realization.

A contract revision is never edited in place. A changed obligation creates a
new revision.

## 4.2 Adapter qualification lifecycle

```text
Required
    ↓
Capabilities Declared
    ↓
Contracts Matched
    ↓
Validated
    ↓
Qualified
    ↓
Superseded or Retired
```

Required identifies the exact active set. Capabilities Declared records
explicit capabilities and limitations. Contracts Matched resolves every
obligation to a capability, approved fallback, or incompatibility. Validated
attaches complete evidence. Qualified permits realization for that exact set
and declaration. A source, contract, or capability revision supersedes prior
qualification. Any failed validation yields **Not Qualified**.

# 5. Adapter Contract Taxonomy

## 5.1 Admission and exclusivity

A category is canonical only when it owns a distinct boundary responsibility,
has upstream authority, produces observable obligations, and cannot be fully
represented by another category. Each obligation has one primary AC owner.
Cross-category dependencies are references, not duplicated ownership.

## 5.2 Canonical categories

| ID | Contract category | Primary responsibility | Canonical sources |
| --- | --- | --- | --- |
| **AC-01** | Rendering Projection Contract | Preserve Rendering Tree generation, node identity, correspondence, parentage, semantic order, references, continuity, and atomic replacement. | Canonical Rendering Model; Design Object Model |
| **AC-02** | Semantic Preservation Contract | Preserve Semantic Roles, semantic dimensions, distinctions, priority, and forbidden ambiguity across every supported expression. | Canonical Design Semantics; Visual Semantics |
| **AC-03** | Token Realization Contract | Realize resolved Semantic Token meaning without merging dimensions or promoting platform values to canonical status. | Semantic Token Architecture |
| **AC-04** | Presentation State Realization Contract | Preserve valid Presentation State, orthogonality, precedence, continuity, and deterministic state disposition. | Presentation State Model |
| **AC-05** | Component Realization Contract | Preserve Canonical Component identity, professional responsibility, admissible node structure, slots, replacement, and reuse boundaries. | Canonical Component Model |
| **AC-06** | Composition and Layout Realization Contract | Preserve Composition Plan relationships, containment, semantic order, Structural Regions, boundaries, and Layout Intent independently of geometry. | Composition and Layout System |
| **AC-07** | Interaction Realization Contract | Preserve Interaction Pattern participants, preconditions, authority checks, progression, consequences, cancellation, retry, interruption, recovery, and idempotency. | Canonical Interaction Patterns; Operational Interaction Language |
| **AC-08** | Navigation Representation Contract | Preserve NR-01–NR-08 distinctions, current context, destinations, origin, return, interruption, suspended context, continuity, history representation, and recovery without owning navigation. | Navigation Representation Model; Operational Navigation; Navigation Governance |
| **AC-09** | Degradation and Fallback Contract | Resolve capability gaps through ordered, source-authorized, explicit alternatives without semantic loss or hidden approximation. | All applicable M6 source contracts |
| **AC-10** | Capability Declaration Contract | State adapter identity, supported abstract capabilities, limitations, and revision-bound coverage without inferring support. | This model and source capability obligations |
| **AC-11** | Conformance Evidence Contract | Prove complete coverage, deterministic resolution, preservation, degradation honesty, and boundary compliance for the whole Adapter Contract Set. | This model and AC-01–AC-10 |

## 5.3 Required coverage

An Adapter Contract Set is complete only when:

- AC-01 traces every in-scope DO occurrence to its RN occurrence;
- AC-02 covers every applied DSR and independent semantic dimension;
- AC-03 covers every resolved STC obligation;
- AC-04 covers every active PSD dimension and valid combination;
- AC-05 covers every in-scope CCT definition and occurrence;
- AC-06 covers every in-scope CR, SR, and LI obligation;
- AC-07 covers every in-scope CIP occurrence and its OI source;
- AC-08 covers every required NR representation and NAV source;
- AC-09 resolves every declared capability gap;
- AC-10 declares every capability used by AC-01–AC-09;
- AC-11 supplies evidence for every preceding category.

Missing coverage makes the set Incompatible.

# 6. Capability Declaration and Matching

## 6.1 Capability Declaration

A Capability Declaration is immutable for a qualification attempt and includes:

- adapter identity and revision;
- supported presentation modalities and perceivable channels;
- tree, identity, ordering, reference, and atomic replacement support;
- semantic distinguishability and redundancy support;
- token and Presentation State realization support;
- component, composition, Structural Region, and Layout Intent support;
- interaction progression, interruption, completion, cancellation, retry,
  recovery, authority-validation, and idempotency support;
- navigation continuity, suspension, return, history, and recovery support;
- accessibility-equivalence, persistence, and recovery capabilities;
- supported fallback classes, limitations, unavailable capabilities, and
  evidence references.

The declaration describes capability, not mechanism. Omission means
unsupported.

## 6.2 Deterministic matching

```text
Active Adapter Contract Set
        +
Canonical input revisions
        +
Capability Declaration
        ↓
Coverage Matrix
        ↓
Complete | Explicitly Degraded | Incompatible
```

For each obligation, matching identifies the single owning category, resolves
the exact source, finds a declared direct capability, evaluates approved
fallbacks in canonical order if necessary, records the selection, verifies
preservation and continuity, attaches evidence, and rejects unresolved or
contradictory matches.

The same inputs produce the same matrix and outcome. Platform preference,
performance convenience, and framework defaults cannot influence the result.

## 6.3 Match outcomes

- **Complete** — every obligation has a direct, meaning-preserving realization.
- **Explicitly Degraded** — every unavailable direct capability has an approved
  meaning-preserving fallback, and the limitation is exposed.
- **Incompatible** — a mandatory meaning, operation, order, identity,
  consequence, recovery obligation, or required distinction cannot be
  preserved.

Only Complete or Explicitly Degraded sets proceed to validation. Explicitly
Degraded is not Complete and cannot be reported as such.

# 7. Adapter Responsibilities

## 7.1 Required guarantees

A Platform Adapter must:

1. consume only a valid, current Adapter Contract Set;
2. preserve source identity and revision traceability;
3. preserve Design Object to Rendering Node correspondence;
4. preserve Semantic Role meaning and independent dimensions;
5. preserve tree structure, parentage, order, references, and atomic
   replacement;
6. preserve Semantic Token meaning without giving platform values canonical
   authority;
7. preserve Presentation State meaning, precedence, continuity, and validity;
8. preserve Component responsibility, Composition Plan relationships,
   Structural Regions, and Layout Intent;
9. preserve interaction intent, validation, authority, consequence,
   cancellation, retry, recovery, and idempotency;
10. preserve navigation ownership, distinctions, continuity, interruption,
    return, history representation, and recovery;
11. preserve perceivable and operable equivalence across supported channels;
12. expose every degradation and known limitation;
13. use only declared capabilities and approved fallbacks;
14. provide complete, reproducible evidence;
15. replace realized generations atomically and keep incomplete generations
    non-current;
16. keep platform state and canonical state distinguishable;
17. preserve append-only and post-commit correction boundaries;
18. reject obligations it cannot preserve.

## 7.2 Prohibited transformations

A Platform Adapter must never:

- create, remove, merge, split, or reinterpret canonical meaning;
- infer authority, urgency, priority, focus, certainty, ownership, currentness,
  or lifecycle from presentation;
- collapse independent semantic dimensions into one ambiguous signal;
- turn platform containment or grouping into domain ownership;
- turn technical runtime state into Presentation State or Current Situation;
- turn local interaction completion into canonical commitment;
- bypass validation, authority, freshness, concurrency, or idempotency;
- treat platform navigation history as canonical history or Operational Memory;
- change destination eligibility, interruption class, origin, or return;
- rewrite canonical history or conceal correction and reversal;
- use stale, partial, or mixed contract revisions;
- silently omit unsupported content, operation, relation, state, or distinction;
- apply an unregistered fallback or report degradation as complete;
- write platform values or mechanics back as canonical truth;
- allow framework defaults to override semantic order or consequence;
- produce a current realization from an incomplete generation.

# 8. Fallback and Degradation

## 8.1 Ordered fallback policy

When a direct capability is unavailable, the adapter evaluates only:

1. an equivalent expression in the intended modality;
2. an equivalent expression through another supported modality or perceivable
   channel;
3. a serialized expression preserving identity, semantic order, relationships,
   continuity, and operation;
4. a source-authorized summary or deferral preserving access to the complete
   canonical source;
5. an explicit degradation with preserved essential meaning and a disclosed
   limitation;
6. Incompatible.

The first conformant option is selected. An adapter cannot skip to a preferred
or cheaper fallback.

## 8.2 Degradation and recovery

Degradation is admissible only when the source permits it; no fact, authority,
consequence, identity, or distinction is fabricated or contradicted; required
detail remains recoverable; unavailable operation is explicit; degradation is
distinguishable from completion; continuity is intact; and AC-11 evidence
proves the outcome. Otherwise the result is Incompatible.

When capability becomes sufficient, the adapter rematches the current set,
rebuilds from canonical inputs, preserves identity and continuity, replaces the
degraded generation atomically, and creates no domain event merely because
presentation improved.

---

# 9. Deterministic Rendering Guarantee

Deterministic rendering at this boundary means:

> The same canonical inputs, source revisions, Adapter Contract Set, Capability
> Declaration, and permitted fallback order produce the same obligation
> coverage, mappings, semantic order, state disposition, degradation outcome,
> and conformance verdict.

It does not require identical physical appearance, geometry, timing, platform
values, or implementation mechanics.

Determinism requires stable identifiers, total obligation resolution, one
primary owner per obligation, stable matching and fallback order, no undeclared
environment dependency, no framework-default semantic decisions, atomic
publication, and reproducible evidence.

# 10. Three-Layer Platform Boundary

## 10.1 Boundary

```text
Canonical Presentation Architecture
        ↓  Adapter Contract Set
Platform Adapter
        ↓  Meaning-preserving technical mapping
Platform UI Framework
```

No lower layer may bypass the layer immediately above it to reinterpret an
upstream canonical source.

## 10.2 Canonical Presentation Architecture

The canonical layer owns professional meaning and all M6 source contracts,
produces valid canonical presentation inputs, emits the complete compatible
Adapter Contract Set, defines allowed fallbacks and evidence, remains
independent of platform capabilities, and never selects technical mechanisms or
values.

## 10.3 Platform Adapter

The adapter declares capabilities, translates the complete set, selects only
deterministic approved fallbacks, maintains occurrence traceability, isolates
framework mechanics, validates complete generations, exposes limitations, and
never owns or reinterprets canonical sources.

## 10.4 Platform UI Framework

The framework supplies technical rendering, layout, state, input, navigation,
persistence, and accessibility mechanics; realizes only adapter mappings; may
optimize mechanics without changing contract outcomes; reports capability and
failure information; and establishes no canonical truth.

Framework output is a platform realization, never canonical architecture.

## 10.5 Boundary failures

The boundary fails if the canonical layer selects a mechanism, the adapter
changes professional meaning, the framework interprets sources directly,
framework state becomes canonical state, adapter limitations are hidden, or
two layers share responsibility ownership.

# 12. Conformance Evidence

## 12.1 Required evidence

A qualification package contains:

- exact Adapter Contract Set, sources, and Capability Declaration;
- an AC-01–AC-11 coverage matrix;
- traceability for in-scope DO, DSR, RN, STC, PSD, CCT, CR, SR, LI, CIP, OI,
  NR, and NAV identifiers;
- direct-capability and fallback selections;
- Complete, Explicitly Degraded, and Incompatible scenarios;
- semantic-distinction and accessibility-equivalence evidence;
- state, identity, order, continuity, and atomic-replacement evidence;
- interaction authority, idempotency, interruption, and recovery evidence;
- navigation continuity, suspension, return, degradation, and recovery evidence;
- deterministic rerun evidence;
- prohibited-transformation audit, limitations, and final verdict.

Evidence proves observable obligations. It does not prescribe implementation
code or framework internals.

## 12.2 Deterministic verdict

```text
Conformant
```

requires Complete or valid Explicitly Degraded matching, full AC-01–AC-11
coverage, no prohibited transformation, complete reproducible evidence, no
unresolved mandatory obligation, and mutually exclusive layer ownership.
Otherwise the verdict is:

```text
Non-conformant
```

No conditional or implied conformance verdict is allowed.
