# M6.8 — Canonical Interaction Patterns

## Status

```text
Approved for M6 dependency use
Milestone M6
```

## Authority

This document is the single source of truth for reusable,
platform-independent interaction patterns consumed by Canonical Components and
Composition Plans. It defines pattern identity, ownership, lifecycle, taxonomy,
participants, initiation, progression, interruption, completion, cancellation,
retry, recovery, composition, the Platform Interaction Runtime boundary, and
conformance.

Canonical Interaction Patterns orchestrate interactions from the approved
Canonical Operational Interaction Language. They create no interaction
vocabulary, professional intent, authority, consequence, lifecycle, or domain
truth.

# 1. Purpose

The Canonical Operational Interaction Language defines what each professional
interaction means. M6 components and composition plans define where interaction
responsibilities can be presented. A reusable architectural contract is still
required to preserve the full interaction obligation across contexts and
platform mechanics.

```text
One or more OI-01–OI-61 interaction contracts
        +
Canonical Component participants
        +
Composition Plan context and continuity
        +
Rendering, Token, and Presentation State obligations
        ↓
Canonical Interaction Pattern
        ↓
Validated Pattern Occurrence
        ↓
Platform Interaction Runtime
```

An Interaction Pattern answers:

> How are existing professional interactions safely orchestrated and made
> reusable without changing their meaning?

It does not answer:

> Which device event or runtime mechanism invokes them?

# 2. Interaction Pattern Principles

1. **Vocabulary Preserved.** Every pattern step references one OI-01–OI-61
   interaction and never invents another professional intent.
2. **Contract, Not Flow Implementation.** A pattern defines professional
   responsibilities, guards, consequences, and recovery, not runtime mechanics.
3. **One Primary Pattern Responsibility.** Every pattern has one bounded
   orchestration purpose.
4. **Authority Remains Source-Owned.** Pattern availability, progression, or
   component placement grants no authority.
5. **Attempt Before Consequence.** Initiation creates an attempt, not canonical
   commitment.
6. **Validation Before Commitment.** Identity, authority, freshness,
   concurrency, and interaction-specific guards precede every consequential
   commitment.
7. **Cancellation Is Pre-Commit Only.** Cancellation before commitment has no
   canonical consequence.
8. **Append-Only After Commitment.** After commitment, correction or reversal
   occurs through a new authorized canonical interaction and event.
9. **Retry Is a New Attempt.** Retry never re-executes a previous commitment.
10. **Interruption Preserves Identity.** Interruption preserves attempt,
    context, known progress, indeterminacy, and recovery path.
11. **Feedback Is Attributable.** Receipt, validation, commitment, completion,
    failure, and recovery remain distinguishable.
12. **Components Do Not Execute.** Components present participants and
    obligations; the owning interaction contract governs consequence.
13. **Presentation State Is Not Interaction State.** PSD values may express
    condition but never prove validation, commitment, or outcome.
14. **Deterministic Orchestration.** Equivalent canonical input and pattern
    revision produce equivalent admissible progression.
15. **Adapter Neutral.** Pattern meaning survives materially different input and
    runtime mechanics.
16. **Accessible Equivalence.** Intent, precondition, consequence, state,
    feedback, cancellation, and recovery remain recoverable.
17. **No Hidden Transaction.** Pattern composition never creates an undeclared
    transaction across independent canonical interactions.
18. **No Implicit Navigation.** Pattern progression changes context only through
    an explicit OI navigation interaction.
19. **No Implicit Lifecycle.** Pattern completion does not advance Matter
    lifecycle or Operational Transition unless the referenced OI contract owns
    that consequence.
20. **No Rollback of History.** Runtime rollback cannot erase canonical events.

# 3. Canonical Interaction Pattern Contract

## 3.1 Definition

A Canonical Interaction Pattern Definition is a versioned orchestration
contract containing:

- one stable Pattern ID and category;
- one bounded professional orchestration responsibility;
- one or more referenced OI contracts;
- admissible participant roles;
- preconditions and authority sources;
- progression and branching rules;
- completion and outcome distinctions;
- cancellation, retry, interruption, recovery, correction, and reversal
  obligations;
- component, composition, token, state, and feedback bindings;
- platform-runtime obligations and prohibited implications.

A Pattern Occurrence is one attributable application of an active definition in
one professional context.

## 3.2 Ownership

Canonical Interaction Patterns own only:

- pattern identity, category, version, and orchestration responsibility;
- OI step composition without semantic modification;
- participant-role and component-binding contracts;
- pattern occurrence lifecycle and progression validation;
- interruption, cancellation, retry, and recovery orchestration;
- completion and feedback distinctions;
- the Platform Interaction Runtime boundary;
- pattern conformance.

Ownership remains outside this model for:

| Concern | Owner |
|---|---|
| Professional interaction vocabulary, intent, consequence, authority, persistence, cancellation, retry, and recovery semantics | Canonical Operational Interaction Language |
| Canonical commitment, append-only events, replay, and correction history | Operational Memory and owning domain model |
| Professional truth, objects, and lifecycle | Canonical Management Model and owning source models |
| Navigation, interruption classification, and professional Current Focus | Operational Navigation and Navigation Governance |
| Rendering Node interaction and feedback contracts | Canonical Rendering Model |
| Interaction and continuity tokens | Semantic Token Architecture |
| Presentation-only condition | Presentation State Model |
| Reusable presentation participants | Canonical Component Model |
| Structural Regions, order, and Layout Intent | Composition and Layout System |
| Input mechanics, scheduling, and runtime execution | Platform Interaction Runtime |

## 3.3 Pattern definition descriptor

Every pattern definition declares:

| Field | Requirement |
|---|---|
| **Pattern ID and version** | Stable identity and monotonic definition revision. |
| **Category** | Exactly one CIP-01–CIP-12 category. |
| **Primary responsibility** | One bounded professional orchestration purpose. |
| **OI contracts** | Exact OI IDs, order constraints, and step responsibilities. |
| **Participants** | Required and optional participant roles and eligibility. |
| **Context boundary** | Matter/non-production scope, Context Envelope reference, origin, and return. |
| **Initiation contract** | Eligible initiator, subject, intent, and attempt creation. |
| **Preconditions** | Identity, authority, freshness, concurrency, source, and OI-specific guards. |
| **Progression graph** | Permitted phases, branches, dependencies, and terminal results. |
| **Canonical-consequence boundary** | Exact point at which commitment may create a canonical event. |
| **Cancellation and retry** | Pre-commit cancellation and new-attempt retry obligations. |
| **Interruption and recovery** | Preservation, indeterminacy, resume/revalidation, and fallback. |
| **Outcome contract** | No-consequence completion, canonical commitment, rejection, failure, or indeterminate result. |
| **Component bindings** | Required CCT participant responsibilities and admissible plan regions. |
| **Feedback contract** | Required receipt, validation, commitment, completion, failure, and recovery distinctions. |
| **Idempotency contract** | Identity used to prevent duplicate canonical consequence. |
| **Adapter obligation** | Professional meaning the Platform Interaction Runtime must preserve. |
| **Prohibited implications** | Meaning no progression or runtime mechanic may introduce. |
| **Lifecycle condition** | Proposed, Registered, Active, Deprecated, or Retired. |

## 3.4 Pattern occurrence descriptor

Every occurrence declares:

| Field | Requirement |
|---|---|
| **Occurrence ID** | Identity of this pattern application. |
| **Definition reference** | Exact Pattern ID and active version. |
| **Attempt ID** | Unique identity of the current attempt. |
| **Actor and authority references** | Attributable actor plus current authority source and scope. |
| **Subject and context** | Exact canonical/source identities and Context Envelope reference. |
| **Current phase** | One permitted pattern-occurrence lifecycle phase. |
| **Completed OI steps** | Attributable step results without inferred commitment. |
| **Pending OI step** | Exact next eligible interaction contract. |
| **Component and plan references** | Exact current participant instances and composition plan. |
| **Feedback state** | Receipt, validation, commitment, completion, failure, interruption, or recovery distinction. |
| **Canonical event reference** | Present only after proven canonical commitment. |
| **Origin and return** | Preserved continuity and valid recovery target. |
| **Previous attempt** | Link when this occurrence is a retry. |
| **Conformance result** | Complete, interrupted, indeterminate, invalid, or terminal. |

# 4. Pattern Lifecycle

## 4.1 Definition lifecycle

Pattern definition lifecycle is governance metadata:

```text
Proposed
    ↓ Architecture Review
Registered
    ↓ Approved use
Active
    ↓ Compatible successor
Deprecated
    ↓ Migration complete
Retired
```

Changed OI meaning, canonical-consequence boundary, primary responsibility, or
authority contract requires a new Pattern ID.

## 4.2 Occurrence lifecycle

The occurrence lifecycle consumes the OIL canonical interaction lifecycle:

```text
Eligible
    ↓
Attempt
    ↓
Validation
    ├─ Invalid ───────────────► End — no canonical consequence
    ├─ Cancellation ──────────► End — no canonical consequence
    └─ Ready
         ├─ Completion without canonical consequence
         │      └─────────────► End
         └─ Commitment
                ↓
         Canonical Event evidence
                ↓
         Completion
                ↓
         Recovery / later Correction or Reversal when required
```

Interruption may occur before a terminal result:

```text
Non-terminal occurrence
    ↓
Interrupted
    ↓
Recover
    ├─ Revalidate and continue the same valid attempt
    ├─ End as indeterminate with explicit reconciliation
    └─ Retry as a new linked Attempt
```

The pattern lifecycle does not replace OIL interaction semantics or create a
domain lifecycle.

# 5. Participant Roles

Participant roles are references to existing actors, objects, components, and
governance contracts. They create no new domain actors.

| Participant role | Responsibility | Required basis |
|---|---|---|
| **Initiating Actor** | Express the professional intent that creates the attempt. | Authenticated identity and eligible OI intent. |
| **Authorized Actor** | Supply authority where the OI contract requires it. | Current authority source, scope, and validity. |
| **Professional Subject** | Be the identified object or projection to which intent applies. | Canonical/source identity and current revision. |
| **Context Carrier** | Preserve Matter/non-production boundary, origin, purpose, and return. | Valid Context Envelope and Navigation projection. |
| **Action Participant** | Present one eligible professional action. | CCT-07 with RN-08, STC-04, and exact OI mapping. |
| **Feedback Participant** | Present attributable processing condition and next valid path. | CCT-08 with RN-10 and operation identity. |
| **Supporting Participant** | Provide required subject, evidence, comparison, explanation, or context. | Compatible CCT-02–CCT-06 or CCT-09 responsibility. |
| **Canonical Recorder** | Append proven consequential event under owning model. | Operational Memory/domain command boundary. |
| **Navigation Coordinator** | Apply explicit Navigate, Return, Interrupt, or Recover Context contracts. | OI-51–OI-55 and canonical Navigation. |
| **Platform Runtime** | Apply mechanics to a validated pattern contract. | Platform Interaction Runtime boundary. |

One actor may fulfill several eligible roles, but each responsibility and
authority source remains explicit.

# 6. Canonical Pattern Taxonomy

## 6.1 Admission rule

A category exists only when it:

- groups a distinct family of OI responsibilities;
- has stable participant, consequence, and recovery boundaries;
- remains reusable across components, composition plans, and adapters;
- introduces no new professional interaction;
- cannot merge with another category without obscuring authority or consequence.

## 6.2 Taxonomy and OI coverage

| ID | Category | OI coverage | Primary orchestration responsibility |
|---|---|---|---|
| **CIP-01** | **Retrieval and Review** | OI-01–OI-06 | Retrieve, orient, trace, traverse, and review without silently adopting context or changing truth. |
| **CIP-02** | **Attention and Context Control** | OI-07–OI-13 | Adopt, inspect, compare, deepen, quiet, suspend, or resume professional context with explicit continuity. |
| **CIP-03** | **Material and Evidence Qualification** | OI-14–OI-18 | Admit attributable material, verify source, qualify Evidence, challenge claims, and record observations. |
| **CIP-04** | **Reasoning and Synthesis** | OI-19–OI-26 | Propose Relationships, develop/test reasoning, resolve contradictions, synthesize, and explain with epistemic boundaries. |
| **CIP-05** | **Judgment and Decision Disposition** | OI-27–OI-33 | Acknowledge, accept, reject, defer, revise Current Situation, record, or reconsider Decision under explicit authority. |
| **CIP-06** | **Authority and Coordination** | OI-34–OI-39 | Delegate, accept delegation, transfer ownership, commit, coordinate dependencies, or request reclassification. |
| **CIP-07** | **Operational Transition Stewardship** | OI-40–OI-44 | Authorize, adapt, report deviation, pause, or stop an Operational Transition without manufacturing execution truth. |
| **CIP-08** | **Monitoring, Outcome, and Closure** | OI-45–OI-50 | Establish observation, review monitoring, assess Outcome, judge stabilization, close, or reopen Matter. |
| **CIP-09** | **Navigation and Return** | OI-51–OI-52 | Adopt another valid professional context or return through preserved origin and validity checks. |
| **CIP-10** | **Interruption Governance** | OI-53–OI-54 | Interrupt under one governed class and dispose the interrupting concern without aggregation escalation. |
| **CIP-11** | **Context Recovery and Abandonment** | OI-55–OI-56 | Reconstruct, offer, adopt, or deliberately abandon preserved professional intent without asserting resolution. |
| **CIP-12** | **Memory, Learning, and Practice** | OI-57–OI-61 | Inspect history, reflect, conduct isolated Practice, and govern learning admission without production leakage. |

Each OI ID belongs to exactly one primary pattern category. A pattern definition
may compose OI steps across categories only under the rules in §10.

# 7. Initiation and Preconditions

## 7.1 Initiation

Initiation is valid only when:

1. one active Pattern Definition is selected deterministically;
2. one exact primary OI intent is expressed;
3. initiator, subject, context, and origin are attributable;
4. CCT-07 Action Participant maps to the same OI ID;
5. required CCT-08 Feedback Participant is available or has approved fallback;
6. the current Composition Plan admits the participants;
7. no canonical consequence is claimed.

Initiation creates a unique Attempt ID and an occurrence in Validation.

## 7.2 Mandatory validation

Before progression, validate:

- identity and authentication;
- subject identity and source revision;
- authority source, scope, validity, and separation;
- Context Envelope validity;
- freshness and changed-since-presentation;
- concurrency and existing commitment evidence;
- OI-specific preconditions;
- RN, STC, PSD, Component, and Composition Plan revisions;
- idempotency identity;
- required feedback and recovery path.

Validation cannot be inferred from component availability or presentation state.

## 7.3 Validation outcomes

```text
Ready
```

when all required guards pass;

```text
Invalid
```

when a guard fails and no correction path exists within the same attempt;

```text
Blocked
```

when an attributable unmet precondition can be resolved before revalidation;

```text
Indeterminate
```

when commitment or runtime outcome cannot yet be proven.

Only Ready may progress toward completion or commitment.

# 8. Progression and Completion

## 8.1 Progression

Every progression step:

1. references exactly one OI contract;
2. declares its participant roles;
3. reads the current occurrence and source revisions;
4. validates its preconditions;
5. distinguishes presentation feedback from professional result;
6. produces one attributable step result;
7. identifies the next eligible step or terminal outcome;
8. preserves cancellation and recovery rules.

Step order derives from the Pattern Definition, never from platform event order.

## 8.2 Non-consequential completion

An interaction may complete without canonical consequence when its OI contract
is inspectional, presentational, explanatory, or otherwise non-persistent.
Completion records no canonical event unless OIL explicitly requires
attributable history.

## 8.3 Canonical commitment

Consequential progression requires:

```text
Ready validated attempt
        ↓
Owning-model command boundary
        ↓
Atomic canonical commitment
        ↓
Canonical Event evidence
        ↓
Committed feedback
```

The pattern cannot claim commitment from runtime receipt, optimistic
presentation, request dispatch, or local completion.

## 8.4 Completion outcomes

| Outcome | Meaning | Canonical consequence |
|---|---|---|
| **Completed without consequence** | Professional interaction completed without persistent change. | None unless OIL requires attributable history. |
| **Committed** | Owning model accepted the authorized consequence and event evidence exists. | Append-only canonical event. |
| **Rejected** | Owning model or validation declined progression with reason. | Only rejection history required by the owning contract. |
| **Cancelled** | Uncommitted attempt ended deliberately. | None. |
| **Failed** | Attempt did not achieve a valid terminal result. | Failure history only when consequentially required. |
| **Indeterminate** | Receipt or commitment cannot be proven. | No duplicate retry; reconciliation required. |
| **Interrupted** | Non-terminal occurrence paused with preservation contract. | No consequence from interruption alone unless governed OI says otherwise. |

# 9. Cancellation, Retry, Interruption, and Recovery

## 9.1 Cancellation

Cancellation:

- applies only before canonical commitment;
- ends the uncommitted attempt;
- creates no Canonical Event;
- preserves no false success or completion;
- differs from proposal withdrawal, context abandonment, and post-commit
  correction/reversal;
- leaves upstream canonical state unchanged.

After commitment, cancellation is impossible.

## 9.2 Retry

Retry:

- creates a new Attempt ID linked to the prior attempt;
- repeats identity, authority, freshness, concurrency, and OI-specific
  validation;
- preserves prior attempt feedback and indeterminacy;
- uses idempotency to prevent duplicate canonical consequence;
- never replays an already proven commitment.

## 9.3 Interruption

Interruption preserves:

- Pattern and occurrence identity;
- Attempt ID and completed steps;
- current subject and Context Envelope;
- source revisions and validation age;
- known runtime receipt;
- canonical-event evidence or its absence;
- next eligible step;
- origin, return, and recovery obligations.

An interruption class comes only from Navigation Governance and remains
mutually exclusive. Pattern composition cannot aggregate concerns into a higher
class.

## 9.4 Recovery

Recovery resolves:

1. current identity and authority;
2. source freshness and changes since interruption;
3. whether commitment occurred;
4. whether the same attempt remains valid;
5. whether revalidation is required;
6. whether an indeterminate act needs reconciliation;
7. whether a new retry attempt is safe;
8. the valid return or abandonment path.

Recovery never creates a canonical event merely to reconstruct interaction
state.

## 9.5 Post-commit correction and reversal

Correction or reversal:

- uses a new authorized OI interaction;
- creates a new append-only canonical event where consequential;
- references the original event and reason;
- never deletes or mutates the original commitment;
- preserves deterministic replay.

Runtime rollback is not post-commit correction.

# 10. Pattern Composition

## 10.1 Permitted composition relationships

| Relationship | Meaning | Constraint |
|---|---|---|
| **precedes** | One pattern occurrence must reach a declared terminal condition before another becomes eligible. | Terminal evidence and dependency basis are explicit. |
| **enables** | A validated outcome satisfies a precondition of another pattern. | Does not initiate the enabled pattern automatically. |
| **supports** | One non-authoring pattern supplies inspection, evidence, explanation, or context to another. | Creates no commitment or authority transfer. |
| **branches to** | One explicit result selects among declared next pattern definitions. | Branch condition is canonical or OI-owned, never platform-owned. |
| **runs independently with** | Occurrences may progress concurrently without shared commitment. | Identities, authority, state, and failure remain independent. |
| **interrupts** | A governed CIP-10 occurrence suspends another occurrence. | Interruption class and preservation contract are explicit. |
| **recovers** | CIP-11 reconstructs or reconciles another interrupted/indeterminate occurrence. | Cannot infer commitment or overwrite history. |
| **corrects or reverses** | A later authorized pattern addresses a committed result. | New event; original history remains immutable. |

## 10.2 Composition constraints

1. The composition graph is acyclic except explicit new-attempt retry links and
   later correction/reversal references.
2. Every occurrence retains Pattern ID, Attempt ID, participants, and authority.
3. Shared context creates no shared transaction.
4. Concurrent occurrences never share an idempotency identity.
5. One occurrence cannot cancel another after commitment.
6. Failure in one occurrence affects another only through a declared dependency.
7. Navigation between pattern contexts uses explicit CIP-09.
8. Interruption uses CIP-10 and recovery uses CIP-11.
9. No component, Structural Region, or Layout Intent determines pattern order.
10. Repetition creates a new occurrence or attempt, never an implicit loop.

## 10.3 Component and plan bindings

| Interaction responsibility | Canonical presentation participant |
|---|---|
| Professional subject and context | CCT-02/CCT-04/CCT-05 in SR-03 or SR-04 |
| Navigation and return | CCT-06 in SR-02 |
| Action and preconditions | CCT-07 in SR-05 |
| Feedback, failure, and recovery | CCT-08 in SR-06 |
| Temporary inspection or choice | CCT-09 in SR-07 |

Bindings expose pattern obligations but do not execute or own them.

# 11. Deterministic Pattern Resolution

## 11.1 Input contract

Resolution accepts:

- one active OIL registry revision;
- one active Pattern registry revision;
- exact actor, authority, subject, and context references;
- current Canonical Component instances and Composition Plan;
- current Rendering Tree, token, and Presentation State revisions;
- Operational Memory evidence and idempotency references;
- Platform Interaction Runtime capability declaration;
- prior attempt or occurrence where retry/recovery applies.

## 11.2 Resolution pipeline

```text
Identify Primary OI Intent
        ↓
Select One Eligible Active Pattern
        ↓
Bind Participants and Context
        ↓
Create Attempt Identity
        ↓
Validate Preconditions and Authority
        ↓
Resolve Permitted Progression
        ↓
Bind Feedback, Cancellation, and Recovery
        ↓
Publish Valid Pattern Occurrence Contract
```

Equivalent input and registry revisions produce equivalent pattern selection,
participant bindings, validation result, eligible progression, consequence
boundary, feedback, and recovery obligations.

## 11.3 Outcomes

```text
Valid Pattern Occurrence Contract
```

```text
Explicitly Blocked or Indeterminate Contract
```

or:

```text
Invalid — No Runtime Handoff
```

Ambiguous pattern selection is invalid. Registry order, platform preference,
component placement, and event order cannot select a pattern.

# 12. Platform Interaction Runtime Boundary

## 12.1 Boundary contract

```text
Canonical Interaction Patterns
  own reusable professional orchestration contracts
        ↓
Validated Pattern Occurrence and next eligible OI step
        ↓
Platform Interaction Runtime
  owns platform-specific interaction mechanics
```

The validated occurrence contract is the only handoff. The runtime cannot
reinterpret OI meaning or bypass canonical validation.

## 12.2 Canonical side responsibilities

Canonical Interaction Patterns must:

- provide exact Pattern, OI, attempt, actor, subject, context, and authority
  references;
- validate participants, preconditions, progression, and consequence boundary;
- preserve cancellation, retry, interruption, recovery, correction, and
  reversal obligations;
- distinguish receipt, validation, commitment, completion, failure, and
  indeterminacy;
- expose idempotency and append-only requirements;
- reject ambiguous, stale, unauthorized, or incomplete contracts;
- remain neutral to input and runtime mechanics.

It must not:

- prescribe device events or handlers;
- execute domain commands;
- infer commitment from runtime completion;
- define runtime scheduling;
- use platform capability to change professional intent.

## 12.3 Platform runtime responsibilities

A Platform Interaction Runtime may implement mechanics for a valid occurrence.
It must:

- consume the exact current occurrence and eligible OI step;
- preserve professional intent, participants, authority, preconditions, and
  consequence;
- maintain attempt and idempotency identity;
- report attributable receipt, completion, failure, interruption, and
  indeterminacy;
- request revalidation when sources or authority change;
- preserve cancellation and recovery boundaries;
- prevent duplicate consequential dispatch after proven commitment;
- reject stale or unsupported contracts.

It must not:

- invent OI interactions or pattern steps;
- bypass validation or authority;
- treat local completion as canonical commitment;
- erase, overwrite, or roll back canonical history;
- mutate Component, Plan, RN, STC, or PSD semantics;
- define a competing interaction-pattern taxonomy.

## 12.4 Mechanics independence

Materially different runtime mechanics conform when they preserve equivalent
intent, participant roles, validation, authority, progression, consequence,
feedback, cancellation, retry, interruption, recovery, correction, and
idempotency.

This document defines no Platform Interaction Runtime implementation.

# 14. Conformance Criteria

A Canonical Interaction Pattern realization conforms only when:

1. every definition and occurrence satisfies its descriptor;
2. CIP-01–CIP-12 cover OI-01–OI-61 exactly once as primary categories;
3. participant roles are explicit and source-owned;
4. initiation and validation create no canonical consequence;
5. progression preserves OI order, guards, authority, and outcome boundaries;
6. cancellation, retry, interruption, recovery, correction, and reversal obey
   OIL and Operational Memory;
7. canonical commitment requires event evidence;
8. pattern composition is deterministic and transaction-honest;
9. component and plan bindings remain presentation-only;
10. Platform Interaction Runtime ownership does not overlap canonical ownership;
11. equivalent mechanics preserve equivalent professional interaction;
12. accessibility equivalence is demonstrable;
13. invalid and indeterminate results fail safely;
14. no implementation vocabulary enters the canonical contract;
15. all 46 invariants pass.
