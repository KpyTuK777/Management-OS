# M6.3 — Canonical Rendering Model

## Status

```text
Ready for Architecture Review
Milestone M6
```

## Authority

This document is the single source of truth for transforming semantically
assigned Canonical Design Objects into a platform-independent Rendering Tree. It
defines Rendering Nodes, transformation, composition, ordering, degradation,
replacement, and conformance.

The Rendering Model consumes the Canonical Design Object Model and Canonical
Design Semantics. It does not change either source. A Rendering Tree is a
replaceable presentation projection, not domain truth, information residency,
navigation state, interaction state, Operational Memory, or canonical history.

# 1. Purpose

Canonical Design Objects define which presentation-semantic objects may exist.
Canonical Design Semantics defines why each occurrence exists in its
professional context. The Canonical Rendering Model defines how those validated
occurrences become an adapter-consumable tree without choosing a UI technology.

```text
Canonical/source snapshot
        +
Context and adapter capability
        +
Design Object graph (DO-01–DO-11)
        +
Semantic assignments (DSR-01–DSR-14)
        ↓
Canonical Rendering Transformation
        ↓
Rendering Tree snapshot
        ↓
Platform adapter expression
```

The model prevents adapters from inventing structure, omitting professional
meaning, treating component trees as architecture, or changing authority and
consequence through rendering choices.

# 2. Rendering Principles

1. **Projection, Never Truth.** A Rendering Tree represents source-owned
   meaning and is always replaceable.
2. **Semantic Input Required.** No semantic Rendering Node exists without a
   valid Design Object and primary DSR role.
3. **Deterministic Transformation.** Equivalent validated input produces an
   equivalent Rendering Tree.
4. **Meaning-Preserving Structure.** Parentage, order, grouping, and omission
   preserve declared semantic composition and create no new professional
   meaning.
5. **One Occurrence, One Node Identity.** Each rendered Design Object occurrence
   has one stable Rendering Node identity within a tree generation.
6. **Canonical Identity Preserved.** Multiple nodes may represent one subject
   only while retaining the same source identity and declared representation
   roles.
7. **Composition Before Expression.** Tree structure is resolved before any
   platform adapter chooses presentation mechanics.
8. **Capability-Honest Adaptation.** An adapter may serialize, summarize, defer,
   or explicitly mark unavailable expression; it may not silently discard
   required meaning.
9. **Accessible Equivalence.** Semantic order, identity, state, action,
   consequence, feedback, origin, and return survive changes of sensory channel.
10. **No Implicit Authority.** Root position, depth, ancestry, ordering,
    repetition, persistence, or adapter exposure grants no authority.
11. **Explicit Degradation.** Missing source data or adapter capability produces
    a declared fallback or a conformance failure, never fabricated meaning.
12. **Atomic Replacement.** A new valid tree replaces an obsolete tree as one
    projection; partial replacement cannot become current.
13. **Rendering Independence.** The model defines no markup, styling,
    component, token, layout, or framework contract.

# 3. Rendering Tree

## 3.1 Definition

A Rendering Tree is an immutable, generation-scoped, ordered hierarchy of
Rendering Nodes derived from one validated rendering input. It provides a
platform adapter with:

- one active presentation context;
- semantic containment and composition;
- stable node identity for the generation;
- canonical/source references rather than copied truth;
- explicit semantic order;
- interaction and authority references;
- adapter-equivalence obligations;
- declared fallback and degradation behavior.

The tree is not a page tree, scene graph, component tree, document tree,
accessibility tree, route graph, information architecture, or domain hierarchy.
An adapter may derive its own implementation structures only if their combined
expression conforms to this Rendering Tree.

## 3.2 Tree shape

```text
RN-01 Surface Root
  ├─ RN-02 Responsibility Node
  │    └─ RN-03 Composition Node
  │         ├─ RN-04 Place Node
  │         │    └─ eligible semantic node
  │         └─ other eligible child nodes
  ├─ RN-07 Navigation Node
  └─ RN-11 Transient Node
       └─ temporary compatible subtree
```

The example shows permissible structure, not required visual hierarchy or
layout.

## 3.3 Tree identity

Every Rendering Tree declares:

| Field | Requirement |
|---|---|
| **Tree generation ID** | Unique identity of this derived projection generation. |
| **Input revision** | Exact Design Object graph, semantic assignment, context, source snapshot, and adapter-capability revision. |
| **Root node ID** | Exactly one RN-01 node for the active presentation boundary. |
| **Semantic order contract** | Deterministic traversal order and its canonical or composition basis. |
| **Completeness result** | Complete, explicitly degraded, or invalid. |
| **Adapter obligations** | Meaning that every conforming adapter must preserve. |
| **Replacement relation** | Previous generation replaced by this tree, when applicable. |

## 3.4 Ownership

The Canonical Rendering Model owns only:

- the Rendering Tree contract;
- RN-01–RN-11 node kinds;
- Design Object-to-Rendering Node correspondence;
- canonical transformation and validation rules;
- semantic parentage, ordering, cross-reference, replacement, and degradation
  contracts;
- the boundary that every Platform Adapter must satisfy.

Ownership remains outside the Rendering Model for:

| Concern | Owner |
|---|---|
| Professional truth, identity, authority, and Matter lifecycle | Canonical Management Model and its owning source models |
| Design Object types and relationships | Canonical Design Object Model |
| Primary semantic roles and independent qualifiers | Canonical Design Semantics and Visual Semantics |
| Information residency and representation role | Canonical Information Architecture |
| Navigation context and professional attention | Operational Navigation and Navigation Governance |
| Interaction intent, validation, commitment, and recovery | Operational Interaction Language and Operational Memory |
| Expression mechanics and technical lifecycle | Platform Adapter |

The Rendering Tree owns no represented subject. It holds attributable references
and projection obligations only.

## 3.5 Projection lifecycle

Rendering Tree lifecycle is a presentation-projection lifecycle, not a Matter,
Artifact, Relationship, interaction, or domain lifecycle.

```text
Requested
    ↓
Building
    ↓
Validated
    ↓
Current
    ↓
Obsolete

Building or validation failure
    ↓
Invalid — Never Current
```

| Condition | Meaning | Permitted consequence |
|---|---|---|
| **Requested** | A validated input revision requires a tree generation. | Begin a new independent build. |
| **Building** | Nodes and relations are being derived but are not consumable as current. | Continue, abandon, or restart without changing the current tree. |
| **Validated** | The complete generation satisfies all tree contracts. | Become current through atomic replacement. |
| **Current** | The generation is the active projection for its declared input and adapter boundary. | Be consumed without acquiring canonical authority. |
| **Obsolete** | A newer valid generation has replaced it or its input is no longer current. | Retain only non-canonical diagnostic provenance where permitted. |
| **Invalid** | Transformation or validation failed. | Report failure; never replace the current valid generation. |

No lifecycle condition creates a Memory Event, changes Current Situation,
executes an interaction, or changes represented professional state.

# 4. Canonical Rendering Nodes

## 4.1 Node admission rule

A Rendering Node is admitted only when it:

- maps to one Design Object occurrence;
- preserves that occurrence's valid primary semantic role;
- has a stable responsibility not reducible to adapter implementation;
- participates in an allowed Rendering Tree relationship;
- can be expressed equivalently by materially different adapters.

The canonical inventory contains eleven node kinds.

## 4.2 Node inventory and correspondence

| Rendering Node | Required Design Object | Required role | Rendering responsibility |
|---|---|---|---|
| **RN-01 Surface Root** | DO-01 Presentation Surface | DSR-01 Surface Context Host | Root one adapter-addressable presentation context and its continuity obligations. |
| **RN-02 Responsibility Node** | DO-02 Semantic Region | DSR-02 Information Responsibility | Bound a subtree to one declared IA responsibility without creating residency. |
| **RN-03 Composition Node** | DO-03 Composition | DSR-03 Semantic Composition | Preserve one declared semantic whole and the identities of its members. |
| **RN-04 Place Node** | DO-04 Semantic Slot | DSR-04 Declared Semantic Place | Preserve eligibility, obligation, cardinality, occupancy, and fallback for one semantic place. |
| **RN-05 Subject Node** | DO-05 Subject Representation | DSR-05, DSR-06, DSR-07, or DSR-08 | Project one identified subject in exactly one IA representation role. |
| **RN-06 Set Node** | DO-06 Set Representation | DSR-09 Set Projection | Project an attributable ordered set and its organizing and completeness basis. |
| **RN-07 Navigation Node** | DO-07 Navigation Representation | DSR-10 Navigation Context | Project orientation, destination, origin, interruption, suspension, or return context. |
| **RN-08 Affordance Node** | DO-08 Interaction Affordance | DSR-11 Professional Action | Expose one OI interaction contract without executing it or granting authority. |
| **RN-09 State Node** | DO-09 State Indicator | DSR-12 Semantic State Communication | Expose one registered semantic dimension and its source-owned value. |
| **RN-10 Feedback Node** | DO-10 Feedback Presentation | DSR-13 Interaction Feedback | Project one attributable interaction condition and next valid path. |
| **RN-11 Transient Node** | DO-11 Transient Presentation Layer | DSR-14 Transient Support | Attach a temporary subtree while preserving origin, return, persistence, and dismissal semantics. |

No adapter may invent a twelfth semantic node kind. Adapter-only infrastructure
with no professional meaning may exist outside the canonical tree but cannot
alter its semantics or satisfy a required node.

# 5. Rendering Node Contract

Every Rendering Node records:

| Field | Requirement |
|---|---|
| **Node ID** | Stable occurrence identity within the tree generation. |
| **Node kind** | Exactly one RN-01–RN-11 kind. |
| **Design Object reference** | DO identity, type, and occurrence identity. |
| **Primary semantic role** | One permitted DSR identity. |
| **Canonical basis** | Source identity, projection identity, provenance, and revision/currentness as applicable. |
| **Context basis** | Active professional context and Context Envelope reference where applicable. |
| **IA mapping** | Information responsibility and representation role where applicable. |
| **OI mapping** | Interaction ID, authority requirement, consequence, cancellation, retry, and recovery where applicable. |
| **Qualifiers** | Independent Visual Semantics dimensions with sources and scope. |
| **Parent relation** | One semantic parent except for RN-01. |
| **Child order** | Deterministic semantic order with declared basis. |
| **Cross-references** | Non-parent relationships to origin, return, subject, interaction, or source nodes. |
| **Persistence class** | Generation, context, transient, or source-governed persistence obligation. |
| **Adapter equivalence** | Meaning and operation that must survive adapter expression. |
| **Fallback contract** | Required behavior when source or expression capability is unavailable. |
| **Prohibited implications** | Meaning the node and its position must not convey. |

Node IDs are projection identities. They are not domain IDs, event IDs,
component keys, element IDs, or stable canonical history.

# 6. Canonical Rendering Transformation

## 6.1 Input contract

Transformation accepts one immutable input package:

1. validated Design Object graph;
2. valid DSR assignment for every semantic occurrence;
3. canonical/source snapshot and provenance;
4. active professional context and applicable Context Envelope;
5. IA and OI mappings;
6. independent semantic qualifiers;
7. adapter capability declaration;
8. previous tree generation reference, when replacing a tree.

Missing required input makes transformation invalid. Rendering cannot repair
canonical source data or infer authority, truth, currentness, priority, Focus,
interaction success, or information residency.

## 6.2 Transformation stages

```text
Validate Input
      ↓
Normalize Occurrences
      ↓
Materialize Rendering Nodes
      ↓
Resolve Composition and Places
      ↓
Resolve Semantic Order and Cross-references
      ↓
Evaluate Capability and Fallback
      ↓
Validate Tree
      ↓
Publish Complete Generation
```

### Validate Input

Confirm DO type, DSR compatibility, canonical basis, context, mappings,
qualifiers, composition rules, and source revisions.

### Normalize Occurrences

Assign a distinct occurrence identity to each valid representation while
preserving shared canonical subject identity across occurrences.

### Materialize Rendering Nodes

Create exactly one corresponding RN kind for each included Design Object
occurrence. No role or meaning is added during materialization.

### Resolve Composition and Places

Apply `contains`, `composes`, `occupies`, semantic dependency, and transient
attachment contracts from the Design Object graph. Resolve place eligibility,
cardinality, required occupancy, and fallback.

### Resolve Semantic Order and Cross-references

Establish deterministic traversal from canonical order, declared set order,
composition dependency, professional sequence, or explicit neutral fallback.
Cross-references never become parentage implicitly.

### Evaluate Capability and Fallback

Determine whether the target adapter can preserve every required semantic
obligation. Apply only declared equivalent fallbacks; otherwise fail.

### Validate Tree

Check root uniqueness, completeness, acyclicity, node mapping, parentage,
ordering, identity, composition, authority, and adapter equivalence.

### Publish Complete Generation

Make the complete valid tree available as one replaceable projection. Invalid
or partially built generations remain non-current.

## 6.3 Output contract

Transformation returns exactly one:

```text
Complete Rendering Tree
```

```text
Explicitly Degraded Rendering Tree
```

or:

```text
Invalid — No Replacement
```

An explicitly degraded tree identifies every unavailable obligation and the
approved fallback. It cannot report semantic completeness. Invalid
transformation leaves the prior valid tree current where one exists.

# 7. Composition and Ordering

## 7.1 Parentage

1. RN-01 is the only node without a parent.
2. Every other node has exactly one semantic parent.
3. RN-02 scopes compatible subtrees to one IA responsibility.
4. RN-03 owns presentation composition only, never its children's canonical
   subjects or truth.
5. RN-04 contains only eligible node kinds and respects declared cardinality.
6. RN-06 may contain member nodes and set-level state or action nodes under an
   explicit organizing basis.
7. RN-11 attaches beneath the active root and cannot become an ancestor of
   permanent context.
8. Parentage creates no domain containment, Relationship, ownership, authority,
   Focus, priority, or lifecycle.

## 7.2 Semantic order

Child order must have exactly one declared basis:

- canonical/source order;
- IA responsibility order;
- set query or sequence order;
- composition dependency order;
- OI professional sequence;
- navigation continuity order;
- explicit neutral deterministic order.

Visual position and traversal mechanics may differ by adapter, but equivalent
semantic order and dependencies must remain recoverable. Order cannot imply
priority, authority, causality, chronology, or certainty unless that implication
is supplied by its canonical basis.

## 7.3 Cross-references

Origin, return, subject identity, navigation context, interaction target,
feedback operation, and source provenance may use typed cross-references.
Cross-references:

- do not create a second parent;
- do not create a canonical Relationship;
- must resolve within the tree or to an attributable external canonical source;
- must state behavior when their target is unavailable.

# 8. Replacement, Continuity, and Degradation

## 8.1 Replacement

A Rendering Tree is rebuilt when its validated input changes materially.
Replacement is atomic:

```text
Current valid generation
        ↓
Build and validate next generation
        ↓
Atomic replacement
        ↓
Previous generation becomes obsolete
```

Rebuilding or replacing a tree:

- creates no canonical event;
- changes no Operational Memory;
- does not mutate Current Situation;
- does not execute an interaction;
- does not advance Matter lifecycle;
- preserves required continuity references;
- may be repeated deterministically.

## 8.2 Continuity

Continuity is preserved through canonical/source identity, context identity,
origin and return, active interaction identity, and replacement relation.
Adapters may preserve local expression state only when it does not impersonate
canonical or operational state.

## 8.3 Degradation

Permitted degradation may:

- serialize simultaneous meaning;
- substitute an equivalent sensory channel;
- summarize a Secondary representation within its source-defined purpose;
- defer an unavailable optional interaction explicitly;
- state that a source value, relationship, or capability is unavailable;
- preserve a reference when full inspection cannot be expressed.

Degradation must not:

- omit a required Primary representation silently;
- convert Reference into Primary or Inspection;
- infer missing state or authority;
- report an interaction as committed;
- replace professional language with unexplained decoration;
- collapse independent semantic dimensions;
- fabricate a fallback subject, relationship, or navigation context.

# 9. Rendering Invariants

1. Every current Rendering Tree is derived from one immutable input revision.
2. Every tree has exactly one RN-01 root.
3. Every non-root node has exactly one semantic parent.
4. The parent-child graph is acyclic.
5. Every included Design Object occurrence maps to exactly one RN kind.
6. Every RN kind maps to exactly one permitted Design Object type.
7. Every node preserves one valid primary DSR role.
8. No node exists as a semantic catch-all.
9. Node materialization adds no professional meaning.
10. Node omission removes no required professional meaning.
11. Multiple nodes for one subject preserve one canonical identity.
12. Primary, Secondary, Reference, and Inspection remain distinct.
13. Rendering identity never replaces canonical identity.
14. Tree parentage never creates domain containment or Relationship.
15. Tree depth never creates authority, priority, certainty, or consequence.
16. Tree order has one explicit deterministic basis.
17. Repetition and frequency create no importance or truth.
18. RN-08 always references one OI interaction and never executes it.
19. RN-09 communicates one primary semantic dimension.
20. RN-10 feedback never proves canonical commitment without event evidence.
21. RN-11 preserves origin, return, and transient boundaries.
22. Unoccupied required RN-04 places use declared fallback or invalidate the
    tree.
23. Cross-references never create implicit parentage.
24. Missing capability is explicit.
25. Degraded trees identify every degraded obligation.
26. Invalid or partial trees never replace a current valid tree.
27. Tree replacement is atomic from the adapter consumer's perspective.
28. Rebuilding a tree creates no canonical history.
29. Equivalent input produces equivalent node kinds, identities, relationships,
    semantic order, and obligations.
30. Adapter expression cannot add, remove, weaken, or reassign semantics.
31. Accessible expression preserves equivalent identity, role, state, order,
    action, consequence, feedback, origin, and return.
32. No Rendering Node owns domain truth, IA residency, Navigation, Context
    Envelope, authority, lifecycle, Operational Memory, or Current Situation.
33. Projection lifecycle never becomes professional or domain lifecycle.
34. Only a complete validated generation can become current.
35. A Platform Adapter consumes the tree contract without re-reading sources to
    reinterpret it.
36. Adapter capability changes expression eligibility, never canonical meaning.

# 10. Platform Adapter Boundary

## 10.1 Boundary

```text
Canonical Rendering Model
  owns meaning-preserving projection
        ↓
Validated Rendering Tree
  is the complete boundary contract
        ↓
Platform Adapter
  owns technology-specific expression
```

The validated Rendering Tree is the only architectural handoff. The Rendering
Model cannot depend on adapter internals, and a Platform Adapter cannot reach
behind the tree to reinterpret canonical sources.

## 10.2 Canonical Rendering Model responsibilities

The Canonical Rendering Model must:

- emit a complete, valid, generation-identified tree;
- preserve Design Object type, semantic role, canonical basis, qualifiers, IA
  and OI mappings, identity, order, relationships, and prohibitions;
- expose adapter-equivalence and fallback obligations;
- state capability requirements without selecting expression mechanics;
- distinguish complete, degraded, and invalid outcomes;
- replace current projection atomically;
- remain neutral to platform, sensory channel, input method, and technology.

It must not:

- choose technical primitives;
- prescribe expression mechanics;
- inspect or depend upon adapter-internal structures;
- create platform-specific node kinds;
- weaken an obligation because one adapter cannot express it.

## 10.3 Platform Adapter responsibilities

A Platform Adapter must:

- consume only a validated complete or explicitly degraded tree;
- express every required node responsibility and relationship;
- preserve semantic order, identity, role, qualifiers, action consequence,
  feedback, origin, return, and fallback;
- declare capability before transformation validation;
- make unavailable meaning or operation explicit;
- provide equivalent access to the tree's professional meaning;
- reject a tree it cannot express conformantly.

It must not:

- add, remove, merge, split, or reinterpret professional meaning;
- infer truth, authority, priority, Focus, currentness, or interaction success;
- substitute adapter structure for RN identity or canonical identity;
- treat technical containment as domain containment or Relationship;
- write to canonical sources as a consequence of rendering;
- define a competing Rendering Node taxonomy.

## 10.4 Neutrality rule

Multiple adapters may express one Rendering Tree differently. They conform only
when an observer can recover equivalent:

- professional context;
- subject identity and representation role;
- composition and semantic order;
- state and provenance;
- available professional action, authority requirement, and consequence;
- feedback, interruption, recovery, origin, and return;
- missing or degraded obligations.

The boundary defines no adapter class or adapter implementation.

# 11. Conformance Criteria

A Rendering Model realization conforms only when:

1. its inputs satisfy the DO and DSR contracts;
2. all eleven RN mappings are implemented without substitution;
3. transformation stages and outcomes are explicit;
4. node descriptors contain every applicable required field;
5. the tree has one root, single parentage, and no cycles;
6. composition, place eligibility, cardinality, ordering, and cross-references
   are deterministic;
7. canonical and rendering identities remain separate;
8. required meaning is complete or explicitly degraded;
9. invalid generations do not replace valid trees;
10. replacement is atomic and creates no canonical history;
11. interaction, navigation, state, authority, Memory, and Current Situation
    boundaries remain intact;
12. at least two materially different adapters can preserve an equivalent tree;
13. accessibility equivalence is demonstrable;
14. no implementation technology appears in the canonical transformation
    contract;
15. all 36 rendering invariants pass.

## Deterministic verdict

```text
Pass
```

when every applicable criterion and invariant is satisfied;

```text
Fail
```

when transformation or adapter expression adds, removes, duplicates, obscures,
or reassigns canonical meaning;

```text
Not Applicable
```

only for adapter infrastructure that carries no semantic node responsibility.

# 12. Completion Criteria

The Canonical Rendering Model architecture definition is complete when:

1. Rendering Tree identity, input, output, and replacement contracts are
   explicit;
2. every DO-01–DO-11 occurrence has exactly one RN correspondence;
3. transformation is deterministic, complete, and implementation-independent;
4. composition, parentage, ordering, cross-reference, and degradation rules are
   bounded;
5. all rendering invariants are testable;
6. conformance produces an unambiguous verdict;
7. adapters may vary expression without changing meaning;
8. the model creates no domain truth, IA residency, Navigation, interaction,
   authority, lifecycle, Memory, Current Situation, or Context Envelope;
9. Rendering Model and Platform Adapter responsibilities are mutually exclusive
   and joined by one validated tree contract;
10. downstream Rendering Contracts, Accessibility Model, and Design-to-Code
   Mapping can consume the tree without inventing another rendering taxonomy;
11. Architecture Review approves the document for dependency use.
