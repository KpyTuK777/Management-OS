# M6.5 — Presentation State Model

## Status

```text
Approved for M6 dependency use
Milestone M6
```

## Authority

This document is the single source of truth for platform-independent
Presentation State attached to Canonical Rendering Nodes. It defines the state
dimensions, state snapshot, lifecycle, permitted presentation state
transitions, consistency rules, Platform Runtime boundary, and conformance.

Presentation State describes how a Rendering Node is currently presented. It
does not change what the node is, why it exists, which canonical meaning it
represents, or which Semantic Tokens it resolves.

# 1. Purpose

The Canonical Rendering Model produces a stable semantic tree. Semantic Token
Architecture resolves which meanings every node must express. A runtime still
needs a canonical, adapter-neutral way to report current presentation
conditions such as whether a node is exposed, available, emphasized, expanded,
selected, presentation-focused, resolving, degraded, or ready for a meaningful
presentation transition.

```text
Validated Rendering Node
        +
Resolved Semantic Token Set
        +
Declared presentation capabilities and intent
        ↓
Presentation State Resolution
        ↓
Presentation State Snapshot
        ↓
Platform Runtime mechanics
```

Without this model, runtime mechanics could impersonate semantic state,
selection could imply acceptance, presentation focus could replace professional
Current Focus, loading could imply interaction commitment, and adapters could
invent incompatible state machines.

# 2. Presentation State Principles

1. **Condition, Not Meaning.** Presentation State describes current expression
   condition and never authors semantic meaning.
2. **Node-Bound.** Every state snapshot belongs to one Rendering Node occurrence
   in one Rendering Tree generation.
3. **Independent Dimensions.** Exposure, availability, emphasis, disclosure,
   selection, presentation focus, fulfillment, fidelity, and presentation
   transition readiness remain separate.
4. **Upstream Immutable.** Presentation state changes never modify Design
   Objects, Semantic Roles, Rendering Nodes, or Semantic Tokens.
5. **Source Honest.** Any state derived from canonical or semantic input
   preserves the owning source and revision.
6. **No Professional Implication.** Selected is not accepted, Focused is not
   professional Focus, Emphasized is not priority, and Resolved is not canonical
   commitment.
7. **Deterministic Applicability.** The same node contract and state inputs
   produce the same applicable dimensions and valid states.
8. **Explicit Driver.** Every presentation state transition has one declared,
   attributable driver.
9. **Guarded Change.** No presentation state transition occurs without valid
   source state, target state, preconditions, and consistency checks.
10. **No Implicit Coupling.** A change in one dimension does not change another
    unless an explicit consistency rule requires it.
11. **Reversible Where Semantically Neutral.** Local presentation-only choices
    remain reversible unless the owning upstream contract makes a condition
    unavailable.
12. **Adapter Neutral.** Platform Runtime mechanics may differ while state
    identity and meaning remain equivalent.
13. **Accessible Equivalence.** State and state change remain recoverable
    independently of one sensory channel.
14. **Projection Only.** State resolution and change create no canonical event,
    history, authority, lifecycle progression, or Current Situation change.
15. **Qualified Transition.** Every use of transition in this model means a
    presentation state transition, never a Matter lifecycle transition,
    Operational Transition, or navigation transition.

# 3. Presentation State Contract

## 3.1 Definition

Presentation State is an immutable snapshot vector of the applicable
presentation-state dimensions for one Rendering Node:

```text
Presentation State Snapshot
  ├─ Rendering Tree generation
  ├─ Rendering Node occurrence
  ├─ resolved Semantic Token Set revision
  ├─ applicable PSD-01–PSD-09 dimensions
  ├─ exactly one current value per applicable dimension
  ├─ source and driver evidence
  └─ consistency and conformance result
```

There is no single aggregate “status.” Compound condition is a vector of
independently recoverable dimension values.

## 3.2 Ownership

Presentation State Model owns only:

- PSD-01–PSD-09 presentation-state dimensions and values;
- dimension applicability rules;
- state snapshot and presentation state transition contracts;
- permitted and invalid presentation state transitions;
- cross-dimension consistency;
- the Platform Runtime boundary;
- presentation-state conformance.

Ownership remains outside this model for:

| Concern | Owner |
|---|---|
| Professional truth, state, identity, authority, and Matter lifecycle | Canonical Management Model and owning source models |
| Design Object identity and relationships | Canonical Design Object Model |
| Primary Semantic Role | Canonical Design Semantics |
| Rendering Node identity, tree, generation, and replacement | Canonical Rendering Model |
| Semantic Token identity, meaning, and resolution | Semantic Token Architecture |
| Visual semantic dimensions and professional signals | Canonical Visual Semantics |
| Navigation and professional Current Focus | Operational Navigation and Navigation Governance |
| Interaction validation, commitment, correction, and recovery | Operational Interaction Language and Operational Memory |
| State mechanics, scheduling, and expression | Platform Runtime |

## 3.3 State snapshot descriptor

Every Presentation State Snapshot declares:

| Field | Requirement |
|---|---|
| **Snapshot ID** | Generation-scoped presentation projection identity. |
| **Tree generation and Node ID** | Exact RN occurrence to which the snapshot belongs. |
| **DO and DSR references** | Upstream type and role, read-only. |
| **Token-set revision** | Exact resolved Semantic Token Set used. |
| **Applicable dimensions** | Deterministically derived subset of PSD-01–PSD-09. |
| **Current values** | Exactly one value per applicable dimension. |
| **State sources** | Token, Rendering Model condition, presentation intent, capability, or runtime observation. |
| **State scope** | Node, declared composition, or presentation-focus scope. |
| **Consistency result** | Valid, explicitly constrained, or invalid. |
| **Previous snapshot** | Immediately superseded state snapshot where applicable. |
| **Platform Runtime obligations** | Meaning and restrictions mechanics must preserve. |
| **Prohibited implications** | Canonical meanings no state value may convey. |

Snapshot identity is not canonical subject identity, history identity, event
identity, or implementation state identity.

# 4. Presentation State Lifecycle

Presentation State Snapshot lifecycle is a presentation-projection lifecycle:

```text
Required
    ↓
Derived
    ↓
Validated
    ↓
Current
    ↓ presentation state transition
Superseded

Derivation or consistency failure
    ↓
Invalid — Never Current

Rendering Node becomes obsolete
    ↓
Discarded
```

| Condition | Meaning | Permitted consequence |
|---|---|---|
| **Required** | A current Rendering Node requires an initial or replacement state snapshot. | Begin derivation from the exact input revision. |
| **Derived** | Applicable dimensions and candidate values are known. | Validate all guards and cross-dimension rules. |
| **Validated** | Candidate snapshot is complete and consistent. | Atomically become current for the node. |
| **Current** | Snapshot is the node's active presentation condition. | Serve as source of a permitted presentation state transition. |
| **Superseded** | A newer valid snapshot for the same node has replaced it. | Retain non-canonical diagnostic trace only where permitted. |
| **Invalid** | Required dimension, source, guard, or consistency rule failed. | Never become current; preserve the prior valid snapshot. |
| **Discarded** | Its Rendering Node or tree generation is obsolete. | No further presentation state transition is permitted. |

This lifecycle creates no Memory Event and cannot extend the lifecycle of an
obsolete Rendering Node.

# 5. Canonical State Taxonomy

## 5.1 Taxonomy rule

A presentation-state dimension is admitted only when it:

- describes current presentation condition rather than canonical meaning;
- varies independently from other dimensions;
- has bounded values and deterministic applicability;
- has explicit presentation state transition guards;
- survives different Platform Runtime mechanics;
- cannot be represented by an upstream Semantic Token alone.

## 5.2 PSD-01 Exposure

Answers whether the node's obligation is currently exposed through the active
presentation.

| Value | Meaning |
|---|---|
| **Presented** | The node's required presentation meaning is currently available to the adapter expression. |
| **Withheld** | The node remains in the tree but its direct expression is intentionally not exposed under an approved disclosure or fallback contract. |

Withheld is not absent, deleted, unauthorized, unimportant, or non-canonical.
Required meaning cannot be withheld when no equivalent route or fallback exists.

## 5.3 PSD-02 Presentation Availability

Answers whether the node's declared presentation responsibility can currently
be fulfilled by the active runtime context.

| Value | Meaning |
|---|---|
| **Indeterminate** | Availability evidence is not yet sufficient. |
| **Available** | Required presentation capability and preconditions are satisfied. |
| **Unavailable** | A declared capability or presentation precondition is not satisfied. |

Availability grants no professional authority and says nothing about canonical
system availability unless an explicit STC-02/D-17 token separately states it.

## 5.4 PSD-03 Presentation Emphasis

Answers the node's current relative expression strength under existing semantic
obligations.

| Value | Meaning |
|---|---|
| **Baseline** | No additional or reduced expression strength is required. |
| **Emphasized** | A source-owned semantic obligation requires stronger recoverable expression. |
| **De-emphasized** | Context permits reduced expression while meaning remains recoverable. |

Emphasis cannot create priority, urgency, authority, consequence, certainty, or
professional Current Focus.

## 5.5 PSD-04 Disclosure

Answers which declared semantic extent is currently exposed.

| Value | Meaning |
|---|---|
| **Fixed** | The node has no alternative disclosure extent in this generation. |
| **Condensed** | The approved reduced semantic extent is current. |
| **Expanded** | The approved extended semantic extent is current. |

Condensed is not incomplete, lower truth, or Secondary representation unless
the upstream IA role already says so. Expansion creates no new information
residency or meaning.

## 5.6 PSD-05 Presentation Selection

Answers whether the node is the current member of a declared local presentation
selection scope.

| Value | Meaning |
|---|---|
| **Not Selectable** | No presentation-selection contract applies. |
| **Unselected** | The node is eligible but not the current selection in its scope. |
| **Selected** | The node is the current local presentation selection in its scope. |

Selected does not mean accepted, approved, chosen as a Decision, professional
Focus, authorized, or committed.

## 5.7 PSD-06 Presentation Focus

Answers whether the node is the current local target for presentation input
routing in a declared scope.

| Value | Meaning |
|---|---|
| **Not Focusable** | No presentation-focus contract applies. |
| **Unfocused** | The node is eligible but is not the local routing target. |
| **Focused** | The node is the local routing target in its presentation-focus scope. |

Presentation Focus is not Operational Navigation Current Focus, professional
attention, selection, inspection, acceptance, or authority.

## 5.8 PSD-07 Presentation Fulfillment

Answers the current fulfillment condition of a presentation-only resolution
obligation.

| Value | Meaning |
|---|---|
| **Idle** | No unresolved presentation fulfillment request is active. |
| **Resolving** | Required presentation input or expression is being resolved. |
| **Resolved** | The presentation-only resolution completed for the declared request. |
| **Failed** | The presentation-only resolution did not complete and has an explicit failure path. |

Resolving is the canonical presentation meaning behind a loading concern. It
does not imply an OI attempt, canonical commitment, domain activity, or event
creation. Resolved does not mean professional success.

## 5.9 PSD-08 Presentation Fidelity

Answers how fully the node's token obligations can currently be expressed.

| Value | Meaning |
|---|---|
| **Complete** | Every required token obligation is independently recoverable. |
| **Degraded** | Approved fallback preserves truthful but explicitly reduced expression. |
| **Unavailable** | No conforming expression or approved fallback is currently available. |

Fidelity derives from Rendering Model and token resolution conditions. It never
changes the underlying meaning.

## 5.10 PSD-09 Presentation Transition Readiness

Answers whether a declared meaningful presentation transition can proceed.

| Value | Meaning |
|---|---|
| **Stable** | No presentation transition preparation is active. |
| **Preparing** | Preconditions for one identified presentation transition are being evaluated. |
| **Ready** | All declared presentation transition preconditions are satisfied. |
| **Blocked** | At least one required presentation transition precondition is unsatisfied. |

Readiness authorizes no interaction and predicts no result. It is unrelated to
Matter lifecycle transition readiness, Operational Transition readiness, or
navigation transition readiness.

# 7. Presentation State Transition Contract

## 7.1 Presentation state transition descriptor

Every requested presentation state transition declares:

| Field | Requirement |
|---|---|
| **Presentation transition ID** | Generation-scoped identity of the requested state change. |
| **Node and snapshot** | Exact RN occurrence and current snapshot revision. |
| **Dimension** | Exactly one PSD-01–PSD-09 dimension. |
| **Source value** | Current value in that dimension. |
| **Target value** | One permitted value in the same dimension. |
| **Driver** | Canonical derivation, presentation intent, adapter capability, runtime observation, or tree lifecycle. |
| **Evidence** | Attributable input revision supporting the driver. |
| **Preconditions** | Complete guards required before change. |
| **Cross-dimension constraints** | Consistency obligations affected by the requested state. |
| **Runtime obligation** | Meaning mechanics must preserve while applying the state. |
| **Failure result** | Explicit unchanged or constrained state when validation fails. |
| **Supersession result** | New complete snapshot replacing the previous snapshot atomically. |

One presentation state transition changes one dimension. Coordinated changes use
an atomic set of individually valid presentation state transitions; dimensions
do not merge.

## 7.2 Drivers

Permitted drivers are:

| Driver | May establish | Cannot establish |
|---|---|---|
| **Canonical derivation** | State required by a changed validated tree or token set. | New canonical truth or semantic meaning. |
| **Presentation intent** | Reversible local disclosure, selection, or presentation-focus request. | Acceptance, Decision, authority, professional Focus, or commitment. |
| **Adapter capability** | Availability or fidelity supported by declared capability. | Semantic priority or alternative meaning. |
| **Runtime observation** | Fulfillment result or presentation-mechanics availability. | Domain result, interaction success, or canonical event. |
| **Tree lifecycle** | Initial state, replacement, invalidation, or discard. | Mutation of the Rendering Node or its source. |

## 7.3 Permitted presentation state transitions

| Dimension | Permitted presentation state transitions | Required guard |
|---|---|---|
| **PSD-01 Exposure** | Presented ↔ Withheld | Approved disclosure/fallback preserves every required obligation and return path. |
| **PSD-02 Availability** | Indeterminate → Available; Indeterminate → Unavailable; Available ↔ Unavailable | Attributable capability or precondition evidence. |
| **PSD-03 Emphasis** | Baseline ↔ Emphasized; Baseline ↔ De-emphasized; Emphasized ↔ De-emphasized | Resolved token obligation changes or a valid context-specific expression contract exists. |
| **PSD-04 Disclosure** | Condensed ↔ Expanded | Both extents are declared for the node and preserve identity and truth. Fixed has no outgoing presentation state transition. |
| **PSD-05 Selection** | Unselected ↔ Selected | Node is selectable in the exact selection scope. Not Selectable has no outgoing presentation state transition. |
| **PSD-06 Presentation Focus** | Unfocused ↔ Focused | Node is focusable, Presented, and valid in the exact presentation-focus scope. Not Focusable has no outgoing presentation state transition. |
| **PSD-07 Fulfillment** | Idle → Resolving; Resolving → Resolved; Resolving → Failed; Failed → Resolving; Resolved → Resolving | Identified presentation-only request and attributable runtime observation. |
| **PSD-08 Fidelity** | Complete ↔ Degraded; Complete ↔ Unavailable; Degraded ↔ Unavailable | Changed token completeness, fallback, or declared adapter capability evidence. |
| **PSD-09 Presentation Transition Readiness** | Stable → Preparing; Preparing → Ready; Preparing → Blocked; Ready → Stable; Ready → Blocked; Blocked → Preparing; Blocked → Stable | One identified meaningful presentation transition and its current preconditions. |

## 7.4 Deterministic resolution

```text
Current valid snapshot
        +
One requested presentation state transition
        +
Exact driver evidence
        ↓
Validate node generation and dimension applicability
        ↓
Validate source and target pair
        ↓
Validate preconditions and cross-dimension consistency
        ↓
Produce one complete successor snapshot
        ↓
Atomic snapshot replacement
```

Equivalent current snapshot, requested change, driver evidence, and upstream
revisions produce the same permitted, blocked, or invalid result.

# 8. Invalid Presentation State Transitions

A requested presentation state transition is invalid when:

1. the Rendering Node or tree generation is obsolete;
2. the source snapshot is not current;
3. the dimension is not applicable to the node;
4. source value does not match the current snapshot;
5. target value is outside the dimension;
6. the source-target pair is not permitted;
7. driver or evidence is missing;
8. a required precondition fails;
9. it changes more than one dimension without an atomic coordinated contract;
10. it attempts to modify a DO, DSR, RN, or STC identity or meaning;
11. it infers professional state from presentation mechanics;
12. it would conceal required meaning without approved fallback;
13. it treats selection as acceptance or Decision;
14. it treats Presentation Focus as professional Current Focus;
15. it treats emphasis as priority, authority, urgency, or consequence;
16. it treats fulfillment as domain or interaction result;
17. it treats fidelity as truth quality;
18. it creates an unqualified lifecycle, Operational Transition, or navigation
    transition;
19. it depends on unspecified Platform Runtime behavior;
20. it would produce an incomplete or inconsistent successor snapshot.

Invalid requests leave the current valid snapshot unchanged and create no
canonical consequence.

# 9. Cross-Dimension Consistency

1. Focused requires PSD-01 Presented.
2. Expanded requires PSD-01 Presented.
3. Withholding a Focused node requires an atomic change to Unfocused or a valid
   presentation-focus transfer in the same scope.
4. Selected and Focused remain independent.
5. Emphasized and Selected remain independent.
6. Emphasized and Focused remain independent.
7. PSD-02 Unavailable does not imply PSD-01 Withheld; explicit unavailability
   may itself require presentation.
8. PSD-08 Degraded or Unavailable does not modify STC meaning.
9. PSD-07 Resolving requires attributable presentation feedback while the node
   is Presented, or an explicit equivalent feedback reference.
10. PSD-09 Ready does not change PSD-02 Availability, PSD-05 Selection, or
    PSD-06 Presentation Focus.
11. A single-select scope has at most one Selected node, but the scope rule must
    be declared upstream of runtime mechanics.
12. A presentation-focus scope has at most one Focused node.
13. Tree replacement re-derives applicability before preserving any reversible
    local state.
14. State preservation across tree generations requires stable canonical
    subject identity, equivalent RN/DSR responsibility, and explicit continuity
    permission.
15. No consistency rule creates canonical meaning that is absent upstream.

# 10. Platform Runtime Boundary

## 10.1 Boundary contract

```text
Presentation State Model
  owns state meaning, applicability, guards, and valid successor snapshots
        ↓
Current State Snapshot + Valid Presentation State Transition Contract
        ↓
Platform Runtime
  owns technology-specific state mechanics
```

The Platform Runtime receives a complete state contract. It cannot reinterpret
state meaning or treat mechanics as a canonical source.

## 10.2 Presentation State Model responsibilities

The canonical side must:

- derive applicable dimensions from validated RN and STC input;
- provide one complete current state vector;
- validate requested presentation state transitions deterministically;
- enforce permitted pairs, guards, and cross-dimension consistency;
- expose equivalent state meaning and runtime obligations;
- atomically publish a complete successor snapshot;
- reject invalid or stale requests;
- remain neutral to platform mechanics and timing.

It must not:

- prescribe how state is stored or applied;
- define input events or scheduling;
- infer canonical meaning from runtime mechanics;
- mutate upstream architecture or source state;
- require a specific implementation lifecycle.

## 10.3 Platform Runtime responsibilities

A Platform Runtime may implement mechanics for a valid state contract. It must:

- consume the exact current snapshot and validated presentation state
  transition;
- preserve PSD identity and meaning;
- apply only the permitted target condition;
- report attributable completion, failure, or capability evidence;
- keep coordinated dimension changes atomic from the presentation contract's
  perspective;
- preserve accessible state equivalence;
- reject stale or unsupported state contracts.

It must not:

- invent PSD dimensions or values;
- change DO, DSR, RN, or STC data;
- infer authority, professional Focus, acceptance, priority, or commitment;
- convert runtime activity into canonical history;
- expose a partially applied coordinated state as valid;
- define a competing Presentation State taxonomy.

## 10.4 Runtime observation rule

Runtime observation is evidence about presentation mechanics only. It may drive
PSD-02, PSD-07, PSD-08, or PSD-09 when the corresponding contract permits it.
It cannot update semantic tokens or any canonical/source-owned state.

This document defines no Platform Runtime implementation.

# 12. Conformance Criteria

A Presentation State realization conforms only when:

1. every snapshot satisfies the descriptor contract;
2. every RN-01–RN-11 kind receives deterministic dimension applicability;
3. every applicable dimension has one valid value;
4. all PSD-01–PSD-09 values preserve their explicit boundaries;
5. presentation state transitions use valid pairs, drivers, evidence, and
   guards;
6. invalid requests preserve the current valid snapshot;
7. cross-dimension consistency is complete and deterministic;
8. coordinated changes are atomic;
9. upstream DO, DSR, RN, and STC contracts remain immutable;
10. professional and presentation state remain distinct;
11. Presentation Focus and Operational Navigation Current Focus remain distinct;
12. Platform Runtime responsibilities do not overlap canonical ownership;
13. equivalent state meaning is accessible across materially different runtime
    mechanics;
14. no implementation vocabulary enters the state contract;
15. all 40 invariants pass.

## Deterministic verdict

```text
Pass
```

when every applicable criterion and invariant is satisfied;

```text
Fail
```

when a state, presentation state transition, consistency rule, or runtime
mechanic changes, invents, hides, or ambiguously represents canonical meaning;

```text
Not Applicable
```

only for runtime infrastructure that neither owns nor expresses a Presentation
State obligation.

# 13. Completion Criteria

Presentation State Model is complete when:

1. state purpose, ownership, descriptor, lifecycle, and responsibilities are
   explicit;
2. PSD-01–PSD-09 are exhaustive, independent, and bounded;
3. all RN-01–RN-11 applicability rules are deterministic;
4. permitted and invalid presentation state transitions are complete;
5. presentation state transition guards, drivers, evidence, and outcomes are
   explicit;
6. cross-dimension consistency prevents semantic conflation;
7. DO, DSR, RN, and STC inputs remain immutable;
8. Platform Runtime and canonical responsibilities are mutually exclusive;
9. no platform mechanic or implementation lifecycle enters the canonical model;
10. conformance produces an unambiguous verdict;
