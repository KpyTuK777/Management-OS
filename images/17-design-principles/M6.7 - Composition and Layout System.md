# M6.7 — Composition and Layout System

## Status

```text
Ready for Architecture Review
Milestone M6
```

## Authority

This document is the single source of truth for platform-independent
composition of Canonical Components and for Layout Intent. It defines
Composition Plans, component relationships, containment, semantic order,
Structural Regions, composition boundaries, replacement, Layout Intent, the
Platform Layout Engine boundary, and conformance.

Composition and Layout System governs architectural organization. It does not
define geometry, visual arrangement, or runtime layout mechanics.

# 1. Purpose

Canonical Components encapsulate reusable professional presentation
responsibilities. Larger presentation structures require an explicit contract
for how component instances coexist, contain one another, preserve boundaries,
follow semantic order, support comparison, remain persistent, attach transient
support, adapt to constrained expression, and replace one another.

```text
Validated Canonical Component Instances
        +
Rendering Tree, Token, and Presentation State contracts
        +
One active professional context
        ↓
Canonical Composition Resolution
        ↓
Validated Composition Plan + Layout Intent Set
        ↓
Platform Layout Engine
```

Without this layer, visual arrangement could invent information hierarchy,
platform mechanics could reorder professional meaning, containment could become
domain ownership, and adaptive presentation could silently remove required
context.

# 2. Composition Principles

1. **Organization, Not Geometry.** Composition defines structural
   responsibilities and relationships, never physical arrangement.
2. **Components Remain Intact.** Composition consumes valid Canonical Component
   instances without changing their identity or responsibility.
3. **Rendering Tree Remains Structural Authority.** Component organization
   cannot reparent, reorder, or duplicate Rendering Nodes.
4. **Information Architecture Remains Residency Authority.** Structural Regions
   do not create information spaces or ownership.
5. **Semantic Order Before Placement.** Professional traversal and dependency
   order exist independently from platform placement.
6. **One Active Context.** A Composition Plan operates inside one declared
   professional context and never creates another Context Envelope.
7. **Explicit Relationships.** Containment, order, grouping, comparison,
   support, context anchoring, transient attachment, and replacement are typed.
8. **No Meaning from Proximity.** Co-presence or grouping creates no domain
   Relationship, causality, authority, or priority.
9. **Intent Before Mechanics.** Layout Intent states what must remain
   structurally recoverable, not how to arrange it.
10. **Capability-Honest Adaptation.** Constrained expression preserves required
    meaning or declares degradation.
11. **Deterministic Composition.** Equivalent input and registry revisions
    produce an equivalent Composition Plan.
12. **Atomic Replacement.** A complete valid plan replaces an obsolete plan as
    one projection.
13. **Accessible Equivalence.** Structural regions, order, comparison,
    relationships, and continuity remain recoverable across modalities.
14. **No Implicit Authority.** Region role, order, persistence, containment, or
    engine placement grants no authority.
15. **Projection Only.** Composition creates no canonical event, domain truth,
    navigation state, lifecycle progression, or Current Situation.

# 3. Composition Model

## 3.1 Composition Plan

A Composition Plan is an immutable, generation-scoped architectural projection
that organizes valid Canonical Component instances within one presentation
context:

```text
Composition Plan
  ├─ one Plan identity and revision
  ├─ one context and Surface Component boundary
  ├─ Component instance membership
  ├─ typed CR-01–CR-08 relationships
  ├─ SR-01–SR-07 Structural Region assignments
  ├─ LI-01–LI-08 Layout Intent obligations
  ├─ deterministic semantic order
  ├─ adaptation and replacement contracts
  └─ conformance result
```

The Composition Plan is not a Rendering Tree, component tree, information
hierarchy, navigation graph, or platform layout structure.

## 3.2 Ownership

Composition and Layout System owns only:

- Composition Plan identity, descriptor, lifecycle, and validation;
- component membership in a plan;
- CR-01–CR-08 presentation-structural relationships;
- SR-01–SR-07 Structural Region roles;
- LI-01–LI-08 Layout Intent obligations;
- composition boundary, semantic order, adaptation, and replacement rules;
- the Platform Layout Engine boundary;
- composition conformance.

Ownership remains outside this model for:

| Concern | Owner |
|---|---|
| Professional truth, authority, and lifecycle | Canonical Management Model and owning source models |
| Information spaces, residency, and representation roles | Canonical Information Architecture |
| Design Objects and Semantic Roles | Canonical Design Object Model and Canonical Design Semantics |
| Rendering Tree, Nodes, parentage, and semantic order source | Canonical Rendering Model |
| Semantic Token identity and meaning | Semantic Token Architecture |
| Presentation State | Presentation State Model |
| Component identity, responsibility, members, reuse, and version | Canonical Component Model |
| Navigation and professional Current Focus | Operational Navigation and Navigation Governance |
| Geometry and platform-specific arrangement mechanics | Platform Layout Engine |

## 3.3 Composition Plan descriptor

Every Composition Plan declares:

| Field | Requirement |
|---|---|
| **Plan ID and revision** | Stable projection identity and exact plan revision. |
| **Context basis** | Active professional context, dominant object, and Context Envelope reference. |
| **Surface boundary** | Exactly one CCT-01 instance and its Rendering Tree generation. |
| **Component registry revision** | Exact definitions used by all member instances. |
| **Membership** | Exact component instances included in the plan. |
| **Relationships** | Typed CR identities, endpoints, source, and constraints. |
| **Structural Regions** | Exact SR assignments, accepted component categories, and obligations. |
| **Semantic order** | Deterministic traversal and dependency order with source. |
| **Layout Intent Set** | Applicable LI obligations and their source contracts. |
| **Adaptation contract** | Required preservation, permitted serialization, deferral, and degradation. |
| **Replacement contract** | Successor compatibility, continuity, and atomicity. |
| **Engine obligations** | Meaning and structure the Platform Layout Engine must preserve. |
| **Prohibited implications** | Meanings neither plan nor engine may introduce. |
| **Conformance result** | Complete, explicitly degraded, or invalid. |

# 4. Composition Lifecycle

## 4.1 Definition lifecycle

Reusable Composition Plan definitions follow governance lifecycle:

```text
Proposed
    ↓ Architecture Review
Registered
    ↓ Approved use
Active
    ↓ Compatible successor
Deprecated
    ↓ Migration complete
Retired
```

Meaning cannot change under one definition identity. Changed context
responsibility, Structural Region contract, or required Layout Intent creates a
new identity.

## 4.2 Plan-instance lifecycle

```text
Required
    ↓
Derived
    ↓
Validated
    ↓
Current
    ↓ replacement or context change
Obsolete

Derivation or validation failure
    ↓
Invalid — Never Current
```

A plan instance cannot outlive its Surface Component or Rendering Tree
generation. Composition lifecycle is presentation governance and creates no
Memory Event or professional lifecycle condition.

# 5. Admissible Component Relationships

## 5.1 Relationship taxonomy

| ID | Relationship | Meaning | Constraint |
|---|---|---|---|
| **CR-01** | **contains structurally** | One component provides the declared composition boundary for another. | Must preserve existing component nesting and Rendering Tree parentage. |
| **CR-02** | **orders before** | One component precedes another in recoverable semantic traversal or dependency order. | Requires one declared canonical, component, navigation, or neutral deterministic basis. |
| **CR-03** | **groups with** | Components form one presentation-structural group under a declared purpose. | Creates no canonical Collection or domain Relationship. |
| **CR-04** | **supports** | One component provides secondary presentation support to another identified responsibility. | Cannot imply lower truth, ownership, causality, or authority. |
| **CR-05** | **compares with** | Components participate in one explicit comparison contract. | Comparison basis and corresponding dimensions remain explicit. |
| **CR-06** | **anchors context for** | A context-bearing component preserves orientation for another component or group. | Creates no Context Envelope, professional Focus, or information residency. |
| **CR-07** | **attaches transiently to** | A transient-support component relates to a stable origin and return target. | Requires CCT-09, explicit origin, persistence, dismissal, and return. |
| **CR-08** | **replaces structurally** | One compatible component or group is the declared successor of another within a new plan revision. | Requires identity, responsibility, continuity, and atomic replacement contract. |

These are presentation-structural relationships. They are not canonical
Relationship entities and cannot be promoted by presentation alone.

## 5.2 Relationship constraints

1. Every relationship has one type, source, scope, and exact endpoints.
2. CR-01 containment is acyclic.
3. Every component has at most one direct CR-01 parent in a plan.
4. CR-02 forms an acyclic order within one declared order scope.
5. CR-03 grouping has one explicit purpose and boundary.
6. CR-04 support cannot change Primary/Secondary/Reference/Inspection role.
7. CR-05 comparison cannot manufacture equivalence or causality.
8. CR-06 context anchoring does not change Navigation or Current Focus.
9. CR-07 cannot become permanent containment silently.
10. CR-08 is effective only through a complete successor plan.
11. Relationship omission uses an approved fallback or invalidates the plan.
12. Platform placement cannot add a CR relationship.

# 6. Structural Regions

## 6.1 Definition

A Structural Region is a named presentation-composition responsibility inside a
Composition Plan. It classifies where component responsibility participates in
the plan, not where it is physically placed.

A Structural Region:

- is not DO-02 Semantic Region or RN-02 Responsibility Node;
- is not an IA information space;
- owns no information, navigation, context, truth, or geometry;
- accepts only component categories declared by its contract.

## 6.2 Region taxonomy

| ID | Structural Region | Responsibility | Admissible component basis | Must not imply |
|---|---|---|---|---|
| **SR-01** | **Context Frame** | Preserve active context, dominant object, continuity, and return boundary. | One CCT-01 and declared context-bearing CCT-02/CCT-06 instances. | New Context Envelope, Workspace ownership, or route. |
| **SR-02** | **Navigation Orientation** | Preserve canonical orientation, destination, origin, interruption, and return. | CCT-06 and supporting CCT-07/CCT-08. | Navigation creation, lifecycle progression, or professional Focus. |
| **SR-03** | **Primary Work Responsibility** | Carry the component responsibility corresponding to the current dominant professional object or task context. | Compatible CCT-02–CCT-05 derived from canonical context. | New priority, authority, or universal Primary representation. |
| **SR-04** | **Supporting Context** | Preserve necessary reference, comparison, explanation, or secondary context. | Compatible CCT-02–CCT-05. | Lower truth, dispensability, or hidden residency. |
| **SR-05** | **Professional Action** | Group available action responsibilities without creating intent or authority. | CCT-07 with supporting CCT-04/CCT-08. | Execution, commitment, acceptance, or permission. |
| **SR-06** | **Feedback and Recovery** | Preserve attributable feedback, failure, recovery, and next valid path. | CCT-08 and recovery-capable CCT-07. | Domain outcome, event evidence, or generic notification area. |
| **SR-07** | **Transient Support** | Preserve temporary support with explicit origin, return, and persistence. | CCT-09 with compatible nested component instances. | Permanent destination, second context, or independent Focus. |

## 6.3 Region rules

1. Every plan has exactly one SR-01.
2. SR-03 is required when the context has an active dominant professional
   responsibility.
3. SR-02, SR-04, SR-05, SR-06, and SR-07 exist only when their source
   responsibilities apply.
4. A component has one primary Structural Region assignment in one plan.
5. Cross-region references do not duplicate component instances.
6. Region order follows semantic order, not physical placement.
7. Region role changes require a new validated plan revision.

# 7. Composition Boundaries and Containment

## 7.1 Boundary rule

One Composition Plan is bounded by:

- one active professional context;
- one current Rendering Tree generation;
- one CCT-01 Surface Context Assembly;
- one component-registry revision;
- one Layout Intent registry revision;
- one Platform Layout Engine capability declaration.

Cross-context composition uses references and navigation continuity; it cannot
merge contexts or create a larger hidden envelope.

## 7.2 Containment rule

1. Containment uses CR-01 only.
2. Containment must agree with Canonical Component admissible nesting.
3. Containment cannot reparent Rendering Nodes.
4. Containment cannot cross the Surface boundary.
5. Containment depth creates no professional hierarchy or importance.
6. A referenced component is not contained.
7. Transient attachment uses CR-07, not permanent CR-01 containment.
8. Generic untyped containers are non-conforming.

## 7.3 Ordering rule

Semantic order derives from exactly one declared basis:

- Rendering Tree order;
- Canonical Component dependency;
- canonical/source sequence;
- Navigation continuity;
- professional interaction sequence;
- explicit neutral deterministic fallback.

Order must remain recoverable even when a Platform Layout Engine changes
physical arrangement or serializes concurrent content. Order cannot infer
priority, chronology, causality, certainty, or authority unless the source basis
already owns that meaning.

# 8. Layout Intent

## 8.1 Definition

Layout Intent is a platform-independent structural obligation attached to a
Composition Plan relationship, Structural Region, component group, or plan
boundary. It describes what organization must survive platform arrangement.

Layout Intent does not prescribe physical direction, size, distance, alignment,
position, or adaptation mechanics.

## 8.2 Layout Intent taxonomy

| ID | Layout Intent | Canonical obligation | Must not determine |
|---|---|---|---|
| **LI-01** | **Semantic Traversal** | Preserve declared reading, reasoning, dependency, and interaction order. | Physical direction or placement. |
| **LI-02** | **Concurrent Availability** | Preserve the ability to access components as one current composition without losing context. | Simultaneous physical exposure or screen partition. |
| **LI-03** | **Boundary Distinction** | Keep component, Structural Region, context, and transient boundaries independently recoverable. | Borders, surfaces, distance, or visual styling. |
| **LI-04** | **Comparison Correspondence** | Preserve compared subjects, dimensions, baseline, and correspondence. | Physical adjacency or matching geometry. |
| **LI-05** | **Context Persistence** | Preserve required context and orientation across component disclosure or replacement. | Fixed physical position or technical persistence. |
| **LI-06** | **Transient Attachment** | Preserve transient origin, relationship, return, persistence, and dismissal meaning. | Overlay mechanics or layer implementation. |
| **LI-07** | **Capacity Adaptation** | Preserve required responsibilities and declare permitted serialization, deferral, summarization, or degradation. | Device classes or responsive mechanics. |
| **LI-08** | **Replacement Continuity** | Preserve identity, responsibility, focus distinction, state eligibility, and return across atomic plan replacement. | Animation or physical movement. |

## 8.3 Intent application

Every Layout Intent occurrence declares:

| Field | Requirement |
|---|---|
| **Intent ID and type** | One LI-01–LI-08 identity. |
| **Target scope** | Plan, Structural Region, relationship, component group, or exact component instance. |
| **Source obligation** | Canonical, RN, STC, PSD, component, or navigation contract. |
| **Preservation requirement** | Meaning and structure that must remain recoverable. |
| **Permitted adaptation** | Bounded structural transformation without geometry. |
| **Forbidden adaptation** | Any change that would alter meaning, order, identity, relationship, or continuity. |
| **Fallback** | Explicit truthful degradation or failure. |
| **Engine evidence** | Proof the Platform Layout Engine preserved the obligation. |

## 8.4 Adaptation hierarchy

When expression capacity changes, resolution follows this order:

1. preserve all required component responsibilities;
2. preserve active context, identity, semantic order, and continuity;
3. preserve professional action, authority requirement, feedback, and recovery;
4. preserve comparison correspondence and required co-availability;
5. apply only declared serialization, deferral, or summarization;
6. state every degradation explicitly;
7. fail rather than remove or reinterpret required meaning.

This order is a preservation contract, not new professional priority.

# 9. Deterministic Composition Resolution

## 9.1 Input contract

Resolution accepts:

- one active context and current Rendering Tree generation;
- validated Canonical Component instances;
- resolved Semantic Token Sets;
- current Presentation State contracts;
- active Composition and Layout Intent registry revisions;
- Navigation and IA references;
- Platform Layout Engine capability declaration;
- prior compatible plan when replacement applies.

Resolution cannot query alternate sources to reinterpret components.

## 9.2 Resolution pipeline

```text
Validate Context and Surface Boundary
        ↓
Bind Eligible Component Instances
        ↓
Resolve Structural Regions
        ↓
Resolve CR-01–CR-08 Relationships
        ↓
Resolve Semantic Order
        ↓
Resolve LI-01–LI-08 Obligations
        ↓
Validate Containment, Adaptation, and Continuity
        ↓
Publish Complete Composition Plan
```

Equivalent input and registry revisions produce equivalent membership, regions,
relationships, order, intents, fallback, and engine obligations.

## 9.3 Outcomes

```text
Complete Composition Plan
```

```text
Explicitly Degraded Composition Plan
```

or:

```text
Invalid — No Layout Engine Handoff
```

Ambiguous region assignment, cyclic containment/order, missing required
component, or unresolved Layout Intent invalidates the plan.

# 10. Replacement Rules

## 10.1 Compatible replacement

A successor plan is compatible only when it preserves:

- active professional context and Surface boundary;
- component and canonical subject identities where still applicable;
- required Structural Region responsibilities;
- semantic order and typed relationships;
- token and Presentation State ownership;
- Layout Intent preservation obligations;
- origin, return, feedback, recovery, and degradation disclosure.

## 10.2 Atomic replacement

```text
Current valid Composition Plan
        ↓
Derive and validate successor plan
        ↓
Verify Layout Intent continuity
        ↓
Atomic plan replacement
        ↓
Prior plan becomes obsolete
```

Invalid or partial plans never replace a current valid plan. Replacement creates
no canonical event and modifies no Component, Rendering Node, Semantic Token, or
Presentation State.

# 11. Platform Layout Engine Boundary

## 11.1 Boundary contract

```text
Composition and Layout System
  owns component organization and structural intent
        ↓
Validated Composition Plan + Layout Intent Set
        ↓
Platform Layout Engine
  owns platform-specific physical arrangement
```

The plan and intent set are the only handoff. The engine cannot reinterpret
canonical sources or component responsibilities.

## 11.2 Canonical side responsibilities

Composition and Layout System must:

- provide complete membership, region, relationship, order, and intent
  contracts;
- state required preservation, permitted adaptation, and truthful fallback;
- validate boundaries, cycles, cardinality, continuity, and replacement;
- expose accessibility-equivalent structural obligations;
- reject ambiguous, incomplete, or incompatible plans;
- remain neutral to physical arrangement and runtime mechanics.

It must not:

- select physical arrangement primitives;
- prescribe dimensions, positions, or adaptation mechanics;
- inspect engine internals;
- change structural meaning to satisfy engine limitations;
- infer professional meaning from engine output.

## 11.3 Platform engine responsibilities

A Platform Layout Engine may choose any physical arrangement that conforms. It
must:

- consume the exact current plan and intent revision;
- preserve component identity, responsibility, Structural Regions, semantic
  order, relationships, and boundaries;
- preserve all LI-01–LI-08 obligations;
- keep navigation, feedback, recovery, transient origin, and return recoverable;
- report unsupported obligations and applied degradation;
- preserve accessible structural equivalence;
- reject a plan it cannot express conformantly.

It must not:

- add, remove, duplicate, or reinterpret component responsibilities;
- turn physical containment into domain containment;
- derive priority, authority, Focus, causality, or Relationship from placement;
- reorder professional meaning without permitted adaptation;
- feed physical arrangement back as canonical state;
- define a competing composition or Layout Intent taxonomy.

## 11.4 Arrangement independence

Materially different physical arrangements conform when the same component
membership, context, semantic order, boundaries, relationships, intents,
continuity, and degradation remain independently recoverable.

This document defines no Platform Layout Engine implementation.

# 13. Conformance Criteria

A Composition and Layout realization conforms only when:

1. every plan satisfies the descriptor contract;
2. every member is a valid current Canonical Component instance;
3. CR-01–CR-08 relationships are typed, sourced, and valid;
4. SR-01–SR-07 assignments are complete and non-authoring;
5. LI-01–LI-08 obligations are complete and value-free;
6. containment and semantic order are acyclic;
7. component, RN, DSR, STC, and PSD contracts remain immutable;
8. adaptation preserves required meaning or declares degradation;
9. replacement is compatible and atomic;
10. Platform Layout Engine ownership does not overlap canonical ownership;
11. materially different arrangements preserve equivalent structural intent;
12. accessibility equivalence is demonstrable;
13. invalid plans fail safely;
14. no implementation vocabulary enters the canonical contract;
15. all 44 invariants pass.

## Deterministic verdict

```text
Pass
```

when every applicable criterion and invariant is satisfied;

```text
Fail
```

when composition, adaptation, replacement, or engine arrangement adds, removes,
duplicates, hides, or reinterprets canonical responsibility or structural
intent;

```text
Not Applicable
```

only for engine infrastructure that neither consumes nor fulfills a Composition
Plan or Layout Intent obligation.

# 14. Completion Criteria

Composition and Layout System is complete when:

1. composition purpose, ownership, descriptor, lifecycles, responsibilities,
   and boundaries are explicit;
2. CR-01–CR-08 relationships are exhaustive and bounded;
3. SR-01–SR-07 Structural Regions organize responsibility without creating IA;
4. containment, order, grouping, comparison, transient attachment, and
   replacement are deterministic;
5. LI-01–LI-08 express structural intent without physical arrangement values;
6. adaptation and replacement preserve canonical meaning and continuity;
7. Canonical Component responsibilities remain immutable;
8. Platform Layout Engine and canonical ownership remain mutually exclusive;
9. conformance produces an unambiguous verdict;
10. Architecture Review approves the document for dependency use.
