# 2. Contract Review

## 2.1 Purpose and authority

M6.14 is limited to traceability and implementation-facing addressability.
Mapping never creates, completes, corrects, or infers canonical meaning. It is a
translation ledger and conformance boundary, not a programming model, schema,
generator, repository convention, or professional source.

**Result: Pass.**

## 2.2 Ownership

The model owns only mapping identity/revision, association to aliases, category,
target context, coverage, traceability, compatibility, migration, evidence,
publication, deprecation, withdrawal, recovery, and mapping conformance.

Professional truth, Design Objects, semantics, rendering, tokens, Presentation
State, components, composition, layout, interactions, navigation, adapter
contracts, accessibility, motion, and conversational presentation remain
upstream-owned. Adapters and artifacts own mechanics only.

**Result: Pass.**

## 2.3 Descriptor

The descriptor keeps canonical source identity/revision/owner, mapping
identity/revision/category, target context, alias, artifact multiplicity,
dependencies, coverage, compatibility, degradation, evidence, and lifecycle
distinct. The fields are logical obligations rather than a prescribed schema.

**Result: Pass.**

## 2.4 Responsibilities and lifecycles

The contract requires exact source binding, complete coverage, preserved
ownership, explicit degradation, evidence-backed compatibility and migration,
non-authoritative artifacts, and deterministic verdicts. It prohibits invented
obligations, collapsed distinctions, name-based identity, reverse state
inference, target-defined validity, and implementation reference models.

Definition publication requires an approved exact source, complete obligations,
dependencies, compatibility, degradation, recovery, and evidence. Realization
separately resolves source/mapping revisions, target context, dependencies,
qualification, traceability, migration, supersession, and withdrawal. Consumer
publication is atomic.

**Result: Pass.**

# 4. Traceability and Determinism

## 4.1 Identity and multiplicity

Canonical source, mapping record, implementation-facing alias, and realized
artifact identities remain non-interchangeable. Alias equality proves no
semantic equality; alias difference proves no semantic difference.

Multiple realizations require identical applicable obligations, explicit
mechanical or degraded differences, cross-platform evidence, no canonical
reference implementation, and independent replaceability. Composed artifacts
retain separate source identities and mapping records.

**Result: Pass.**

## 4.2 Forward-only authority

Authority flows only from canonical source to mapping, qualified adapter
realization, and artifact. Inspection may provide drift evidence but cannot
define or repair canonical meaning. Round-trip generation, reverse engineering,
usage, runtime behavior, and artifact shape are non-authoritative.

**Result: Pass.**

## 4.3 Completeness and resolution

Every obligation, category, dependency, unsupported condition, alias, normal
path, replacement, degradation, recovery, and evidence requirement has a
disposition. Identical source revisions, mapping revision, target context, and
capability declaration produce identical mapping and conformance obligations.
Incomplete or conflicting inputs fail closed.

**Result: Pass.**

# 5. Change, Degradation, and Recovery

Editorial, Compatible, Migration-required, Incompatible, and
Canonical-source changes are distinct and evidence-backed. Mechanical
compatibility cannot conceal semantic incompatibility.

Deprecation preserves history, replacement, compatibility, sources, evidence,
and active consumers. It cannot waive obligations or redirect an alias to
different meaning.

Migration identifies source/destination revisions, aliases, contexts,
dependencies, preserved obligations, incompatibilities, coexistence, cutover,
degradation, recovery, and evidence. Mixed incompatible publication is
prohibited.

Fallback order is full equivalence, equivalent composition,
essential-preserving explicit reduction, then safe unavailability. Recovery
revalidates sources, mappings, capabilities, dependencies, identity,
interaction/navigation uniqueness, accessibility, no-motion, multimodality,
continuity, atomic replacement, and fresh evidence. Artifacts cannot
self-certify.

**Result: Pass.**

# 6. Boundary Review

```text
Canonical Presentation Architecture
        ↓
Design-to-Code Mapping Contract
        ↓
Implementation Artifact Adapter
        ↓
Code / Generated Artifacts / Platform Interfaces
```

| Layer | Responsibility | Prohibited authority |
| --- | --- | --- |
| Canonical Presentation Architecture | All canonical meaning, identity, state, structure, interaction, navigation, accessibility, motion, conversation, and invariants. | Dependence on artifacts for validity. |
| Design-to-Code Mapping Contract | Traceability, aliases, coverage, compatibility, dependencies, and evidence. | Upstream meaning or downstream mechanics. |
| Implementation Artifact Adapter | Resolve published mappings and realize declared target mechanics. | Create mappings, reinterpret sources, infer truth, or approve architecture. |
| Artifacts and platform interfaces | Mechanics only. | Canonical identity, meaning, ownership, state, authority, or conformance. |

Handwritten and generated artifacts have equal non-authoritative status.

**Result: Pass.**
