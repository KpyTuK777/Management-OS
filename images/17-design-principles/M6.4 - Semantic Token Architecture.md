# M6.4 — Semantic Token Architecture

## Status

```text
Ready for Architecture Review
Milestone M6
```

## Authority

This document is the single source of truth for canonical semantic tokens in
Management OS. It defines what a Semantic Token is, which token categories
exist, how tokens bind to Rendering Nodes, how canonical resolution works, and
which obligations cross the Platform Theme / Design System Adapter boundary.

Semantic Token Architecture consumes approved canonical meaning. It does not
create professional meaning, visual semantics, Design Objects, Semantic Roles,
Rendering Nodes, platform values, styling, or implementation artifacts.

# 1. Purpose

A Rendering Tree preserves semantic structure, but a Platform Adapter still
needs an explicit, technology-neutral contract describing the meanings that
each Rendering Node must express. Semantic Tokens provide that contract.

```text
Canonical and source-owned meaning
        ↓
Design Object + Primary Semantic Role
        ↓
Validated Rendering Node
        ↓
Canonical Semantic Token Resolution
        ↓
Resolved Semantic Token Set
        ↓
Platform Theme / Design System Adapter
        ↓
Platform-specific expression
```

A Semantic Token is a stable symbolic reference to one already-owned semantic
obligation. It answers:

> Which canonical meaning must be expressed for this Rendering Node?

It does not answer:

> Which visual or technical value should express it?

Without this layer, adapter values could become the source of meaning, unrelated
semantic dimensions could be conflated, token names could invent product
concepts, and platform differences could change professional interpretation.

# 2. Semantic Token Principles

1. **Meaning, Not Value.** A Semantic Token identifies meaning and carries no
   platform value.
2. **Source-Owned.** Every token traces to an approved canonical owner.
3. **Rendering-Bound.** A token is consumed through a validated Rendering Node,
   not by bypassing the Rendering Tree.
4. **One Obligation per Token.** One token represents one recoverable semantic
   responsibility or dimension.
5. **Independent Dimensions.** Authority, certainty, attention, urgency,
   lifecycle, activity, and other dimensions never collapse into one token.
6. **Role Before Qualification.** Every semantic node resolves its primary role
   obligation before independent qualifiers.
7. **No Value Semantics.** A concrete value never defines, renames, or changes a
   token.
8. **Deterministic Resolution.** Equivalent tree input and registry revision
   produce an equivalent resolved token set.
9. **No Implicit Inheritance.** Parentage, nesting, proximity, or repetition
   cannot pass meaning to a child without an explicit canonical binding rule.
10. **Capability Honest.** An adapter either preserves a token obligation,
    applies an approved equivalent fallback, or declares non-conformance.
11. **Adapter Neutral.** Token identity and meaning survive every conforming
    expression technology.
12. **Accessible Equivalence.** A token obligation remains recoverable without
    dependence on one sensory channel or value.
13. **No Implicit Authority.** Token presence, absence, order, or frequency
    grants no authority.
14. **Projection Only.** Token resolution changes no canonical source,
    Operational Memory, Current Situation, interaction, or Matter lifecycle.
15. **Explicit Supersession.** A revised token definition supersedes rather than
    silently reinterprets an existing semantic identity.

# 3. Canonical Semantic Token

## 3.1 Definition

A Canonical Semantic Token is a registered symbolic contract containing:

- one stable token identity;
- one taxonomy category;
- one source-owned semantic obligation;
- one permitted scope;
- one binding rule;
- one resolution and conflict rule;
- one adapter-equivalence obligation;
- one fallback contract;
- explicit prohibited implications.

A token is not a value, variable, property, class, selector, style, asset,
component input, or design-tool primitive.

## 3.2 Ownership

Semantic Token Architecture owns only:

- the token taxonomy and token descriptor;
- token registration and supersession rules;
- Rendering Node binding rules;
- deterministic canonical resolution;
- resolved token-set contracts;
- the Platform Theme / Design System Adapter boundary;
- token conformance criteria.

It does not own:

| Concern | Canonical owner |
|---|---|
| Professional meaning, truth, identity, authority, and lifecycle | Canonical Management Model and owning source models |
| Visual meaning and independent semantic dimensions | Canonical Visual Semantics |
| Design Object types | Canonical Design Object Model |
| Primary Semantic Roles | Canonical Design Semantics |
| Rendering Tree and Rendering Node identity | Canonical Rendering Model |
| Information residency and representation role | Canonical Information Architecture |
| Navigation and professional attention | Operational Navigation and Navigation Governance |
| Interaction intent, consequence, commitment, and recovery | Operational Interaction Language and Operational Memory |
| Concrete expression values and technical mapping | Platform Theme / Design System Adapter |

## 3.3 Token descriptor

Every token definition declares:

| Field | Requirement |
|---|---|
| **Token ID** | Stable canonical token identity. |
| **Category** | Exactly one STC-01–STC-06 category. |
| **Semantic obligation** | One source-owned meaning the adapter must preserve. |
| **Canonical source** | Owning model, source identifier, and applicable revision. |
| **Eligible Rendering Nodes** | RN kinds and DSR roles to which the token may bind. |
| **Scope** | Node occurrence, composition, tree generation, interaction, or declared source scope. |
| **Binding condition** | Complete deterministic predicate over validated tree data. |
| **Cardinality** | Required, optional, or conditionally required occurrence count. |
| **Combination rule** | Permitted coexistence with other token categories and dimensions. |
| **Conflict rule** | Required disposition for contradictory candidates. |
| **Adapter obligation** | Meaning and distinction a platform expression must preserve. |
| **Fallback rule** | Canonically permitted behavior when expression is unavailable. |
| **Prohibited implications** | Meanings no resolution or platform value may convey. |
| **Lifecycle condition** | Registered, Active, Deprecated, or Retired definition status. |
| **Supersession reference** | Replacement token definition where applicable. |

Token IDs are architecture identities. They are not names for platform values or
implementation interfaces.

# 4. Token Lifecycle

## 4.1 Definition lifecycle

Token definition lifecycle is governance metadata, not a domain or Matter
lifecycle:

```text
Proposed
    ↓ Architecture Review
Registered
    ↓ Approved use
Active
    ↓ Explicit replacement
Deprecated
    ↓ Migration complete
Retired
```

| Condition | Meaning | Consumption rule |
|---|---|---|
| **Proposed** | Candidate definition under review. | Cannot appear in a conforming resolved set. |
| **Registered** | Identity, category, source, and contract are accepted. | May be prepared for approved activation. |
| **Active** | Current definition for its semantic obligation. | May resolve when its binding condition holds. |
| **Deprecated** | Still interpretable but superseded for new resolution. | Existing references remain traceable; new resolution uses the successor. |
| **Retired** | No current resolution may emit the definition. | Historical governance reference only. |

Meaning cannot change under one Token ID. A semantic change requires a new
definition and explicit supersession.

## 4.2 Binding lifecycle

A token occurrence within one Rendering Tree generation follows a projection
lifecycle:

```text
Eligible
    ↓
Bound
    ↓
Resolved
    ↓
Handed Off
    ↓
Obsolete with tree generation

Conflict or missing requirement
    ↓
Invalid — No conforming handoff
```

Binding lifecycle creates no canonical event and cannot outlive the Rendering
Node or tree generation to which it belongs.

# 5. Canonical Token Taxonomy

## 5.1 Admission rule

A token category exists only when it represents a distinct canonical obligation
that:

- is required by at least one Rendering Node;
- cannot be expressed as another category without ambiguity;
- has a canonical source and stable binding rule;
- remains meaningful across materially different adapters;
- contains no concrete expression value.

## 5.2 Taxonomy

| ID | Token category | Represents | Canonical basis | Must not represent |
|---|---|---|---|---|
| **STC-01** | **Semantic Role Token** | Why the Rendering Node exists in its professional context. | One DSR-01–DSR-14 primary role. | Appearance, node type, importance, or platform control role. |
| **STC-02** | **Semantic Dimension Token** | One independent Visual Semantics dimension and source-owned value. | One D-01–D-18 dimension assignment. | Combined status, style state, or inferred value. |
| **STC-03** | **Structural Obligation Token** | Meaning carried by semantic parentage, composition, place, order, or typed cross-reference. | Design Object relationships and Rendering Tree contracts. | Layout, geometry, technical containment, or domain Relationship. |
| **STC-04** | **Professional Interaction Token** | One OI interaction obligation, including authority requirement and professional consequence. | DSR-11, RN-08, and canonical OI contract. | Input mechanic, execution, commitment, or authority grant. |
| **STC-05** | **Continuity and Recovery Token** | Origin, return, interruption, transience, persistence, recovery, or navigation-continuity obligation. | Navigation, OI recovery, DSR-10/13/14, and RN-07/10/11 contracts. | New Context Envelope, hidden navigation, or lifecycle progression. |
| **STC-06** | **Rendering Condition Token** | Completeness, degradation, unavailability, replacement, or projection-validity obligation. | Canonical Rendering Model generation and fallback contract. | Domain state, Current Situation, interaction success, or canonical history. |

The taxonomy is exhaustive for M6.4. New categories require Architecture Review
and proof that STC-01–STC-06 cannot express the obligation without conflation.

it:

| Dimension | Meaning source |
|---|---|

| D-02 | Provenance |
| D-03 | Epistemic condition |
| D-04 | Review condition |
| D-05 | Authority |
| D-06 | Ownership and responsibility |
| D-07 | Attention relation |
| D-08 | Attention Priority |
| D-09 | Consequence and materiality |
| D-10 | Temporal urgency |
| D-11 | Lifecycle posture |
| D-12 | Operational participation |
| D-13 | Activity and execution |
| D-14 | Stability and deviation |
| D-15 | Temporal validity and currentness |
| D-16 | Relationship condition |
| D-17 | System availability |
| D-18 | Interruption classification |

One STC-02 occurrence binds one dimension. Compound professional state is a set
of independent token occurrences, never a combined token.

# 6. Token Relationships and Constraints

## 6.1 Permitted relationships

| Relationship | Meaning | Constraint |
|---|---|---|
| **binds to** | Token occurrence applies to one Rendering Node or declared tree scope. | Binding condition must be true for the exact input revision. |
| **qualifies** | STC-02 adds one independent source-owned dimension to a role-bearing node. | Cannot replace or modify STC-01. |
| **requires** | One token obligation makes another conditionally mandatory. | Requirement must be declared by canonical source or Rendering Model contract. |
| **composes with** | Independent tokens coexist as a recoverable semantic set. | Each retains identity and adapter distinction. |
| **references** | Token points to an attributable canonical source or related node obligation. | Creates no ownership, parentage, or domain Relationship. |
| **fallback for** | Approved token preserves an explicitly reduced but truthful obligation. | Cannot claim semantic completeness or equivalence it does not provide. |
| **supersedes** | New token definition replaces an older definition prospectively. | History and original meaning remain traceable. |

## 6.2 Combination rules

1. Every semantic Rendering Node resolves exactly one STC-01 token.
2. A node may resolve zero or more STC-02 tokens, with at most one effective
   occurrence per dimension and declared scope.
3. STC-03 tokens exist only for semantically meaningful Rendering Tree
   relationships.
4. RN-08 requires one STC-04 token.
5. RN-07, RN-10, and RN-11 resolve applicable STC-05 obligations.
6. STC-06 binds only to rendering projection conditions and never substitutes
   professional state.
7. Tokens from different categories compose without precedence unless an
   approved source contract declares a dependency.
8. No token inherits through parentage by default.
9. Identity, authority, priority, currentness, and interaction consequence
   never inherit.
10. Repetition, ordering, grouping, and persistence create no new token.

## 6.3 Conflict rules

A conflict exists when:

- two candidates claim different effective meanings for the same category,
  source dimension, scope, and input revision;
- a required token is absent;
- a token binds to an ineligible RN/DSR combination;
- a fallback claims undegraded equivalence;
- source revisions are inconsistent.

Canonical resolution does not choose a winner through declaration order,
frequency, tree depth, platform preference, or arbitrary priority. It must:

1. defer to the owning canonical source's explicit conflict contract;
2. preserve independent dimensions when no conflict exists;
3. otherwise mark the node token set invalid;
4. prevent conforming adapter handoff until the conflict is corrected.

# 7. Canonical Token Resolution

## 7.1 Input contract

Resolution accepts:

- one validated current Rendering Tree generation;
- RN-01–RN-11 node descriptors;
- DO and DSR references preserved by the tree;
- canonical/source identities and revisions;
- D-01–D-18 qualifier assignments;
- IA, Navigation, and OI mappings;
- active token registry revision;
- declared Platform Adapter capabilities, without platform values.

Resolution cannot query alternative sources to reinterpret the tree.

## 7.2 Resolution pipeline

```text
Validated Rendering Node
        ↓
Resolve STC-01 Primary Role
        ↓
Resolve STC-02 Independent Dimensions
        ↓
Resolve STC-03 Structural Obligations
        ↓
Resolve STC-04 Interaction Obligations
        ↓
Resolve STC-05 Continuity and Recovery
        ↓
Resolve STC-06 Rendering Conditions
        ↓
Validate Completeness and Conflicts
        ↓
Resolved Semantic Token Set
```

## 7.3 Deterministic rules

For every Rendering Node:

1. read only the node's validated descriptor and referenced registry revision;
2. select the single active STC-01 definition matching its DSR role;
3. emit one STC-02 occurrence for every applicable explicit qualifier;
4. emit STC-03 only for declared semantic relationships;
5. require STC-04 exactly when an OI interaction mapping exists;
6. emit applicable STC-05 obligations from explicit navigation, feedback,
   transient, origin, return, or recovery contracts;
7. emit STC-06 only from Rendering Model condition and fallback data;
8. evaluate cardinality, eligibility, combination, and source revision;
9. reject unresolved same-scope conflict;
10. order the resolved set by category identity and stable token identity for
    deterministic comparison, never to imply professional priority.

Equivalent inputs produce the same token identities, bindings, scopes,
relationships, required distinctions, and fallback obligations.

## 7.4 Resolved token set contract

Each node-level resolved set declares:

| Field | Requirement |
|---|---|
| **Tree and Node identity** | Exact generation and RN occurrence. |
| **Registry revision** | Exact semantic token registry used. |
| **Resolved tokens** | Stable token IDs with category, semantic obligation, source, and scope. |
| **Relationships** | Requires, composes-with, references, and fallback relations. |
| **Completeness** | Complete, explicitly degraded, or invalid. |
| **Adapter distinctions** | Token meanings that must remain independently recoverable. |
| **Unavailable obligations** | Missing capability and approved fallback, if any. |
| **Prohibited implications** | Meaning no platform assignment may introduce. |

The resolved set contains no concrete expression values.

## 7.5 Resolution outcomes

```text
Complete Resolved Token Set
```

```text
Explicitly Degraded Resolved Token Set
```

or:

```text
Invalid — No Adapter Handoff
```

Partial or invalid resolution never becomes a conforming handoff.

# 9. Platform Theme / Design System Adapter Boundary

## 9.1 Boundary contract

```text
Semantic Token Architecture
  owns symbolic meaning and canonical resolution
        ↓
Complete or explicitly degraded Resolved Semantic Token Set
        ↓
Platform Theme / Design System Adapter
  owns concrete platform value assignment
```

The resolved token set is the only handoff. The canonical layer cannot select
platform values. The adapter cannot reinterpret token meaning.

## 9.2 Canonical side responsibilities

Semantic Token Architecture must:

- provide stable token identity, meaning, source, scope, and relationships;
- resolve tokens deterministically from the validated Rendering Tree;
- expose all required independent distinctions;
- state completeness, degradation, fallback, and prohibited implications;
- remain neutral to expression technology and design tool;
- reject ambiguous or incomplete token sets.

It must not:

- assign concrete values;
- define value formats or scales;
- select a platform convention;
- use adapter availability to change canonical meaning;
- treat adapter mapping as canonical truth.

## 9.3 Adapter side responsibilities

A Platform Theme / Design System Adapter may assign one or more
platform-specific values or signals to each resolved token. It must:

- preserve token identity and source traceability;
- keep independent token meanings independently recoverable;
- provide equivalent meaning across required sensory channels;
- preserve role, state, authority, attention, consequence, continuity, and
  rendering-condition distinctions;
- declare mapping coverage and unsupported obligations;
- fail rather than fabricate meaning when no conforming assignment exists.

It must not:

- rename or redefine token meaning;
- merge non-equivalent tokens into one ambiguous signal;
- assign one signal two incompatible professional meanings;
- infer a missing canonical token from a platform convention;
- feed platform values back as canonical or source-owned state;
- create a competing semantic token taxonomy.

## 9.4 Value independence

A token may require several complementary platform signals for accessible and
unambiguous expression. No individual platform signal is canonical. Replacing
all assigned values while preserving every token obligation changes expression,
not professional meaning.

This document defines the boundary only. It defines no Platform Theme, Design
System Adapter, value vocabulary, or mapping implementation.

# 10. Semantic Token Invariants

1. Every active token has one stable Token ID.
2. Every token belongs to exactly one STC-01–STC-06 category.
3. Every token represents exactly one recoverable semantic obligation.
4. Every token has one attributable canonical source.
5. A token never creates professional meaning.
6. A token contains no concrete platform value.
7. Every semantic Rendering Node resolves exactly one STC-01 token.
8. STC-01 preserves the node's primary DSR role.
9. Each STC-02 occurrence represents exactly one D-01–D-18 dimension.
10. Independent dimensions remain separate.
11. RN-09 resolves exactly one primary STC-02 occurrence.
12. STC-03 never converts tree structure into layout or domain Relationship.
13. RN-08 resolves exactly one STC-04 interaction obligation.
14. STC-04 never executes or commits an interaction.
15. STC-05 never creates Context Envelope, navigation, Focus, or lifecycle.
16. STC-06 never becomes domain state or Current Situation.
17. Parentage creates no token inheritance by default.
18. Identity, authority, priority, currentness, and consequence never inherit.
19. Repetition, grouping, order, and persistence create no token.
20. One input and registry revision produce one equivalent resolved set.
21. Resolution order never implies professional priority.
22. Same-scope conflict is never resolved by platform preference.
23. Missing required token invalidates the node set.
24. Explicit degradation never claims full semantic equivalence.
25. A resolved token occurrence cannot outlive its Rendering Tree generation.
26. Token lifecycle creates no canonical event.
27. Meaning never changes under an existing Token ID.
28. Supersession preserves the identity and meaning of the superseded token.
29. Deprecated tokens do not enter new resolution.
30. Retired tokens do not enter current resolution.
31. Adapter mapping cannot alter token identity, category, meaning, or scope.
32. One platform signal cannot carry incompatible token meanings.
33. Concrete values cannot flow back as canonical state.
34. Accessible expression preserves all required token distinctions.
35. Invalid token sets never cross the adapter boundary as conforming input.
36. Semantic Tokens own no domain truth, authority, lifecycle, Navigation,
    Operational Memory, Current Situation, Context Envelope, Design Object,
    Semantic Role, Rendering Node, or information residency.

# 11. Conformance Criteria

A Semantic Token system conforms only when:

1. every token satisfies the descriptor contract;
2. every active definition belongs to STC-01–STC-06;
3. every token traces to an approved canonical source;
4. all RN-01–RN-11 token obligations are covered;
5. STC-02 covers D-01–D-18 without combining dimensions;
6. resolution uses only validated Rendering Tree and registry input;
7. equivalent input produces equivalent resolved sets;
8. cardinality, eligibility, combination, conflict, and fallback rules are
   deterministic;
9. missing or conflicting obligations fail safely;
10. resolved sets contain no concrete values;
11. adapter assignments preserve every independent semantic distinction;
12. token and platform value ownership remain separate;
13. accessible equivalence is demonstrable;
14. no implementation vocabulary enters token identity or resolution;
15. all 36 invariants pass.

## Deterministic verdict

```text
Pass
```

when every applicable criterion and invariant is satisfied;

```text
Fail
```

when a token, resolution, or adapter mapping adds, removes, combines,
reinterprets, or ambiguously expresses canonical meaning;

```text
Not Applicable
```

only for non-semantic adapter infrastructure that neither consumes nor fulfills
a Semantic Token obligation.

# 12. Completion Criteria

Semantic Token Architecture is complete when:

1. Semantic Token purpose, ownership, descriptor, responsibilities, and
   lifecycles are explicit;
2. STC-01–STC-06 are exhaustive and mutually bounded;
3. DSR-01–DSR-14 roles and D-01–D-18 dimensions remain source-owned;
4. all RN-01–RN-11 consumption obligations are defined;
5. canonical token resolution is deterministic and implementation-independent;
6. token relationships, combination, conflict, fallback, and supersession rules
   are complete;
7. the Platform Theme / Design System Adapter boundary has mutually exclusive
   responsibilities;
8. no concrete value, platform convention, or design-tool primitive enters the
   canonical layer;
9. conformance produces an unambiguous verdict;
10. Architecture Review approves the document for dependency use.
