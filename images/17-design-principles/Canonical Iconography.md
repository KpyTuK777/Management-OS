# Canonical Iconography

## Status

```text
Research Only
```

This document defines the intended iconography system for Management OS. It does
not approve assets, change the interface, or authorize implementation.

## 1. Purpose

Management OS iconography is a recognition layer for operational meaning. It
must help a person distinguish material, evidence, reasoning, governed work, and
navigation without competing with the Current Situation or implying authority
that the underlying model does not possess.

An icon is admissible only when it improves recognition, orientation, or
interaction. It is never decoration, a substitute for a label, or a source of
domain truth.

## 2. Current-State Audit

### Repository inventory

No standalone production `.svg` asset exists. The current interface contains
three visual mechanisms:

1. Four inline SVG definitions generated by `js/sidebar.js`.
2. Emoji and Unicode symbols embedded in `index.html`,
   `js/natural-capture.js`, and CSS generated content.
3. CSS classes that style both SVG and emoji as if they belonged to one family.

The data-URI SVG in `css/pages.css` is a noise texture, not an icon, and is
outside the semantic icon system.

### CSS audit

`.dock-icon` establishes a coherent baseline: 20–21 px rendered size, a 24×24
viewBox, no fill, `currentColor`, round caps and joins, and a 1.55 stroke.
However, the class is declared more than once and later rules also treat it as
text with `font-size`. `.collection-icon` is likewise defined repeatedly with
font sizing, filters, borders, backgrounds, and several dimensions. These rules
style containers but do not define a canonical glyph contract.

### Semantic duplication and collision

- Target currently means Operational Matters but is also the natural candidate
  for Focus or Outcome.
- Magnifier currently means Current Situation but conventionally means Search
  or Inspect.
- Pin currently means Symptom, although it conventionally means location,
  attachment, or persistence.
- Chart currently means Data and Evidence.
- Brain currently means Hypothesis, making epistemic status look like a content
  topic.
- Warning currently means Contradiction, warning, and material risk.
- Arrow-up-right currently means Source but conventionally means external link.

### Audit verdict

The Dock SVGs demonstrate a viable geometric direction. They are not yet a
governed family and their semantic assignments need review. The emoji and
Unicode operational layer is not production-ready. The current system has
recognizable individual marks but no canonical icon vocabulary.

## 3. Canonical Principles

1. **Semantic first.** One canonical meaning maps to one canonical glyph.
2. **Decoration never.** Remove an icon that adds no recognition or action.
3. **Model before metaphor.** The domain definition determines the mark; library
   names do not.
4. **No authority by styling.** Fill, color, or emphasis cannot turn proposed
   meaning into accepted meaning.
5. **One family.** Production surfaces cannot mix emoji, icon fonts, Unicode
   pictograms, and unrelated SVG families.
6. **Shared construction.** Use a 24×24 master grid, common keylines, optical
   center, cap/join behavior, terminal language, and corner radii.
7. **Controlled weight.** Default outline weight is optically equivalent across
   glyphs. Nominal stroke alone is not sufficient.
8. **Quiet silhouette.** Prefer one primary contour and at most one semantic
   modifier. Avoid miniature illustrations.
9. **Material hierarchy.** Operational objects may carry stronger presence than
   navigation controls, but not different drawing grammar.
10. **State is additive.** State is communicated by label, container, and when
    necessary a governed badge; never by swapping to an unrelated icon.
11. **Color is supplementary.** Meaning survives monochrome and forced-colors
    rendering.
12. **Labels remain canonical.** Unfamiliar domain icons require visible text;
    icon-only controls require an accessible name and tooltip where helpful.
13. **Stable placement.** Active states may change container or fill but cannot
    move or reshape the glyph.
14. **No inferred causality.** Relationship-like lines and arrows appear only
    for real accepted Relationship semantics.
15. **No silent fallback.** Unknown semantic tokens fail visibly in development;
    they do not become a dot, sparkle, or generic document.

## 4. Construction Contract

| Property | Canonical rule |
|---|---|
| Master grid | 24×24 |
| Primary live area | 20×20; overshoot only for optical correction |
| Default rendered sizes | 16, 20, and 24 px |
| Default style | Outline |
| Nominal stroke | Research target 1.75 at 24 px; validate optically at all sizes |
| Caps and joins | Round unless a semantic geometry requires a deliberate exception |
| Corner system | Limited shared radius set; no arbitrary per-icon rounding |
| Optical weight | Equal perceived darkness, not mechanically identical path length |
| Detail budget | Recognizable at 16 px; normally no more than two semantic layers |
| Color | `currentColor`; semantic color belongs to the component/state token |
| Filled form | Only for selected/active state or intrinsically solid status marks |
| Bounding box | Stable between outline, filled, active, and disabled variants |
| Mirroring | Only directional navigation glyphs; semantic/domain glyphs do not auto-mirror |

Filled and outline forms are not two interchangeable aesthetics. Outline is the
base vocabulary. A filled form is admitted only when it expresses selection or
a tested small-size requirement without changing meaning.

## 5. Canonical Categories

### Shared state contract

All categories follow these interaction rules:

| State | Treatment |
|---|---|
| Rest | Outline glyph in normal text/icon color |
| Hover | Component state layer changes; glyph geometry does not |
| Focus-visible | External focus ring; never encode focus by glyph alone |
| Active/selected | Container emphasis; optional approved filled counterpart |
| Disabled | Reduced component contrast, retained silhouette and accessible name |
| Pending/proposed | Explicit text/state badge; never lighter authority by icon guesswork |
| Accepted/completed | Governed state mark plus text; no color-only confirmation |
| Error/risk | Dedicated semantic mark and text; never reuse Contradiction automatically |

### Operational

| Token | Meaning and use | Do not use for | Variants |
|---|---|---|---|
| `current-situation` | Governed present understanding of a Matter | Search, dashboard, investigation | Outline; filled only when selected |
| `artifact` | Canonical material object with identity and provenance | Generic file or attachment | Outline |
| `relationship` | Accepted/proposed semantic relation between endpoints | Decorative connectors, hyperlinks | Outline; state supplied separately |
| `operational-memory` | Append-only consequential memory | Browser history, archive folder | Outline |
| `decision` | Governed choice or judgment | Target, task, acceptance alone | Outline; restrained solid status form |
| `change` | Meaningful transition between states | Refresh, sync, navigation | Outline |
| `intervention` | Intentional action applied to a situation | Tool/settings, generic task | Outline |
| `outcome` | Observed result attributable to work | Forecast, upward metric, success | Outline |

Operational marks are identity-bearing nouns. They may appear without interaction
state, so their silhouette must not depend on fill or color.

### Evidence

| Token | Meaning and use | Do not use for | Variants |
|---|---|---|---|
| `observation` | Directly recorded observation | View/inspect action, eyewitness emoji | Outline |
| `symptom` | Observable indication requiring explanation | Location pin, risk | Outline |
| `interview` | Human conversation captured as evidence | Chat action, audio file generally | Outline |
| `document` | Source document | Artifact generally, report specifically | Outline |
| `report` | Structured authored report | Any document or analytics screen | Outline |
| `measurement` | A measured value with method/context | Metric/KPI, chart | Outline |
| `metric` | Defined quantitative indicator | Measurement instance, outcome | Outline |
| `timeline` | Chronological evidence or query | Operational Memory itself | Outline |

Evidence marks identify source form, never evidence quality or truth. Confidence
and acceptance remain separate semantics.

### Reasoning

| Token | Meaning and use | Do not use for | Variants |
|---|---|---|---|
| `hypothesis` | Testable proposed explanation | Idea, brain, accepted finding | Outline |
| `finding` | Supported result of inspection/reasoning | Generic search result | Outline; optional accepted state badge |
| `contradiction` | Two materially incompatible claims/evidence paths | Warning, failure, risk automatically | Outline |
| `assumption` | Unverified premise currently relied upon | Hypothesis or default value | Outline |
| `question` | Explicit unresolved question | Help action | Outline |
| `insight` | Newly articulated consequential understanding | Decorative sparkle or tip | Outline |
| `risk` | Material uncertainty with adverse consequence | Contradiction or warning generally | Outline; solid only in compact status use |
| `confidence` | Degree of support attached to a claim | Completion/progress meter | Outline plus textual/quantitative value |

Reasoning icons must not anthropomorphize cognition. Avoid brains, magic,
sparkles, faces, and lightbulbs as default epistemic language.

### Work

| Token | Meaning and use | Do not use for | Variants |
|---|---|---|---|
| `task` | Bounded unit of work | Checklist collection or decision | Outline |
| `experiment` | Controlled test of a hypothesis | Generic lab decoration | Outline |
| `verification` | Deliberate validation activity | Acceptance/completion | Outline |
| `monitoring` | Ongoing observation against a condition | Notification bell | Outline |
| `completed` | Work reached its defined completion condition | Accepted meaning, positive outcome | Outline/solid status pair |
| `rejected` | Governed proposal was rejected | Error, delete, archive | Outline/solid status pair |
| `accepted` | Governed proposal entered accepted state | Completion or generic check | Outline/solid status pair |
| `proposed` | Meaning awaits governance | Draft file or low confidence | Outline with explicit label/state badge |

State marks may use filled compact forms because they often operate at 16 px,
but the adjacent state text remains required in consequential contexts.

### Navigation

| Token | Meaning and use | Do not use for | Variants |
|---|---|---|---|
| `focus` | Move attention to an operational object | Operational Matters identity, outcome | Outline; filled selected variant allowed |
| `inspect` | Open non-mutating detail/context | Current Situation identity, search | Outline |
| `expand` | Reveal nested content in place | Navigate forward | Directional outline |
| `collapse` | Hide nested content in place | Navigate back | Directional outline |
| `return` | Return to previous spatial context | Undo or rollback | Directional outline |
| `history` | Open retained history | Operational Memory identity, refresh | Outline |

Navigation marks are verbs. Their active state belongs to the control container.
They never imply domain mutation.

## 6. Library Research

The comparison evaluates suitability as a construction source, not popularity.

| Library | Consistency | Optical balance | Readability/density | Workbench suitability |
|---|---|---|---|---|
| Lucide | Strong 24×24 outline grammar and simple paths | Good at 20–24 px; some glyphs become sparse at 16 px | Quiet, low density | Strong utility/navigation foundation; insufficient domain semantics alone |
| Heroicons | Strong within each 24/20/16 family | Excellent size-specific optimization | Clear but relatively bold and product-UI conventional | Good controls/status; small catalogue and SaaS-familiar tone limit domain coverage |
| Tabler | Very broad, consistent 24×24/2 px outline base | Generally good; breadth introduces uneven complexity | Readable, sometimes too detailed or generic-dashboard-like | Best broad reference pool; requires optical normalization and strict curation |
| Phosphor | Coherent family with six weights | Strong type-like optical character | Flexible, but duotone/fill options can create stylistic drift | Strong semantic exploration source; regular weight can feel friendly/illustrative |
| Carbon | Rigorous 16/20/24/32 production discipline | Excellent at compact enterprise sizes | Dense, precise, restrained | Strong process reference; visual language is recognizably IBM/enterprise |
| Fluent | Strong system family with regular/filled themes | Highly polished across sizes | Friendly and sometimes soft/high-detail | Useful state/size reference; brand character and breadth exceed Workbench needs |
| Material Symbols | Large set, optical-size and variable weight/fill axes | Technically strong across sizes | Highly recognizable Material language | Excellent technical reference, poor identity fit without substantial adaptation |
| Remix | Broad neutral outline/filled pairs | Generally balanced | Medium density; many near-duplicate metaphors | Useful catalogue for gaps, but selection freedom risks semantic drift |
| Feather | Simple and coherent 24×24 outline baseline | Clean at 24 px, weak coverage/optimization for dense domain UI | Very quiet, sparse | Good philosophical ancestor; too limited and largely superseded by Lucide |

Research facts:

- Lucide and Feather use a simple 24×24 outline construction.
- Heroicons provides separate size-oriented families and outline/solid forms.
- Tabler uses a 24×24 grid and nominal 2 px stroke.
- Phosphor provides multiple weights including fill and duotone.
- Carbon explicitly optimizes several UI sizes and treats icons as governed
  design-system contributions.
- Fluent separates regular and filled system themes.
- Material Symbols exposes fill, weight, grade, and optical-size axes.
- Remix provides broad paired neutral-style symbols.

No external library defines Management OS concepts such as Canonical Artifact,
accepted Relationship, Current Situation, Operational Memory, contradiction
without warning, or governed proposal state with sufficient precision.

## 7. Final System Recommendation

### Verdict: create a governed Canonical Icon Set

Management OS should not adopt a library wholesale. It should create its own
semantic registry and canonical SVG set, using a carefully selected outline
library as a geometric starting point for universal controls.

This is a **curated and adapted set**, not a demand to redraw every chevron,
close mark, clock, or document primitive from zero:

- common navigation and utility primitives may be adapted from one approved
  source family;
- fundamental Management OS models require owned glyphs;
- every admitted glyph is copied into the product set, normalized, renamed by
  canonical semantic token, tested, and versioned;
- runtime code never imports arbitrary icons directly from the source library.

Recommended research baseline:

1. Use Lucide and Tabler as primary outline construction references.
2. Use Carbon and Material Symbols as optical-size/process references.
3. Use Phosphor to study family cohesion and weight, not to enable arbitrary
   per-instance weights.
4. Design owned marks for Current Situation, Artifact, Relationship,
   Operational Memory, contradiction, assumption, finding, intervention, and
   outcome.

## 9. Acceptance Criteria

A Canonical Iconography implementation is acceptable only when:

1. Every production icon maps to one registered semantic token.
2. Every token has a definition, allowed contexts, prohibited contexts, and
   accessible-name rule.
3. No emoji or platform-dependent pictogram remains in operational UI.
4. No runtime fallback silently substitutes a generic glyph.
5. All glyphs share the construction contract and pass optical review at 16,
   20, and 24 px on light and dark materials.
6. Outline/filled variants retain bounding box and meaning.
7. Active, disabled, focus, hover, proposed, accepted, rejected, and completed
   states remain understandable without color.
8. Current Situation, Artifact, Relationship, and Operational Memory are
   visually distinct without copying their data models into illustrations.
9. Contradiction, risk, rejection, and error cannot be confused.
10. Relationship marks never create decorative or unauthorized causality.
11. Icons supplement labels for domain concepts and all icon-only controls have
    accessible names.
12. Forced-colors, reduced-motion, zoom, and keyboard interaction are verified.
13. One automated inventory test rejects unknown tokens, raw emoji, arbitrary
    inline SVG, and direct third-party imports.
14. Visual regression snapshots prove consistent alignment and state behavior.
15. The canonical registry and SVG set receive independent design review before
    UI migration.

## 10. Rejection List

The Workbench must reject:

- decorative icons;
- emoji or emoji-like pictograms;
- mixed icon families;
- arbitrary per-screen SVG;
- inconsistent stroke, terminals, radii, or optical size;
- 3D, skeuomorphic, glossy, gradient, or shadowed icons;
- duotone used as decoration;
- corporate SaaS packs adopted without semantic governance;
- anthropomorphic brains, eyes, faces, or magic metaphors for reasoning;
- sparkles for AI, insight, or Watson;
- generic charts used to mean evidence;
- warning triangles used for contradiction by default;
- checkmarks that ambiguously mean accepted, verified, completed, or correct;
- arrows that imply causality without an accepted Relationship;
- color-only status;
- fill used merely to make an icon “stronger”;
- icons inside every heading, chip, or card;
- visually noisy miniature illustrations;
- badge stacking that creates unreadable compound marks;
- animation that suggests authority, urgency, or intelligence;
- unknown-token fallback glyphs;
- direct runtime dependency on a third-party catalogue.

## 11. Roadmap

This is sequencing for a future iconography initiative, not authorization to
apply it now.

### Stage 1 — Semantic registry

Freeze the token vocabulary, collisions, aliases, and accessible labels. Verify
it against all canonical models and actual UI usage.

### Stage 2 — Construction study

Produce optical studies at 16/20/24 px for one outline grammar. Compare
candidate primitives without adding them to production.

### Stage 3 — Foundation set

Design and review the four foundational model marks:

```text
Current Situation
Artifact
Relationship
Operational Memory
```

### Stage 4 — Operational vocabulary

Complete Evidence, Reasoning, Work, and Navigation sets. Test confusing pairs
before testing visual preference.

### Stage 5 — Accessibility and state validation

Validate labels, icon-only controls, forced colors, contrast, zoom, state
distinction, and optical alignment.

### Stage 6 — Migration proposal

Prepare a separate implementation proposal that maps each existing usage to a
canonical token, removes emoji and unmanaged SVG, and defines regression tests.
UI migration requires its own approval.

## 12. Production Readiness

Current readiness: **25%**.

What exists:

- a usable outline direction in the Dock;
- a documented preference for 24 px outline geometry;
- accessible labels on Dock links;
- awareness that icons must supplement text.

What is missing:

- a semantic registry;
- owned model glyphs;
- one production family;
- optical masters and size testing;
- state rules in implementation;
- automated enforcement;
- removal of emoji and semantic collisions.

### Final verdict

```text
Not ready for production as a canonical iconography system.

Recommended path:
Governed custom Canonical Icon Set built from an adapted outline foundation,
followed by complete replacement of the current mixed operational iconography.
```

The present Dock SVGs may inform the future set but are not automatically
canonical. The emoji layer must be fully replaced in a separately approved Apply.
