# M6.6 — Canonical Component Model

## Status

```text
Approved for M6 dependency use
Milestone M6
```

## Authority

This document is the single source of truth for platform-independent Canonical
Components. It defines component identity, ownership, lifecycle, taxonomy,
admissible Rendering Node structures, composition, containment, reuse,
replacement, the Platform Component Library boundary, and conformance.

A Canonical Component is a reusable architectural composition of Rendering
Nodes that encapsulates one professional presentation responsibility. It is not
a platform widget, framework component, template, styled object, or runtime
implementation.

# 1. Purpose

Rendering Nodes provide canonical presentation structure. Semantic Tokens
preserve meaning, and Presentation State describes each node's current
presentation condition. These contracts do not by themselves define which
recurring Rendering Node compositions are stable architectural units.

The Canonical Component Model establishes those reusable units:

```text
Validated Rendering Tree subgraph
        +
Resolved Semantic Token Sets
        +
Presentation State contracts
        +
One Canonical Component Definition
        ↓
Validated Canonical Component Instance
        ↓
Platform Component Library
```

The model prevents platform libraries from becoming architectural authorities,
prevents repeated structures from drifting semantically, and permits reuse
without copying canonical identity or inventing component-owned meaning.

# 2. Component Principles

1. **One Professional Responsibility.** Every Canonical Component encapsulates
   exactly one bounded presentation responsibility.
2. **Nodes Remain Canonical Structure.** Components consume Rendering Nodes and
   never replace, mutate, or redefine them.
3. **Semantics Remain Upstream.** DSR roles and STC obligations remain the only
   sources of component meaning.
4. **State Remains Node-Bound.** A component has no competing presentation-state
   machine; PSD state remains attached to Rendering Nodes.
5. **Composition, Not Widget.** A Canonical Component is an architectural
   contract over an admissible node subgraph, not an implementation object.
6. **Reuse Without Duplication.** Reuse applies a stable definition to distinct
   node occurrences without copying domain truth or Rendering Node identity.
7. **Explicit Structure.** Required members, optional members, cardinality,
   ordering, nesting, references, and fallback are declared.
8. **Deterministic Admission.** Equivalent definition, tree subgraph, token
   sets, and state contracts produce the same conformance result.
9. **No Hidden Meaning.** A component name, category, nesting level, or library
   mapping adds no professional semantics.
10. **No Hidden State.** Component-level convenience cannot become canonical or
    presentation state.
11. **Versioned Replacement.** Compatible revision preserves component identity;
    changed professional responsibility requires a new identity.
12. **Adapter Neutral.** One Canonical Component responsibility survives
    materially different platform implementations.
13. **Accessible Composition.** Member roles, semantic order, state, action,
    feedback, and relationships remain recoverable.
14. **No Implicit Authority.** Reuse, containment, prominence, or availability
    grants no authority.
15. **Projection Only.** Component definition and instantiation create no domain
    truth, canonical event, lifecycle progression, or information residency.

# 3. Canonical Component Contract

## 3.1 Definition

A Canonical Component Definition is a versioned architectural contract that
declares:

- one component identity and category;
- one professional presentation responsibility;
- one admissible connected Rendering Node subgraph;
- one anchor node kind and role;
- required and optional member contracts;
- composition, nesting, token, state, continuity, and fallback obligations;
- adapter-equivalence and prohibited implications.

A Canonical Component Instance is a generation-scoped validation that a specific
Rendering Tree subgraph satisfies one active definition.

The component is not inserted into the Rendering Tree. Nodes retain their
original identities, parentage, order, cross-references, tokens, and states.

## 3.2 Ownership

Canonical Component Model owns only:

- component identity, category, definition, and lifecycle;
- professional presentation responsibility boundaries;
- admissible Rendering Node subgraph contracts;
- component composition, containment, reuse, and replacement rules;
- component-instance validation;
- the Platform Component Library boundary;
- component conformance.

Ownership remains outside this model for:

| Concern | Owner |
|---|---|
| Professional truth, authority, and lifecycle | Canonical Management Model and owning source models |
| Design Object identity and relationships | Canonical Design Object Model |
| Semantic Roles and responsibility meaning | Canonical Design Semantics |
| Rendering Tree, Node identity, parentage, order, and replacement | Canonical Rendering Model |
| Semantic Token identity, meaning, and resolution | Semantic Token Architecture |
| Presentation State dimensions and presentation state transitions | Presentation State Model |
| Information residency | Canonical Information Architecture |
| Navigation and professional Current Focus | Operational Navigation and Navigation Governance |
| Platform implementation units and technical composition | Platform Component Library |

## 3.3 Component definition descriptor

Every Canonical Component Definition declares:

| Field | Requirement |
|---|---|
| **Component ID** | Stable canonical component identity. |
| **Version** | Monotonic definition revision with compatibility declaration. |
| **Category** | Exactly one CCT-01–CCT-09 category. |
| **Professional responsibility** | One bounded presentation responsibility. |
| **Anchor contract** | One required RN kind, DSR role, and semantic basis. |
| **Member contracts** | Required and optional RN kinds, roles, relationships, and cardinality. |
| **Admissible subgraph** | Parentage, semantic order, cross-reference, and nesting constraints. |
| **Token obligations** | Required STC categories and distinctions for every member. |
| **State obligations** | Applicable PSD dimensions and cross-node consistency; no new state. |
| **Context and continuity** | Identity, origin, return, scope, and generation requirements. |
| **Configuration points** | Source-bound choices that cannot change professional responsibility. |
| **Fallback contract** | Approved reduced composition or explicit failure. |
| **Reuse contract** | Contexts in which the same definition remains semantically equivalent. |
| **Replacement contract** | Compatible successor conditions and migration obligations. |
| **Adapter obligation** | Responsibility and member distinctions a platform library must preserve. |
| **Prohibited implications** | Meanings neither composition nor implementation may add. |
| **Lifecycle condition** | Proposed, Registered, Active, Deprecated, or Retired. |

Configuration points are architectural bindings, not implementation properties
or APIs.

## 3.4 Component instance descriptor

Every validated instance declares:

| Field | Requirement |
|---|---|
| **Instance ID** | Tree-generation-scoped component occurrence identity. |
| **Definition reference** | Exact Component ID and active version. |
| **Tree generation** | Current validated Rendering Tree revision. |
| **Anchor Node** | Exact anchor RN occurrence. |
| **Member Nodes** | Exact required and optional RN occurrences. |
| **Nested instances** | Explicit compatible child component instances. |
| **Token-set references** | Exact resolved token set for every member. |
| **State references** | Exact current PSD snapshots or declared applicability. |
| **Conformance result** | Complete, explicitly degraded, or invalid. |
| **Replacement relation** | Prior compatible instance replaced where applicable. |

Instance identity is not canonical subject identity, Rendering Node identity, or
platform component identity.

# 4. Component Lifecycle

## 4.1 Definition lifecycle

Component definition lifecycle is governance metadata, not a Matter or domain
lifecycle:

```text
Proposed
    ↓ Architecture Review
Registered
    ↓ Approved use
Active
    ↓ Compatible successor
Deprecated
    ↓ Migration complete
Retired
```

| Condition | Meaning | Use rule |
|---|---|---|
| **Proposed** | Candidate definition under review. | Cannot produce a conforming current instance. |
| **Registered** | Identity, category, responsibility, and structure are accepted. | May prepare for approved activation. |
| **Active** | Current definition version for new instance validation. | May validate compatible tree subgraphs. |
| **Deprecated** | Superseded but still interpretable during migration. | No new instance begins with this version. |
| **Retired** | No current instance may depend on this version. | Historical governance reference only. |

## 4.2 Instance lifecycle

```text
Eligible Subgraph
    ↓
Bound
    ↓
Validated
    ↓
Current
    ↓ tree or definition replacement
Obsolete

Binding or validation failure
    ↓
Invalid — Never Current
```

An instance cannot outlive its Rendering Tree generation. Instance lifecycle
creates no Memory Event and changes no upstream contract.

# 5. Canonical Component Taxonomy

## 5.1 Admission rule

A component category exists only when it:

- owns a distinct professional presentation responsibility;
- has a stable anchor Rendering Node kind;
- requires a reusable multi-node or node-plus-obligation composition;
- cannot be expressed by another category without changing responsibility;
- has admissible structure across materially different adapters;
- introduces no new semantic or presentation state.

## 5.2 Component categories

| ID | Category | Professional responsibility | Required anchor and members | Admissible optional members | Forbidden structure |
|---|---|---|---|---|---|
| **CCT-01** | **Surface Context Assembly** | Present one active adapter-addressable professional context. | RN-01 anchor; at least one RN-02. | RN-03, RN-07, RN-11 and compatible nested instances. | Second RN-01; alternative Context Envelope; domain Workspace ownership. |
| **CCT-02** | **Information Responsibility Assembly** | Present one bounded IA responsibility or compatible subset. | RN-02 anchor; at least one compatible RN-03, RN-05, RN-06, or RN-07. | RN-04, RN-08, RN-09, RN-10 and nested compatible instances. | New residency, route, page, or local truth. |
| **CCT-03** | **Semantic Composition Assembly** | Preserve one declared semantic whole and member obligations. | RN-03 anchor; at least one RN-04 or two compatible member nodes. | Any RN kind permitted by the owning DO-03/DSR-03 contract except RN-01. | Layout geometry, domain aggregation, cyclic membership. |
| **CCT-04** | **Subject Presentation Assembly** | Present one identified subject in exactly one IA representation role. | RN-05 anchor; at least one related RN-08, RN-09, RN-10, or typed subject reference. | Compatible composition, action, state, feedback, and nested subject-reference instances. | Mixed subject identity, copied truth, multiple primary representation roles. |
| **CCT-05** | **Set Presentation Assembly** | Present one attributable set and its organizing basis. | RN-06 anchor; member RN-05 occurrences or an explicit empty/failed condition through RN-09/RN-10. | RN-03, RN-04, RN-08, RN-09, RN-10 and compatible member instances. | Domain Collection ownership, inferred Relationship, unexplained order. |
| **CCT-06** | **Navigation Context Assembly** | Present canonical orientation, destination, origin, interruption, suspension, or return. | RN-07 anchor; at least one related RN-08, RN-09, RN-10, or typed navigation reference. | Compatible subject references, state, feedback, and transient-support reference. | Navigation creation, lifecycle progression, professional Focus ownership. |
| **CCT-07** | **Professional Action Assembly** | Present one OI professional action with precondition, consequence, and feedback boundary. | RN-08 anchor; at least one RN-09 or RN-10 associated with the same interaction. | Supporting subject reference, continuity token, and recovery-action instance. | Multiple OI intents, authority grant, hidden commitment, input mechanic. |
| **CCT-08** | **Interaction Feedback Assembly** | Present one attributable interaction condition and next valid path. | RN-10 anchor; related RN-08 or RN-09 tied to the same operation. | Recovery action, subject reference, state explanation, and nested composition. | Unscoped feedback, success without event evidence, rewritten history. |
| **CCT-09** | **Transient Support Assembly** | Present temporary inspection, comparison, explanation, choice, feedback, or recovery while preserving origin and return. | RN-11 anchor; at least one compatible RN-03, RN-05, RN-06, RN-08, or RN-10. | RN-04, RN-07, RN-09 and compatible nested instances. | Permanent context, second Focus, hidden origin, independent information space. |

RN-04 Place Node and RN-09 State Node are supporting nodes, not independent
component anchors. A lone Rendering Node remains valid architecture but is not a
Canonical Component.

# 6. Admissible Rendering Node Structure

## 6.1 Connected-subgraph rule

A component instance consumes one connected Rendering Tree subgraph or one
anchor subtree plus explicit typed cross-references required by its definition.
It must preserve:

- original RN identities and kinds;
- original parentage and semantic order;
- DSR role and canonical basis;
- STC token sets and distinctions;
- PSD applicability and current state;
- typed cross-reference semantics;
- tree-generation boundary.

Membership creates no new parent-child relationship in the Rendering Tree.

## 6.2 Anchor rule

1. Every component instance has exactly one anchor node.
2. The anchor kind matches the component category.
3. The anchor's DSR role supplies the component responsibility basis.
4. An anchor may itself be a member of one explicitly containing component.
5. Anchor status grants no authority, priority, Focus, or canonical ownership.

## 6.3 Membership rule

1. Every required member is present exactly within declared cardinality.
2. Optional members appear only when their upstream contract and context apply.
3. Every direct member has one declared responsibility inside the component.
4. A Rendering Node has at most one direct component membership at the same
   composition level.
5. Other components may reference the node without copying or reparenting it.
6. Member omission requires an approved fallback or makes the instance invalid.
7. Membership never changes Semantic Role, token, or state.

## 6.4 Component nesting

Canonical Components may compose compatible child components when:

- the parent definition declares a component place and accepted categories;
- the child anchor is an admissible member node;
- parent and child responsibilities remain independently inspectable;
- the child instance retains identity, version, members, tokens, and states;
- the dependency graph is acyclic;
- nesting creates no domain containment or information residency.

After validation, the Rendering Tree remains the structural authority. Component
nesting is a reusable-contract relationship only.

# 7. Deterministic Component Composition

## 7.1 Input contract

Component composition accepts:

- one current validated Rendering Tree generation;
- exact candidate RN subgraph and cross-references;
- resolved Semantic Token Sets for every member;
- applicable Presentation State contracts;
- active Canonical Component registry revision;
- professional context and adapter-capability declaration;
- prior compatible component instance where replacement applies.

It cannot query alternate sources to reinterpret Rendering Nodes.

## 7.2 Composition pipeline

```text
Identify Candidate Anchor and Responsibility
        ↓
Select Exactly One Eligible Active Definition
        ↓
Bind Required and Optional Members
        ↓
Validate Parentage, Order, References, and Cardinality
        ↓
Validate Token and Presentation State Obligations
        ↓
Validate Nested Component Dependencies
        ↓
Evaluate Completeness and Fallback
        ↓
Publish Valid Component Instance
```

Ambiguous definition selection is invalid. Registry order, declaration order,
frequency of reuse, and platform preference cannot choose a definition.

## 7.3 Deterministic result

Equivalent definition registry, Rendering Tree generation, candidate subgraph,
token sets, state contracts, context, and capability declaration produce the
same:

- component eligibility;
- selected definition identity and version;
- anchor and member bindings;
- nested component relationships;
- completeness and fallback result;
- adapter obligations.

The result is:

```text
Complete Canonical Component Instance
```

```text
Explicitly Degraded Canonical Component Instance
```

or:

```text
Invalid — No Platform Library Handoff
```

# 8. Reuse Rules

1. Reuse applies one active definition to multiple distinct Rendering Tree
   subgraphs.
2. Each reuse creates a distinct generation-scoped instance identity.
3. Reuse never copies canonical subject identity or source-owned state.
4. The same definition is reusable only when professional responsibility,
   anchor role, member obligations, and prohibited implications remain
   equivalent.
5. Context-specific data binds through existing RN, STC, and PSD contracts, not
   component-owned properties.
6. Optional member combinations are allowed only when explicitly declared.
7. A configuration point cannot change component category or responsibility.
8. Reuse across adapters preserves the same component definition and
   responsibility.
9. A platform implementation's reuse does not prove canonical reuse.
10. Similar appearance, implementation convenience, or shared technical code is
    insufficient for canonical component identity.

# 9. Replacement Rules

## 9.1 Definition replacement

A successor version may preserve Component ID only when it:

- preserves category and professional responsibility;
- preserves anchor RN/DSR contract;
- preserves all previously required semantic obligations;
- changes no canonical meaning or authority;
- provides an explicit compatibility and migration contract;
- keeps conforming prior inputs valid or explicitly classifies incompatibility.

A changed category, responsibility, anchor meaning, or required semantic
obligation requires a new Component ID.

## 9.2 Instance replacement

```text
Current valid component instance
        ↓
Validate successor definition and current tree subgraph
        ↓
Build complete successor instance
        ↓
Atomic component-instance replacement
        ↓
Prior instance becomes obsolete
```

Replacement:

- does not replace or mutate Rendering Nodes;
- does not alter token or presentation-state snapshots;
- creates no canonical event;
- cannot expose a partially validated instance;
- preserves component continuity only when identity and compatibility rules
  pass;
- fails without replacing the prior valid instance.

# 10. Platform Component Library Boundary

## 10.1 Boundary contract

```text
Canonical Component Model
  owns responsibility, admissible structure, reuse, and replacement
        ↓
Validated Canonical Component Definition and Instance
        ↓
Platform Component Library
  owns technology-specific implementation composition
```

The validated component contract is the only handoff. A platform library cannot
reinterpret RN, DSR, STC, or PSD sources.

## 10.2 Canonical side responsibilities

The Canonical Component Model must:

- provide stable component identity, version, category, and responsibility;
- identify exact anchor, members, relationships, tokens, and state obligations;
- validate composition and nesting deterministically;
- state reuse, compatibility, replacement, fallback, and prohibited
  implications;
- expose all semantic and accessible distinctions the library must preserve;
- reject ambiguous, incomplete, cyclic, or incompatible instances;
- remain neutral to platform implementation structure.

It must not:

- select implementation primitives;
- prescribe technical composition or APIs;
- define platform component identity;
- use library constraints to change canonical responsibility;
- depend on implementation internals.

## 10.3 Platform library responsibilities

A Platform Component Library may implement a Canonical Component through one or
more technical units. It must:

- map implementation output to the exact Component ID and version;
- preserve component responsibility, anchor, members, semantic order, tokens,
  states, relationships, fallback, and continuity;
- retain independent accessibility of nested component responsibilities;
- declare implementation coverage and unsupported obligations;
- reject a contract it cannot implement conformantly.

It must not:

- invent or merge professional responsibilities;
- add, remove, reparent, or reinterpret Rendering Nodes;
- introduce component-owned semantic or canonical state;
- infer authority, priority, professional Focus, or interaction commitment;
- make technical containment appear as domain containment;
- define a competing Canonical Component taxonomy.

## 10.4 Cardinality independence

There is no required one-to-one relationship between a Canonical Component and
a platform implementation unit. One canonical responsibility may require
several implementation units; one technical unit may support several canonical
instances only when every responsibility, identity, state, and semantic
obligation remains independently recoverable.

This document defines no Platform Component Library implementation.

8. Components never replace or redefine Rendering Nodes.
9. Components never change DSR roles.
10. Components never change STC identities, meanings, or resolved sets.
11. Components never create a competing PSD state.
12. Every required member satisfies declared kind, role, relationship, and
    cardinality.
13. Optional members appear only under explicit applicability.
14. Member omission uses approved fallback or invalidates the instance.
15. Membership creates no Rendering Tree parentage.
16. Component nesting is explicit and acyclic.
17. Nesting creates no domain containment or information residency.
18. Anchor status creates no authority, priority, Focus, or ownership.
19. RN-04 and RN-09 are not independent component anchors.
20. A lone Rendering Node is not automatically a component.

25. Configuration cannot change category or professional responsibility.

# 12. Conformance Criteria

A Canonical Component realization conforms only when:

1. every definition satisfies the component descriptor;
2. every active component belongs to CCT-01–CCT-09;
3. every category has one bounded professional responsibility;
4. every instance uses one eligible anchor and complete admissible subgraph;
5. Rendering Node parentage, order, cross-references, identity, and generation
   remain unchanged;
6. token and state obligations remain upstream-owned;
7. composition and nesting are deterministic and acyclic;
8. reuse preserves responsibility without copying truth;
9. replacement preserves compatible identity or creates a new Component ID;
10. degraded and invalid outcomes fail safely;
11. platform implementation preserves all canonical responsibilities and
    distinctions;
12. canonical and platform component identities remain separate;
13. accessibility equivalence is demonstrable;
14. no implementation vocabulary enters the canonical component contract;
15. all 42 invariants pass.

## Deterministic verdict

```text
Pass
```

when every applicable criterion and invariant is satisfied;

```text
Fail
```

when a definition, instance, composition, reuse, replacement, or platform
mapping adds, removes, duplicates, hides, or reinterprets canonical
responsibility;

```text
Not Applicable
```

only for platform infrastructure that neither implements nor fulfills a
Canonical Component responsibility.

# 13. Completion Criteria

Canonical Component Model is complete when:

1. component purpose, ownership, descriptors, lifecycles, and responsibilities
   are explicit;
2. CCT-01–CCT-09 are exhaustive and mutually bounded;
3. all admissible Rendering Node structures are defined;
4. composition, containment, nesting, reuse, and replacement rules are
   deterministic;
5. RN, DSR, STC, and PSD contracts remain immutable and source-owned;
6. components create no competing semantic or state model;
7. Platform Component Library responsibilities are mutually exclusive from
   canonical ownership;
8. platform implementation cardinality may vary without changing canonical
   responsibility;
9. conformance produces an unambiguous verdict;
10. Architecture Review approves the document for dependency use.
