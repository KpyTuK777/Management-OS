# M9 Investigation-first Live Server Materialization Plan

## Plan identity

- Basis: fixed direction record, readiness inventory, and bounded MVP/shared-primitive definition
- Plan state: PREPARED FOR INDEPENDENT REVIEW
- Execution state: NOT AUTHORIZED
- Target: broad runnable local prototype inspectable through Live Server
- Deployment: NOT INCLUDED

## Materialization target

The target is one honest, runnable Management OS experience in which Serhii can traverse a bounded Investigation without reading Git or Markdown. It maximizes visible, already supported Product meaning and labels incomplete behavior explicitly.

Every visible capability must carry one of these implementation-state meanings where ambiguity is possible:

- `WORKING` — the bounded behavior operates and has passed its stage tests;
- `READ-ONLY` — information is inspectable but cannot be changed;
- `PARTIAL` — only the stated subset is implemented;
- `PLACEHOLDER` — spatial or navigational reservation with no claim of function;
- `NOT AVAILABLE` — known Product meaning is intentionally unavailable;
- `REQUIRES FUTURE AUTHORITY` — behavior would cross the fixed authority envelope.

A disabled control must explain its boundary. It may not simulate success.

## Technology sufficiency assessment

The existing static HTML/CSS/JavaScript stack is sufficient for this bounded local prototype because it already demonstrates:

- direct Live Server operation;
- application and workbench shells;
- browser-local state;
- Artifact, Relationship, Operational Memory, and authority-policy modules;
- an Investigation-oriented runnable page;
- Reader navigation, inspection, Working Set, responsive behavior, and browser tests.

Complexity alone does not justify migration. No framework, dependency, API, persistence technology, or deployment topology must be selected to execute the bounded plan. Native modules and existing local storage mechanics are adequate provided the execution review prevents legacy implementation from silently defining Product meaning.

A technology reconsideration becomes necessary only if an authorized stage demonstrates a concrete unmet need such as tested state complexity that existing modules cannot preserve safely, accessibility behavior impossible with the current structure, or an authorized integration/runtime requirement. That event is a stop condition and requires a neutral technology decision; no migration is pre-authorized.

## File-scope derivation rule

A future positive Decision may permit only files demonstrably necessary for the bounded runnable prototype:

- existing application entry, shell, styles, and JavaScript modules;
- new Investigation-specific HTML/CSS/JavaScript modules where separation preserves fixed meaning;
- bounded local sample-data fixtures explicitly labeled non-canonical and non-historical;
- browser/model tests and implementation/review reports;
- Reader implementation files only during Stage 8 reconciliation and only for shared behavior proven in the fixed definition.

Canonical, architecture, governance, research, and historical artifacts remain read-only during implementation. Dependencies, build tooling, external integrations, and deployment files are excluded unless a later Decision separately authorizes them.

## Autonomous execution envelope proposed for consideration

A positive implementation Decision may authorize automatic continuation from one stage to the next without a new human Decision when all stage tests pass, independent review has no blocking findings, corrections remain unambiguous and inside scope, and no stop condition is triggered.

### Stage 1 — Shared shell and navigation consolidation

- Purpose: establish Investigation as primary destination and Reader as supporting module within one coherent shell.
- Included: application shell, global navigation, location identity, module boundary, return paths, state labels.
- Change classes: HTML/CSS/JS consolidation and browser tests; no domain data mutation.
- Tests: direct entry, keyboard navigation, current-location indication, narrow viewport, Reader route preservation.
- Review gate: Investigation is visually and semantically primary; Reader remains available but subordinate.
- Continuation gate: no navigation destination claims unavailable capability as working.
- Stop: shell consolidation requires a new product zone or changes canonical navigation meaning.
- Exclusions: authentication, production routing, deployment.

### Stage 2 — Investigation structural workspace

- Purpose: materialize one Investigation envelope and stable workbench geometry.
- Included: Investigation identity/status/purpose, Current Situation region, material region, Working Set, Inspector reservation, current focus, return path.
- Change classes: bounded UI structure, local state skeleton, sample fixture, tests.
- Tests: open/reset one Investigation, focus persistence, semantic headings, responsive composition, no Reader-state contamination.
- Review gate: one Investigation can be understood without repository vocabulary.
- Continuation gate: placeholders and working regions are visibly distinct.
- Stop: a new Investigation lifecycle or Matter state is required.
- Exclusions: external intake, AI, Decision recording.

### Stage 3 — Current Situation and Evidence handling

- Purpose: let the manager understand and inspect source-bound operational material.
- Included: summary, symptoms, context, known material, uncertainty, missing Evidence, bounded local/manual intake, provenance, attribution, Evidence status, focused inspection.
- Change classes: local data/view logic and tests; fixed semantics only.
- Tests: source/provenance inspection, Evidence/material distinction, missing-source state, no fact promotion, visible prior Current Situation revision.
- Review gate: plain-language comprehension preserves precise meaning and traceability.
- Continuation gate: no local sample is presented as a real organizational record.
- Stop: actual external acquisition, new classification, or uncontracted mutation is required.
- Exclusions: connectors, uploads requiring new security architecture, source mutation.

### Stage 4 — Working Set, unknowns, and contradictions

- Purpose: support temporary relevance and unresolved reasoning without turning selection into truth.
- Included: add/remove Working Set, inspect set, explicit unknowns, unanswered questions, conflicting material, visible unresolved state.
- Change classes: bounded state transitions, semantic presentation, tests.
- Tests: Working Set changes do not alter Evidence status; contradiction remains unresolved; empty/degraded recovery.
- Review gate: selection, acceptance, and truth are visually and behaviorally distinct.
- Continuation gate: no automatic conflict resolution or hidden state loss.
- Stop: a new unknown/contradiction lifecycle must be invented.
- Exclusions: automatic adjudication, organizational task creation.

### Stage 5 — Hypotheses and bounded Relationships

- Purpose: develop provisional interpretations and trace their evidentiary basis.
- Included: local human-created hypotheses, provisional status, supporting/contradicting Evidence links, fixed relation types, inspectable relationship list/map.
- Change classes: bounded domain-view logic using fixed Artifact/Relationship semantics, tests.
- Tests: hypothesis never renders as fact; acceptance is human-owned; unsupported relation types rejected; source trace remains intact.
- Review gate: no cinematic detective-board metaphor and no unrestricted graph ontology.
- Continuation gate: existing automatic-generation code is disabled or clearly demo-only unless separately authorized.
- Stop: new ontology, AI inference, or Product disposition is required.
- Exclusions: autonomous hypothesis generation, causal proof, Root Cause.

### Stage 6 — Timeline and Inspector integration

- Purpose: integrate focused inspection with honest temporal context.
- Included: full Inspector continuity; read-only/static timeline for supported representative events; event-time versus record/publication-time distinction; uncertain and missing time.
- Change classes: presentation/state integration and tests only.
- Tests: dual-time labels, uncertain ordering, source linkage, focus return, keyboard Inspector journey.
- Review gate: timeline is explicitly `READ-ONLY` or `PARTIAL`; no invented chronology.
- Continuation gate: no timeline editing or ordering behavior beyond the fixed contract.
- Stop: interactive timeline authoring becomes necessary.
- Exclusions: inferred dates, full temporal editor.

### Stage 7 — Comprehension, accessibility, and degraded-state completion

- Purpose: make the bounded experience suitable for direct Product Owner evaluation.
- Included: Ukrainian primary language, progressive disclosure, responsive completion, keyboard/focus behavior, accessible names/statuses, empty/loading/degraded/unavailable/error states, content-stress review.
- Change classes: presentation, interaction feedback, tests, screenshots, bounded corrections.
- Tests: complete browser journey; keyboard-only journey; narrow and wide viewport; English-string audit; state-distinction audit; contrast and focus visibility checks.
- Review gate: primary feedback can concern Product experience rather than obvious comprehension/accessibility defects.
- Continuation gate: no plain-language text alters canonical meaning.
- Stop: terminology requires a material semantic Decision or accessibility requires architecture expansion.
- Exclusions: new visual canon, production certification.

### Stage 8 — Supporting Historical Reader reconciliation

- Purpose: prevent shared shell, inspection, traceability, responsive, and accessibility behavior from drifting while preserving Reader-specific authority and Wave 1.5 work.
- Included: proven shared primitives only; module role/navigation; no historical-content integration unless separately authorized.
- Change classes: bounded Reader implementation reconciliation and regression tests only if explicitly included by the positive Decision.
- Tests: Reader historical immutability; Replay unavailable; Wave 1.5 preparation preserved; Reader journey regression; shared-state isolation.
- Review gate: Reader remains supporting and its fixed semantics are unchanged.
- Continuation gate: no Reader correction exceeds separately fixed authority.
- Stop: full Wave 2, historical rewriting, or new Reader semantics are implicated.
- Exclusions: full Wave 2, Replay, H3 validation, reflection finalization.

## Cross-stage verification obligations

Each stage must produce:

1. precheck of fixed HEAD ancestry and clean expected worktree;
2. exact changed-file inventory;
3. traceability from behavior to inventory row and fixed source;
4. automated tests proportional to behavior;
5. principal screenshots where visual or responsive behavior changes;
6. logically separate critical review with `BLOCKING`, `NON-BLOCKING`, or `NONE` findings;
7. correction of only unambiguous in-scope findings;
8. repeated complete review after correction;
9. one bounded implementation commit and separate review evidence where governance requires it;
10. clean continuation gate.

## Global stop conditions

Stop immediately if work requires:

- new or changed canonical, Product, Interaction, or Engineering meaning;
- a materially ambiguous interaction choice;
- new organizational or governance authority;
- ROADMAP/BACKLOG modification or repository transition not separately authorized;
- external integration, dependency change, framework migration, or technology selection;
- production persistence, authentication, security, infrastructure, or deployment;
- autonomous AI behavior or source mutation;
- Replay, H3 validation, Root Cause, causal proof, metrics, KPIs, or experiments;
- historical artifact mutation;
- unexpected repository state or unreliable verification.

## Plan completion condition

The plan is complete only when the runnable prototype is honest about every working, partial, read-only, placeholder, unavailable, and future-authority boundary; all included behavior is traceable; the Reader remains supporting; and no implementation-created choice has become new Product meaning.

This plan is a proposal. It does not authorize its own execution.
