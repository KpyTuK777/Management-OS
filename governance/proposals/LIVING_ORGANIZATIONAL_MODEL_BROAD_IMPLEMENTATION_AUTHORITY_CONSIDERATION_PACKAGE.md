## Proposed human outcome

Materialize a substantially working, organization-first Management OS in the current Live Server-compatible stack so the Product Owner can develop the Product increasingly through direct experiential review.

The experience begins:

`Management OS → Organization → Living Organizational Model → Investigation or Improvement when intentionally chosen`.

Investigation remains preserved and independently governed. It becomes a work mode within the larger Product rather than its conceptual root.

## Proposed authorized execution

If option A is selected, one autonomous cycle may implement, verify, review, and correct:

- honest empty first start and first organization creation;
- progressive Organization Constructor;
- functional Organization Map with bounded lenses, search-to-focus, selection, Inspector, qualification states, and Workbench navigation;
- Department and Role Workbenches;
- people-free modelling of departments, roles, processes, systems, SOPs, KPIs/measures, reports, meetings, responsibilities, dependencies, flows, associations, and interdepartmental interactions;
- Input → Process → Output → Result process comprehension with progressive detail;
- contextual Investigation creation without promotion and non-destructive reconciliation of existing Investigation data;
- bounded Improvement identity/context/proposed-change subset with current/proposed separation and honest unavailable lifecycle;
- permission-aware Operational Memory references and preservation of the Historical Walkthrough Reader;
- organization search, bounded traversal, explicit partial results, versioned local persistence, migrations, recovery, corrupted-state handling, and degraded states;
- organization-first navigation, shared Inspector/dialog foundations, Ukrainian human-first interface, visual continuity, accessibility baseline, viewport-first desktop/laptop composition, tablet degradation, and 390 px rights-preserving support;
- necessary unit, contract, policy, migration, browser, responsive, accessibility, stress, recovery, and regression tests plus implementation evidence;
- independent implementation review, bounded defect correction, repeat verification, and final experiential handoff.

The execution may make ordinary technical and visual choices within the adopted architecture without component-by-component human approval.

## Partial capability boundary

- Named-person runtime, occupancy, Person Workbench data, person search, real InformationContribution activation, and people-data export/import remain unavailable.
- Future-compatible type boundaries and denial tests are permitted, but no person records, shipped fixtures, indexes, counts, navigation, or projections.
- Operational Memory is limited to permission-aware references/read-only history already available.
- Improvement is limited to identity, context, deliberate-change framing, and proposed state separate from current state.
- Legacy Improvement data remains quarantined and cannot migrate into the adopted mode in this cycle.

## Technology, files, and dependencies

The authorized default remains semantic HTML, existing CSS, modular plain JavaScript, browser APIs, browser-local persistence behind the adopted adapter, and direct-browser verification.

No framework, build system, backend, database, package manager, external integration, AI runtime, deployment, or new dependency is authorized.

Permitted writes are purpose-bounded to necessary root application entry points, `css/`, `js/`, `tests/`, bounded people-free test fixtures, `governance/evidence/`, implementation review/correction records, and necessary `README.md` run instructions. Every changed file must be classified and justified in execution evidence. Adopted authority artifacts, `ROADMAP.md`, `BACKLOG.md`, unrelated cleanup, generated profiles, and machine-specific files remain protected.

## Persistence and preservation obligations

The execution must implement adapter-bound schema versions, immutable generations, checksums, commit markers, read-back verification, deterministic recovery, retained prior generation, copy-on-write/restartable migrations, capacity checks, quarantine, and disposable indexes.

Existing Investigation stores remain untouched for the whole cycle. Migrated activation requires preservation comparison of identities, Situation revisions, materials/statuses, Hypothesis relationships, Working Set, timeline, context, and timestamps. Any mismatch falls back to compatible original state. Export/import is excluded.

The generated local `workspaceId` is partitioning metadata only; it is not authentication, Account/Membership, sharing, or human authority.

## Required verification and review

Completion requires real `index.html` browser journeys, not static inspection or a smoke harness alone. Evidence records browser/version, viewport, storage precondition, journey, result, screenshots where applicable, console errors, and runtime errors.

Required gates include empty start; organization/department/relationship/process creation; Map and Workbench navigation; system/SOP/KPI links; Investigation non-promotion; Improvement separation; persistence/reload; v1 migration preservation; corruption/recovery; identity, relationship, temporal, privacy and restricted-absence invariants; keyboard/modal/accessibility behavior; repeated interaction stress; Historical Walkthrough preservation; desktop composition; tablet behavior; and 390 px overflow/orientation/correction/context entry.

After implementation and correction, an independent review and repeat review must confirm the authorized scope, non-leakage, preservation, recovery, responsive/accessibility behavior, and clean repository. Experiential usefulness remains the Product Owner's later judgment.

## Stop conditions

Execution stops before any need for new or changed canonical, Product, Interaction, Engineering, or privacy meaning; sensitive/named-person capability; framework/build-system/backend/database; new dependency; integration; deployment; Watson/AI execution; repository transition; ROADMAP/BACKLOG change; destructive migration; Replay; H3; Root Cause; or causal proof.

Ordinary in-scope implementation choices are delegated and do not require a stop.

## Completion condition

The cycle ends when either:

- the maximum authorized coherent implementation is Live Server-ready, verified, reviewed, corrected, committed, clean, and handed off with evidence plus intentionally unavailable/deferred capabilities; or
- a genuine stop condition is precisely evidenced.

## Human Decision options

### A — Authorize

Authorize the broad bounded implementation execution exactly as defined by the fixed consideration set and controlled by the correction supplement. This permits application code, UI, tests, evidence, bounded refactoring, and implementation review/correction only within the contract.

### B — Revise

Return the package for bounded revision, identifying the exact capability, file, technology, verification, autonomy, preservation, or stop-condition clauses to change. Implementation remains unauthorized.

### C — Decline or defer

Do not authorize execution now. Preserve the adopted architecture and current implementation unchanged.

## Exact indispensable human Decision

> Should Management OS authorize the reviewed broad bounded Living Organizational Model implementation execution, as controlled by the Living Organizational Model broad Implementation Authority correction supplement, to autonomously materialize and verify the maximum coherent organization-first local Product experience in the existing HTML/CSS/JavaScript stack?

The accountable human must choose A, B, or C and provide attributable rationale.

## Required Decision record

Record the Decision in a new separate artifact:

`governance/proposals/LIVING_ORGANIZATIONAL_MODEL_BROAD_IMPLEMENTATION_AUTHORITY_DECISION.md`

The record must identify the accountable human and date; select A, B, or C; cite this consideration package by commit and blob; cite the controlling correction supplement; define any revisions if B; and preserve every non-authorization not expressly changed.

## Current authority effect

NONE. No option is selected. Implementation, UI/application/test changes, repository transition, dependencies, ROADMAP/BACKLOG changes, Watson, integration, deployment, Replay, H3, Root Cause, and causal proof remain unauthorized until an attributable human Decision is recorded.
